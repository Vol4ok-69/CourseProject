# Исполнительное резюме  
Я предлагаю спроектировать и реализовать **DatabaseAnalyzer** как расширение существующей системы анализа проектов. Для этого мы расширим `AnalyzerContext`, определим минимальную модель метаданных базы данных, реализуем набор правил анализа и покроем их тестами. DatabaseAnalyzer будет использовать EF Core-модель (IModel) анализируемого проекта: загружать её через `DbContext.Model` или собирать дизайн-время с помощью пакета EF Core Design. Результаты правил (AnalyzerFinding) будут сохраняться стандартно через `AnalysisService`. В отчёте приводится подробный план действий: входные данные, модель метаданных, конкретные правила (ID, важность, алгоритм), набор тестов, поэтапная реализация с указанием файлов, DI и примеров кода, список внешних библиотек и образец кода. Каждому этапу даны оценки трудозатрат и заметки о рисках.  

## 1) Входной контракт (AnalyzerContext)  
**Текущий контекст:** у `AnalyzerContext` уже есть `RepositoryPath` и `CommitHash`. Для DatabaseAnalyzer нужно дополнительное указание, как получать модель EF Core. Возможные варианты:  

- **Компиляция проекта:** ожидать, что проект с EF Core-контекстом уже собран, и передавать путь к сборке (.dll).  
- **Проектные файлы:** находить в `RepositoryPath` `.csproj` и компилировать или строить модель программно.  
- **Миграции/ModelSnapshot:** если в проекте есть миграции, можно загрузить метамодель из `ModelSnapshot`.  

**Предлагаю расширить `AnalyzerContext`:** добавить, например, свойства   
```csharp
public class AnalyzerContext
{
    public string RepositoryPath { get; init; } = null!;
    public string CommitHash { get; init; } = null!;
    // Новое для DatabaseAnalyzer:
    public string? DbContextClassName { get; init; }  // (необязательное, имя класса DbContext в проекте)
    public string? DbAssemblyPath { get; init; }     // (необязательное, путь к сборке с моделью)
}
```  
**Альтернативы и компромиссы:** можно обойтись без изменения контекста, полагаясь на расположение проекта (например, искать первый класс, наследующий DbContext). Но явно передать имя контекста или сборку проще и надёжнее. Если эти данные не указаны пользователем, стоит пометить поле как «не задано» и пытаться найти контекст по конвенции (например, по наличию `DbContext` в `RepositoryPath`).  

**Примечание:** конкретный механизм поиска/загрузки модели в контракте не регламентируется, поэтому здесь мы определяем только форму (типы и имя полей). Если способ не описан в документации, отмечаем это как «не специфицировано».  

## 2) Минимальная модель метаданных  
Нам нужен in-memory‑модель, отражающая структуру БД и EF-модели для правил. Классы (пример):  

```csharp
namespace ProjectAnalyzer.DatabaseModel
{
    public class DatabaseModel
    {
        public List<DbEntity> Entities { get; init; } = new();
    }

    public class DbEntity
    {
        public string Name { get; init; } = null!;            // имя сущности/таблицы
        public List<DbProperty> Properties { get; init; } = new();
        public DbKey? PrimaryKey { get; init; }              // первичный ключ (если есть)
        public List<DbForeignKey> ForeignKeys { get; init; } = new();
        public List<DbIndex> Indexes { get; init; } = new();
    }

    public class DbProperty
    {
        public string Name { get; init; } = null!;        // имя свойства/столбца
        public string ClrType { get; init; } = null!;     // CLR-тип (например, "int", "string")
        public bool IsNullable { get; init; }             // может ли быть null
        public int? MaxLength { get; init; }             // максимальная длина (для строк)
        public bool IsPrimaryKey { get; init; }          // является частью PK
    }

    public class DbKey
    {
        public List<string> Properties { get; init; } = new();  // имена свойств, составляющих ключ
    }

    public class DbForeignKey
    {
        public string PrincipalEntity { get; init; } = null!;    // имя связанной сущности (родителя)
        public List<string> PrincipalProperties { get; init; } = new();  // имена PK в родителе
        public List<string> DependentProperties { get; init; } = new();  // имена FK в дочерней сущности
        public bool IsUnique { get; init; }                      // уникальность (True для 1:1)
    }

    public class DbIndex
    {
        public string Name { get; init; } = null!;         // имя индекса
        public List<string> Properties { get; init; } = new();  // имена свойств, входящих в индекс
        public bool IsUnique { get; init; } = false;       // уникальный ли индекс
    }
}
```  

**Обоснование полей:** каждая `DbEntity` соответствует `IEntityType` (EF Core). Поле `Name` — название таблицы (можно взять через `entityType.GetDefaultTableName()`). Свойства (`DbProperty`) соответствуют `IProperty`: указываем имя, CLR-тип (для понимания семантики), nullability и ограничения (например, `MaxLength` по аннотации). Поле `IsPrimaryKey` помечает, что свойство входит в первичный ключ. `DbKey` хранит составной PK (список свойств) — map из `entityType.GetDeclaredKeys()`. Список `ForeignKeys` формируем из `entityType.GetDeclaredForeignKeys()`, где указываем родительскую сущность (`PrincipalEntity`) и свойства PK/FK. `DbIndex` соответствует индексам (`GetDeclaredIndexes()`), включаем имя, свойства и флаг уникальности.  

**Отображение EF Core → наша модель:** в `DatabaseAnalyzer` мы можем получить `IModel` из `DbContext.Model` (или через `DbContext.GetService<IModel>()`). Затем для каждого `entityType` из `model.GetEntityTypes()` формируем `DbEntity`:
- `Name = entityType.GetDefaultTableName()`,
- `Properties = entityType.GetDeclaredProperties().Select(p => new DbProperty { ... })`,
- `PrimaryKey = new DbKey { Properties = entityType.FindPrimaryKey()?.Properties.Select(p => p.Name).ToList() }`,
- `ForeignKeys = entityType.GetDeclaredForeignKeys().Select(fk => new DbForeignKey { ... })`,
- `Indexes = entityType.GetDeclaredIndexes().Select(ix => new DbIndex { ... })`.
Свойство `IsPrimaryKey` у `DbProperty` можно пометить по наличию `p.IsPrimaryKey()` у `IProperty` или сравнив имена с PK.  

> **Ссылка:** EF Core представляет модель через объекты типа `IEntityType`, `IProperty` и т.д. (метаданные о сущностях, ключах, связях).  

## 3) Конкретные правила анализа  
Из регламента следует общее требование проверить **структуру БД и нормальные формы**. Конкретных правил в документах явно не задано, поэтому предлагается базовый набор (например, как в типичных анализаторах структуры БД). При этом некоторые правила являются предположительными (отмечено *). Каждое правило имеет уникальный код, категорию (Severity) и алгоритм обнаружения. Ниже — приоритетный список:

| ID    | Описание                                    | Severity  | Алгоритм проверки                                                          | Сложность           |
|-------|---------------------------------------------|-----------|---------------------------------------------------------------------------|--------------------|
| DB01  | **Отсутствует первичный ключ у сущности.** Если у таблицы нет PK. | _Critical_ | Для каждой сущности `e`: `e.PrimaryKey == null`. Если да — отчёт.         | O(E) (обход сущностей) |
| DB02  | **Столбец без соответствующей навигации.** Если свойство FK не имеет парного навигационного свойства. <sup>✶</sup> | _Warning_  | Для каждой FK (`entity.FKs`): проверить, что у родителя есть обратная навигация. (Использовать `IForeignKey.DeclaringEntityType`)  | O(E·F) |
| DB03  | **Неявная связь «многие-ко-многим».** Если найдены два `INavigation` (skip navigation) друг на друга без промежуточной сущности. <sup>✶</sup> | _Info_    | Проверить пары `ISkipNavigation` (пропущенная сущность): у двух сущностей есть навигации друг на друга и нет явной `joinEntityType`. | O(N²) (проверка пар) |
| DB04  | **Нет индекса на FK-столбце.** (Рекомендация) Если FK-свойство не входит ни в один индекс. | _Info_    | Для каждой FK-пары: если ни один `DbIndex` не покрывает эти свойства.      | O(E·I) |
| DB05  | **Дублирующийся индекс.** Есть два индекса с одинаковыми столбцами. | _Info_    | Сравнить индексы в каждой `DbEntity` на совпадение списков свойств.        | O(E·I²) |

<sup>✶</sup> — признак, что правило выдвинуто «на догадку» (не содержится явно в документации регламента).  

**Примечания:**  
- *DB01* критично, так как EF требует наличие PK для сущности.  
- *DB02* выявляет, например, ситуацию, когда в модели указан `[ForeignKey]` без соответствующей навигации.  
- *DB03* проверяет, что многие-ко-многим не реализовано «скрыто» без явной связывающей таблицы (используя `GetSkipNavigations`).  
- Алгоритмы используют перебор сущностей и их метаданных (например, `GetDeclaredForeignKeys()`, `GetProperties()`, `GetNavigations()` из EF Core). Методы `GetDeclared*` упрощают обход (см. документацию EF Core).  

Каждое правило формирует `AnalyzerFinding` с нужным `RuleId` (например, `"DB01"`), `Severity`, и понятным `Message` (пример: *"Entity 'User' has no primary key defined."*).  

## 4) Юнит- и интеграционные тесты  
Для каждого правила пишем тесты (xUnit), проверяющие как позитивные, так и негативные сценарии. Тестовые данные можно создавать вручную, сконструировав `DatabaseModel` или `IModel` вручную. Рекомендуемые тесты:  

- **DB01:**  
  ```csharp
  [Fact]
  public void DB01_NoPrimaryKey_ShouldReport() {
      // Модель с сущностью без PK
      var model = new DatabaseModel {
          Entities = {
              new DbEntity {
                  Name = "T",
                  Properties = { new DbProperty { Name = "X", ClrType="int", IsNullable=false, IsPrimaryKey=false } },
                  PrimaryKey = null
              }
          }
      };
      var findings = new DatabaseAnalyzer().AnalyzeAsync(model).Result.Findings;
      Assert.Contains(findings, f => f.RuleId == "DB01" && f.EntityName == "T");
  }
  ```
  Также тест *не должно быть отчётов*, если PK задан.  
- **DB02:**  
  ```csharp
  [Fact]
  public void DB02_FKWithoutNavigation_ShouldReport() {
      // Два DbEntity: Parent и Child, у Child есть FK без навигации в Parent
      var parent = new DbEntity { Name = "Parent", PrimaryKey = new DbKey { Properties={"Id"} } };
      var child = new DbEntity { Name = "Child", Properties={ new DbProperty{Name="Id", IsPrimaryKey=true} },
                                ForeignKeys={ new DbForeignKey {
                                    PrincipalEntity="Parent",
                                    PrincipalProperties={"Id"},
                                    DependentProperties={"ParentId"},
                                    IsUnique=false } } };
      var model = new DatabaseModel { Entities = { parent, child } };
      var findings = new DatabaseAnalyzer().AnalyzeAsync(model).Result.Findings;
      Assert.Contains(findings, f => f.RuleId == "DB02");
  }
  ```
- **DB03:**  
  ```csharp
  [Fact]
  public void DB03_ImplicitManyToMany_ShouldReport() {
      // Сущности A и B с навигациями без сущности-join
      // В реальности SkipNavigation приходится собирать из EF, но для теста: 
      // Симулируем отсутствие явного DbEntity для связи.
      // (Можно проверять через наличие 2-way флага IsManyToMany без PK)
  }
  ```
- Аналогично тесты для *DB04, DB05*.  

Тесты размещаем в проекте `tests/DatabaseAnalyzer.Tests`, например в файле `DatabaseAnalyzerTests.cs`. При запуске `dotnet test` они должны проходить без ошибок: тестовая модель -> `DatabaseAnalyzer.Analyze` -> Assertions.

## 6) Интеграция в бекенд  
- **Регистрация в DI:** в `Program.cs` (или `Startup.cs`) добавить:  
  ```csharp
  services.AddTransient<IAnalyzer, DatabaseAnalyzer>();
  ```  
  Это позволит `AnalysisService` автоматически вызвать наш анализатор наряду с остальными.  
- **Вызов AnalyzeAsync:** `AnalysisService` перебирает все зарегистрированные `IAnalyzer` и вызывает `AnalyzeAsync(context)`. Важно передать расширенный `AnalyzerContext` с информацией о DbContext.  
- **Сохранение результатов:** `DatabaseAnalyzer` должен формировать `AnalysisResult`, где `Findings` (тип `AnalyzerFinding`) заполняются по правилам. Это уже встроено в `AnalysisService`: после анализа `AnalysisResult` сохраняется в БД (таблицы `Analyses` и `AnalysisResults`). Дополнительных миграций не требуется (используются существующие сущности `AnalysisResult`).  
- **Обратная совместимость:** Поскольку `DatabaseAnalyzer` добавляется как новый анализатор, старые функции не затрагиваются. Если для старых `Analysis` не указывать новых полей, система продолжит работать как прежде. Если поля `DbContextClassName`/`DbAssemblyPath` не заданы, можно просто пропустить `DatabaseAnalyzer` или выдать предупреждение.  

**Пример DI-регистрации:** (в `Program.cs`)  
```csharp
builder.Services.AddTransient<IAnalyzer, CSharpAnalyzer>();
builder.Services.AddTransient<IAnalyzer, DatabaseAnalyzer>();
```  

Таким образом, после выполнения основных анализаторов AnalysisService сохранит `Analysis` и `AnalysisResult` в БД как обычно.  

## 7) Библиотеки и ссылки  
- **Microsoft.EntityFrameworkCore.Design** – содержит классы для построения модели на этапе дизайна. Помогает получить `IModel` без реальной БД.  
- **Microsoft.EntityFrameworkCore** – основной пакет EF Core, даёт `DbContext`, `IModel`, `IEntityType` и т.д. (ссылки на интерфейсы см. документацию).  
- **Microsoft.EntityFrameworkCore.Sqlite** или любой провайдер – можно использовать In-Memory или SQLite для инициализации контекста во время анализа, чтобы получить модель (опционально, если нужно эмуляция БД).  
- **Microsoft.Extensions.DependencyInjection** – для регистрации `IAnalyzer`.  
- **xUnit.net** – для написания тестов (и AutoFixture/Bogus для генерации тестовых данных, при желании).  
- **Roslyn Analyzer SDK** – *не требуется*, т.к. анализ делается на метаданных EF, а не на AST.  

Дополнительно рекомендую изучить примеры использования EF Core Metadata API (Microsoft Learn) и общие советы по написанию анализаторов кода (например, [Wikipedia о статическом анализе][1]).

## 8) Прототип (первые изменения)  
Для демонстрации можно сразу сделать минимальный end-to-end прототип:  

- **Файл:** `src/Analyzers/Database/DatabaseAnalyzer.cs`  
  ```csharp
  public class DatabaseAnalyzer : IAnalyzer
  {
      public string Name => "Database Analyzer";

      public async Task<AnalysisResult> AnalyzeAsync(AnalyzerContext context)
      {
          var result = new AnalysisResult { AnalyzerName = Name };
          // Загрузим модель EF:
          // Здесь упрощенно: ожидаем DbContextClassName заданным
          if (context.DbAssemblyPath != null)
          {
              var asm = Assembly.LoadFrom(context.DbAssemblyPath);
              var ctxType = asm.GetTypes().FirstOrDefault(t => 
                  typeof(DbContext).IsAssignableFrom(t));
              if (ctxType != null)
              {
                  var options = new DbContextOptionsBuilder()
                      .UseSqlite("Data Source=:memory:")
                      .Options;
                  var db = (DbContext)Activator.CreateInstance(ctxType, new object[]{ options });
                  var efModel = db.Model;
                  // Построим простую DatabaseModel для демонстрации:
                  var firstEntity = efModel.GetEntityTypes().FirstOrDefault();
                  if (firstEntity != null)
                  {
                      result.Findings.Add(new AnalyzerFinding {
                          RuleId = "DB-demo",
                          Message = $"Found entity {firstEntity.Name}",
                          Severity = Severity.Info
                      });
                  }
              }
          }
          return result;
      }
  }
  ```
- **Расширение `AnalyzerContext`:** (если нужно)  
  ```csharp
  public class AnalyzerContext
  {
      public string RepositoryPath { get; init; } = null!;
      public string CommitHash { get; init; } = null!;
      public string? DbAssemblyPath { get; init; }
  }
  ```  
- **Регистрация в DI:** в `Program.cs`:  
  ```csharp
  builder.Services.AddTransient<IAnalyzer, DatabaseAnalyzer>();
  ```  
- **Тест-пример:** (xUnit в `tests/DatabaseAnalyzer.Tests`)  
  ```csharp
  public class DatabaseAnalyzerTests
  {
      [Fact]
      public async Task DemoRule_FindsEntity()
      {
          var ctx = new AnalyzerContext { DbAssemblyPath = "path/to/test/db.dll" };
          var analyzer = new DatabaseAnalyzer();
          var result = await analyzer.AnalyzeAsync(ctx);
          Assert.Contains(result.Findings, f => f.RuleId == "DB-demo");
      }
  }
  ```  

Этот прототип показывает основу: получение модели и добавление хотя бы одного `Finding`. После этого можно постепенно внедрять реальные правила и тесты.  

## 9) Таймлайн и стратегия коммитов  
Предлагается итеративный подход с небольшими коммитами (test-first):  
- **[Commit]** `feat: add DatabaseModel classes` – создание классов `DbEntity`, `DbProperty` и др., компиляция.  
- **[Commit]** `feat: extend AnalyzerContext` – добавить поля `DbContextClassName`, `DbAssemblyPath`.  
- **[Commit]** `feat: add DatabaseAnalyzer skeleton` – пустой анализатор, тест на пустой результат.  
- **[Commit]** `feat: register DatabaseAnalyzer in DI` – мелкое добавление, smoke-test `test_all.ps1`.  
- **[Commit]** `feat: load EF model in DatabaseAnalyzer` – код загрузки модели, тест на успешную загрузку (создание тестового DbContext).  
- **[Commit]** `feat: mapping to DatabaseModel` – реализовать преобразование `IModel → DatabaseModel`, покрыть тестом.  
- **[Commit]** `feat: implement rule DB01` – код проверки отсутствия PK, с тестом.  
- **[Commit]** `feat: implement rule DB02` – код проверки FK без навигации, с тестами.  
- **...** (дальше DB03, DB04, DB05)  
- **[Commit]** `test: add tests for DB03–DB05` – написать тесты и убедиться, что их можно корректно выполнять (может потребоваться конструкция тестовых моделей).  
- **[Commit]** `chore: update test_all.ps1 with database analyzer tests` – добавить сценарии в интеграционный скрипт (запустить анализ, проверить результат).  
- **[Commit]** `docs: add design summary for DatabaseAnalyzer` – обновить документацию и регламент (при необходимости).  

Примерное время: 13–15 часов, с учётом отладки и правок.  

## 10) Источники  
- **EF Core Metadata API:** `DbContext.Model` содержит метаданные модели (сущности, свойства, связи). Класс `IEntityType` представляет сущность в модели, методы `GetDeclaredProperties()`, `GetDeclaredKeys()`, `GetDeclaredForeignKeys()` позволяют извлекать поля и связи. Эти ресурсы служат основой для нашего маппинга.  
- **Пользовательские анализаторы кода:** общие принципы статического анализа (без фактической загрузки кода), описаны в литературе по статическому анализу (например, Википедия о статическом анализе[1]). Хотя наш анализатор работает на метаданных модели, концепции единиц анализа (правило, сообщение, severity) аналогичны.  
- **.NET Dependency Injection:** добавление сервисов через `services.AddTransient<IAnalyzer, T>()` – стандартная практика в ASP.NET Core.  
- **xUnit.net:** руководство по написанию тестов (необходимо для раздела с тестами).  

Все приведённые решения основаны на официальной документации EF Core и практике разработки статических анализаторов в .NET.
