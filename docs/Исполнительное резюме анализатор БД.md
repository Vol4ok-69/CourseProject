# Спецификация компонента DatabaseAnalyzer

## 1. Назначение и роль компонента
Модуль **DatabaseAnalyzer** (`src/Analyzers/Database`) предназначен для статического анализа структуры реляционной базы данных и схемы связей на основе метаданных Entity Framework Core.
Компонент выявляет архитектурные и структурные дефекты схемы (отсутствие первичных ключей, неиндексированные внешние ключи, дублирующиеся индексы, отсутствие навигационных свойств, неявные промежуточные таблицы) без подключения к работающему серверу СУБД и без необходимости сборки или выполнения анализируемого кода (`dotnet build` / `Assembly.LoadFrom`).

В серверном конвейере `Backend.Api` компонент подключается через единый контракт `IAnalyzer` и возвращает список унифицированных замечаний `AnalyzerFinding`.

---

## 2. Архитектура и целевой конвейер анализа

Актуальный production-конвейер получения и анализа метаданных изолирован и разделен на статический синтаксический анализ и автономное исполнение правил в контейнере:

```
[AnalyzerContext] (RepositoryPath, CommitHash, ProjectPath?)
       │
       ▼
[IRoslynMetadataExtractor] (RoslynMetadataExtractor)
  - Статический парсинг C# AST синтаксических деревьев без сборки проекта
  - Извлечение моделей DbContext, конфигураций OnModelCreating и IEntityTypeConfiguration
  - Формирование DTO входного контракта DatabaseAnalyzerInputDocument
       │
       ▼
[IDatabaseContainerRunner] (DatabaseContainerRunner)
  - Валидация входного JSON по database-analyzer-input-v1.schema.json
  - Запись input.json в защищенный обменный том (courseproject-exchange-data)
  - Запуск изолированного Docker-контейнера netscope-database-analyzer:latest
    (--network none, --read-only, tmpfs /tmp, non-root appuser, memory/cpu limits)
       │
       ▼
[NetScope.DatabaseAnalyzer.Runner] (Автономный CLI-процесс в контейнере)
  - Десериализация DTO через System.Text.Json (source generation)
  - Валидация схемы и проверка поддерживаемых capabilities
  - Вычисление правил DB01–DB05 движком DatabaseRulesEngine
  - Атомарная запись output.json по database-analyzer-output-v1.schema.json
       │
       ▼
[DatabaseAnalyzer] (IAnalyzer)
  - Чтение и валидация output.json из обменного каталога
  - Преобразование выходных FindingContract в AnalyzerFinding
  - Возврат замечаний в конвейер AnalysisService
```

### Историческая реализация (Legacy / In-Process Provider)
В проекте `src/Analyzers/Database` сохранены классы исторического in-process конвейера:
- `IDatabaseProjectResolver` / `EfCoreDatabaseProjectResolver` (поиск `.csproj` и наследников `DbContext`);
- `IEfCoreModelInspector` / `EfCoreModelInspector` (сборка проекта через `dotnet build` и загрузка сборок через `Assembly.LoadFrom`);
- `EfCoreMetadataMapper` (преобразование живого `IModel` в промежуточную модель);
- `IDatabaseMetadataProvider` / `EfCoreMetadataProvider` (объединяющий фасад).

Эти компоненты сохранены в репозитории и покрыты модульными тестами для сравнительного бенчмаркинга и обратной совместимости, но **не зарегистрированы в production DI-контейнере** `Backend.Api`, устраняя риски выполнения произвольного недоверенного кода и нестабильности сборок в runtime.

## 3. Спецификация правил анализа (DB01–DB05)

Все правила исполняются автономным движком `DatabaseRulesEngine` в `NetScope.DatabaseAnalyzer.Runner` и дублируются эталонными тестами.

### DB01: Сущность без первичного ключа
- **Код правила:** `DB01`
- **Идентификатор:** `PrimaryKeyRequired`
- **Уровень критичности:** `Severity.Warning`
- **Назначение:** Обнаружение сущностей реляционной модели данных, для которых не определен первичный ключ.
- **Условие срабатывания:** Сущность отображена на таблицу (`MappingType.Table`), имеет статус ключа `KeyType.Unknown` или `KeyType.Keyless` без явного исключения, либо в коллекции `Keys` отсутствует ключ с `IsPrimaryKey == true`.
- **Текст сообщения:**
  `Entity '{entity.Name}' does not have a primary key defined.`
- **Рекомендация:**
  `Define a primary key for entity '{entity.Name}' using HasKey() or [Key] attribute, or explicitly configure it as Keyless entity if it represents a view or query.`
- **Ограничения:** Для представлений (Views), функций и SQL-запросов уровень задан как `Warning`, допуская осознанный выбор архитектора модели.

---

### DB02: Внешний ключ без навигационного свойства к главной сущности
- **Код правила:** `DB02`
- **Идентификатор:** `UnidirectionalRelationship` / `MissingNavigationToPrincipal`
- **Уровень критичности:** `Severity.Warning`
- **Назначение:** Проверка соблюдения проектных соглашений двунаправленной навигации связей.
- **Условие срабатывания:** Внешний ключ не имеет навигационного свойства к главной сущности (`NavigationToPrincipal == null` или пусто).
- **Текст сообщения:**
  `Foreign key from '{entity.Name}' to '{foreignKey.PrincipalEntityName}' has no navigation property to the principal entity.`
- **Рекомендация:**
  `Consider adding a navigation property to the principal entity '{foreignKey.PrincipalEntityName}' for better queryability and domain clarity.`
- **Ограничения:** Выполняется консервативно: при `IsNavigationResolved == false` или неполных метаданных навигаций проверка пропускается с фиксацией диагностики.

---

### DB03: Неявная связь многие-ко-многим через скрытую промежуточную таблицу
- **Код правила:** `DB03`
- **Идентификатор:** `ManyToManyPattern` / `ImplicitManyToMany`
- **Уровень критичности:** `Severity.Info`
- **Назначение:** Выявление связей many-to-many, сконфигурированных без явного объявления связующей доменной сущности (join entity).
- **Условие срабатывания:** Обнаружение skip-навигации (`SkipNavigations`), для которой промежуточная таблица не имеет явной доменной сущности. Применяется лексикографическая дедупликация между связанными сущностями.
- **Текст сообщения:**
  `Many-to-many relationship between '{entity.Name}' and '{skipNav.TargetEntityName}' uses an implicit join entity '{skipNav.JoinEntityName}'.`
- **Рекомендация:**
  `Consider defining an explicit join entity for '{skipNav.JoinEntityName}' to support additional attributes and better control over indexes.`

---

### DB04: Внешний ключ без подходящего индекса
- **Код правила:** `DB04`
- **Идентификатор:** `MissingForeignKeyIndex`
- **Уровень критичности:** `Severity.Warning`
- **Назначение:** Предотвращение деградации производительности операций JOIN, фильтрации и каскадного удаления из-за отсутствия индексов на столбцах внешних ключей.
- **Условие срабатывания:** Столбцы внешнего ключа не покрываются ни одним индексом сущности в качестве точного лидирующего префикса в том же порядке.
- **Текст сообщения:**
  `Foreign key ({string.Join(", ", foreignKey.Properties)}) in entity '{entity.Name}' is not covered by any index.`
- **Рекомендация:**
  `Add an index starting with columns ({string.Join(", ", foreignKey.Properties)}) to improve join and delete performance.`
- **Связанный технический долг:** Задачи TD-004 и TD-005 в проектном плане технического долга направлены на добавление недостающих индексов внешних ключей в миграциях и сущностях модели.

---

### DB05: Дублирующиеся индексы
- **Код правила:** `DB05`
- **Идентификатор:** `DuplicateIndex`
- **Уровень критичности:** `Severity.Warning`
- **Назначение:** Обнаружение избыточных индексов, замедляющих операции вставки/обновления (INSERT/UPDATE/DELETE) и нерационально расходующих дисковое пространство.
- **Условие срабатывания:** Наличие двух индексов на одной сущности с идентичной последовательностью столбцов, совпадающим признаком уникальности (`IsUnique`) и эквивалентными фильтрами.
- **Текст сообщения:**
  `Index '{index.Name}' duplicates another index on entity '{entity.Name}' covering columns ({string.Join(", ", index.Properties)}).`
- **Рекомендация:**
  `Remove redundant duplicate index '{index.Name}' to save storage and write overhead.`

## 4. Ограничения и нормализация базы данных

1. **Нормализация 2НФ и 3НФ:**
   Статический анализ метаданных EF Core **не может служить строгим математическим доказательством** соблюдения второй и третьей нормальных форм. Вторая и третья нормальные формы определяются функциональными зависимостями предметной области ($X \rightarrow Y$), которые не выражаются типами данных C# и не сохраняются в реляционной схеме без семантики предметной области.
   `DatabaseAnalyzer` выполняет эвристический структурный аудит:
   - гарантирует наличие суррогатных/естественных первичных ключей (`DB01`);
   - контролирует ссылочную целостность и связность внешних ключей (`DB02`);
   - обеспечивает эффективную индексацию соединений (`DB04`).
2. **Особенности статического анализа Roslyn:**
   - Не требуется компиляция или запуск внешних процессов в анализируемом репозитории.
   - Метаданные извлекаются из объявлений `DbContext`, атрибутов моделей (`[Key]`, `[ForeignKey]`, `[Index]`) и конфигураций Fluent API (`IEntityTypeConfiguration<T>`).
   - При обнаружении сложных конструкций, не поддающихся статическому выводу, формируются диагностические флаги неполноты (`hasIncompleteMetadata`), предотвращающие ложные срабатывания.

## 5. Тестовое покрытие
Подсистема анализа метаданных БД полностью покрыта автоматизированными тестами xUnit:
- **`DatabaseAnalyzer.Tests` (173 теста, 180 с учетом вариантов Theory):**
  - тесты статического анализатора и извлечения метаданных Roslyn;
  - тесты отображения моделей и разрешения сущностей;
  - исторические тесты in-process компонентов (`EfCoreModelInspector`, `EfCoreMetadataMapper`, `EfCoreDatabaseProjectResolver`);
  - тесты уникальных индексов EF Core модели (`Roles`, `Users`, `Projects`, `Commits`).
- **`DatabaseAnalyzer.Runner.Tests` (103 теста, 110 с учетом вариантов Theory):**
  - тесты независимого движка правил `DatabaseRulesEngine` для DB01–DB05;
  - контрактные тесты валидации JSON-схем входа и выхода (`database-analyzer-input-v1.schema.json` и `database-analyzer-output-v1.schema.json`);
  - тесты CLI runner, обработки таймаутов, частичных метаданных и сценариев ошибок;
  - тесты source generation сериализации `System.Text.Json`.

Все 276 тестов анализатора БД регулярно верифицируются и успешно проходят в тестовом контуре проекта.
