# Технический регламент

## 1. Общая архитектура и разделение ответственности
Система представляет собой программный комплекс для статического анализа C#/.NET-проектов и связанных схем баз данных Entity Framework Core. Архитектура построена по принципам чистой слоистой архитектуры (Clean/Layered Architecture) в виде модульного монолита.
Логические компоненты системы:
- **Серверное API (ASP.NET Core Web API)** — оркестрация задач анализа, управление проектами, пользователями и аутентификацией, предоставление REST API.
- **Модули анализаторов (Analyzers)** — независимые библиотеки, реализующие унифицированный контракт `IAnalyzer` и выполняющие проверку кода и метаданных.
- **Хранилище данных (PostgreSQL)** — хранение учетных записей, проектов, коммитов, истории запусков анализа и детализированных результатов (замечаний).
- **Клиентские приложения (Desktop, CLI, Telegram-бот)** — внешние клиенты, исходный код которых размещается в каталоге `src` монорепозитория, а распространение осуществляется через отдельные публичные репозитории. Клиенты взаимодействуют с системой исключительно через REST API и не имеют прямого доступа к базе данных.

## 2. Выбор архитектурного стиля
В качестве архитектурного стиля проекта принят **модульный монолит** на платформе ASP.NET Core (.NET 10).
- Все серверные модули и анализаторы объединены в рамках единого решения `CourseProject.slnx`.
- Переход на микросервисную архитектуру и использование внешних распределенных брокеров сообщений (RabbitMQ, Apache Kafka, Redis, Hangfire) исключены из рамок MVP как создающие неоправданную сложность для курсового проекта.
- Взаимодействие между прикладными сервисами и анализаторами внутри монолита осуществляется через внедрение зависимостей (Dependency Injection) по общему интерфейсу `IAnalyzer`.

## 3. Структура репозитория и проектов
Репозиторий организован по схеме единого репозитория (monorepo):
- `src/Backend/Domain` — сущности предметной области, перечисления и базовые бизнес-правила (не зависит от внешних библиотек и БД).
- `src/Backend/Application` — прикладные сервисы, контракты репозиториев, оркестрация анализа (`AnalysisService`), DTO и интерфейс `IAnalyzer`.
- `src/Backend/Infrastructure` — реализация доступа к данным через EF Core (`AppDbContext`), миграции PostgreSQL, репозитории, JWT и взаимодействие с GitHub API (`RepositorySourceService`).
- `src/Backend/Api` — контроллеры ASP.NET Core, конфигурация DI, Swagger-документация и запуск приложения.
- `src/Analyzers/CSharp` — статический анализатор C# на базе Roslyn (правила `CSHARP001`, `CSHARP002`).
- `src/Analyzers/Database` — анализатор моделей данных EF Core (правила `DB01`–`DB05`).
- `src/Analyzers/Sql` — модуль статического анализа SQL и вызовов методов запросов EF Core (правила `SQL001`, `SQL002`).
- `src/Analyzers/Security` — модуль статического анализа базовых проблем безопасности (правила `SEC001`–`SEC005`).
- `src/Desktop`, `src/Cli`, `src/Bot` — исходный код клиентских приложений в составе монорепозитория (их внешние публичные репозитории служат зеркалами для публикации).
- `tests/SqlAnalyzer.Tests`, `tests/CSharpAnalyzer.Tests`, `tests/SecurityAnalyzer.Tests`, `tests/Backend.Tests`, `tests/DatabaseAnalyzer.Tests` — модульные, компонентные и сервисные тесты (709 тестов). Детальный аудит: `docs/audits/test-suite-evaluation.md`.
- `docker-compose.yml` — конфигурация развертывания контейнера PostgreSQL 17.

## 4. Нейминг и соглашения по коду
В проекте строго соблюдаются официальные соглашения C# и правила репозитория (`AGENTS.md`):
- `PascalCase` — для названий классов, интерфейсов, структур, перечислений, методов, свойств и публичных членов.
- `camelCase` — для локальных переменных и параметров методов.
- `_camelCase` — для приватных полей экземпляров классов.
- Именование сущностей, DTO и сервисов должно четко отражать их назначение.
- В кодовой базе и миграциях не допускается произвольное смешивание стилей.

## 5. Организация API и взаимодействие
Сервер предоставляет защищенный REST API по протоколу HTTPS в формате JSON:
- **Аутентификация:** JWT Bearer-токены. Защищенные эндпоинты требуют заголовок `Authorization: Bearer <token>`.
- **Маршрутизация:** иерархические RESTful-маршруты:
  - Авторизация: `POST /api/auth/register`, `POST /api/auth/login`.
  - Проекты: `GET/POST /api/projects`, `GET/PUT/DELETE /api/projects/{id}`.
  - Коммиты: `GET/POST /api/projects/{projectId}/commits`.
  - Синхронизация с GitHub: `POST /api/projects/{projectId}/github/sync`.
  - Анализ: `POST /api/projects/{projectId}/commits/{commitId}/analyses`, `GET /api/projects/{projectId}/commits/{commitId}/analyses`, `GET .../analyses/{analysisId}`.
- **Документация:** Swagger UI (`/swagger`) на базе OpenAPI 3.0 генерируется автоматически с включением XML-комментариев.

## 6. Работа с GitHub-репозиториями
Интеграция с GitHub реализуется на сервере через сервис `RepositorySourceService`:
- Пользователь указывает URL публичного репозитория GitHub и хэш коммита (или использует автоматическую синхронизацию коммитов через `IGitHubService`).
- Сервер скачивает архив исходного кода по указанному коммиту через GitHub REST API (`https://api.github.com/repos/{owner}/{repo}/zipball/{commitSha}`).
- Архив распаковывается во временный изолированный каталог на диске сервера.
- Анализаторы получают путь к распакованному репозиторию через `AnalyzerContext.RepositoryPath`.
- **Очистка временных каталогов и известная проблема изоляции (DEF-003):**
  - В основном блоке `finally` метода `AnalysisService.ExecuteAnalysisAsync` очистка вызывается через `repositorySourceService.CleanupAsync()` только при сохранении владения задачей (`!ownershipLost`), чтобы предотвратить удаление рабочей директории другим воркером, перехватившим задачу по истечении срока аренды (lease).
  - Однако в методе `RepositorySourceService.DownloadAndExtractAsync` (а также `ExtractArchiveAsync`) блок `catch` при возникновении сбоя или отмены скачивания выполняет безусловный вызов `await CleanupAsync(analysisId, CancellationToken.None)`.
  - Так как рабочий каталог формируется строго по `analysisId` (без включения уникального `ExecutionToken`), при истечении аренды новый воркер может начать обработку задачи в том же каталоге, а завершающийся сбоем предыдущий воркер удалит файлы нового воркера.
  - Таким образом, в текущей кодовой базе **не обеспечивается полная изоляция очистки между воркерами** при конкурентном перехвате задач.
  - **Утвержденное архитектурное решение (ADR-001 / TD-003, статус ACCEPTED):** согласован переход на схему путей `{Storage:AnalysisPath}/{AnalysisId}/{ExecutionToken}` с выносом корня в конфигурацию `Storage:AnalysisPath` (по умолчанию системный Temp-каталог, категорический запрет размещения в `AppContext.BaseDirectory`), сквозной передачей `ExecutionToken` во все методы конвейера, удалением строго каталога текущего токена в `finally` и разработкой фонового механизма очистки «сиротских» каталогов (со строгой проверкой по паре AnalysisId и ExecutionToken, синхронизацией проверки в БД и удаления для защиты от гонок, безусловным сохранением каталогов новых активных токенов того же анализа и отказом от удаления при отсутствии надёжной синхронизации; удаление только по TTL запрещено). Задача зафиксирована в плане технического долга ([`TD-003`](plans/Technical-Debt-Plan.md#td-003)). Воркеры обязаны удерживать разделяемую блокировку `pg_advisory_lock_shared` для `AnalysisId` на протяжении всех файловых операций. После получения `pg_advisory_lock_shared` рабочий процесс обязан повторно проверить в PostgreSQL, что его `ExecutionToken` по-прежнему является актуальным для соответствующего `AnalysisId`. Только после успешной проверки разрешается создавать, распаковывать, читать или изменять файлы рабочего каталога (если токен больше не актуален или состояние БД невозможно достоверно проверить, воркер обязан освободить блокировку и прекратить выполнение без файловых операций). Фоновый очиститель получает эксклюзивный `pg_advisory_lock` для того же `AnalysisId`. После получения эксклюзивной блокировки очистка повторно проверяет актуальный `ExecutionToken` в БД и удаляет только директории, чей токен отличается от актуального токена в БД (директорию актуального запуска удалять запрещено). При потере соединения с БД или блокировки операции немедленно прекращаются, а при невозможности достоверной проверки удаление не выполняется.

## 7. Модули анализаторов
Каждый анализатор представляет собой независимую библиотеку классов и реализует интерфейс `IAnalyzer`:
```csharp
public interface IAnalyzer
{
    AnalyzerType Type { get; }
    Task<IReadOnlyList<AnalyzerFinding>> AnalyzeAsync(
        AnalyzerContext context,
        CancellationToken cancellationToken = default);
}
```
- **Статус реализации:**
  - `CSharpAnalyzer` (реализован): разбор AST синтаксических деревьев Roslyn, правила `CSHARP001` (LargeClass > 500 строк), `CSHARP002` (LongMethod > 50 строк).
  - `DatabaseAnalyzer` (реализован): разрешение проектов через `IDatabaseProjectResolver`, инспекция `IModel` во временной сборке через `IEfCoreModelInspector`, маппинг в `DatabaseMetadata` через `EfCoreMetadataMapper`, правила `DB01`–`DB05`.
  - `SqlAnalyzer` (реализован): статический анализ LINQ/SQL вызовов через Roslyn (правила `SQL001`, `SQL002`). Покрыт 44 тестами xUnit.
  - `SecurityAnalyzer` (реализован): статический поиск открытых секретов, небезопасного CORS, слабой криптографии и отключения валидации сертификатов (правила `SEC001`–`SEC005`). Покрыт 56 тестами xUnit.

> [!NOTE]
> **Целевое архитектурное решение для DatabaseAnalyzer и конвейера (ADR-001, статус ACCEPTED):**
> В рамках устранения дефектов DEF-001/DEF-002 и задач TD-001/TD-002 утверждена взаимодополняющая двухкомпонентная архитектура:
> 1. **Статический анализ C# AST на базе Roslyn:** извлечение метаданных моделей EF Core переводится на статический анализ синтаксических деревьев без предварительной компиляции (`dotnet build`) и без динамической загрузки сторонних сборок в процесс сервера, что устраняет конкретные векторы выполнения недоверенного кода в основном процессе бэкенда. Отказ от загрузки пользовательских сборок в `AssemblyLoadContext.Default` исключает прежний механизм накопления невыгружаемых пользовательских сборок. Это не является гарантией отсутствия любых утечек памяти CLR. Поддерживается строго согласованный перечень Fluent API и Data Annotations, разделение нескольких `DbContext`, статически обнаруживаемые конфигурации в `ApplyConfiguration` / `ApplyConfigurationsFromAssembly` и глубина обхода локальных вспомогательных методов строго до 3 уровней с защитой от циклов.
> 2. **Внешний изолированный контейнер (Docker/Podman):** для глубокого анализа физической структуры БД (PostgreSQL/SQL), DDL-скриптов и специализированных утилит утверждается вынос во внешний контейнер. Контейнер работает строго офлайн (`--network none`), не подключается к пользовательской или рабочей PostgreSQL по сети, анализирует подготовленные входные данные (SQL/DDL, метаданные EF Core) без передачи серверных секретов бэкенда и возвращает результат по выделенному независимому JSON-контракту, преобразование которого во внутренние `AnalyzerFinding` выполняется на стороне бэкенда (сетевое подключение к СУБД в будущем потребует отдельного ADR).
> 3. **Разграничение с `SqlAnalyzer`:** существующий `SqlAnalyzer` (`src/Analyzers/Sql`) сохраняет синтаксический анализ SQL на уровне C# AST (правила `SQL001`, `SQL002`) и не дублирует функционал контейнера.
> 4. **Отказоустойчивость конвейера:** частичный сбой или отсутствие моделей EF Core не приводит к аварийному завершению всего анализа коммита: результаты `CSharpAnalyzer`, `SqlAnalyzer` и `SecurityAnalyzer` сохраняются в базе данных, статус коммита переходит в `Completed`, а причина фиксируется через `AnalyzerFinding` с уровнем `Severity.Warning`.
> *(Реализация утвержденных решений запланирована в TD-001 и TD-002; в текущей кодовой базе коммита 2068c51 сохраняется реализация через `EfCoreModelInspector`).*

## 8. Хранение результатов анализа и схема БД
Схема базы данных спроектирована в третьей нормальной форме (3НФ) в PostgreSQL:
- **Таблицы (PascalCase во множественном числе в кавычках):**
  - `"Roles"` — системные роли пользователей (`Id`, `Name`).
  - `"Users"` — учетные записи (`Id`, `Username`, `PasswordHash`, `RoleId`, `EncryptedGitHubToken`, `GitHubUsername`, `GitHubTokenCreatedAt`).
  - `"Projects"` — исследуемые проекты (`Id`, `Name`, `RepoUrl`, `OwnerId`).
  - `"Commits"` — версии проектов (`Id`, `ProjectId`, `CommitHash`, `CommitDate`).
  - `"Analyses"` — сессии и очередь задач анализа (`Id`, `CommitId`, `Status`, `CreatedAt`, `StartedAt`, `CompletedAt`, `LeaseExpiration`, `ExecutionToken`, `ErrorMessage`).
  - `"AnalysisResults"` — выявленные нарушения (`Id`, `AnalysisId`, `FilePath`, `LineNumber`, `Rule`, `Message`, `Severity`, `Recommendation`, `AnalyzerType`).
- **Индексы:**
  - Уникальные: `IX_Roles_Name` (`Name`), `IX_Users_Username` (`Username`), `IX_Projects_OwnerId_Name` (`OwnerId`, `Name`), `IX_Commits_ProjectId_CommitHash` (`ProjectId`, `CommitHash`).
  - Внешних ключей и очереди: `IX_Users_RoleId`, `IX_Projects_OwnerId`, `IX_Commits_ProjectId`, `IX_Analyses_CommitId_CreatedAt`, `IX_Analyses_Status_CreatedAt`, `IX_AnalysisResults_AnalysisId`.

> **Примечание о верификации схемы:** Актуальный состав таблиц и столбцов зафиксирован на основе кода доменных сущностей, конфигураций `IEntityTypeConfiguration` и миграций EF Core (включая `20261030064123_AddDurableAnalysisQueue`, `20261031081432_AddAnalysisErrorMessage` и `20261103101757_AddUserGitHubIntegration`). Так как во время аудита контейнер PostgreSQL на порту `5433` не был запущен, фактическое применение миграций к работающей базе данных требует валидации при развертывании инфраструктуры.

## 9. Entity Framework Core + PostgreSQL
Для доступа к данным используется EF Core 10 с провайдером Npgsql:
- Все имена таблиц и столбцов задаются в `PascalCase` и заключаются в кавычки (`"Roles"`, `"Id"`, `"RoleId"`). Использование соглашения `snake_case` исключено для обеспечения полного соответствия кодовой базе и нормативу `docs/Правила-базы-данных.txt`.
- Первичные ключи имеют строго имя `"Id"` и тип integer с генерацией `.UseIdentityByDefaultColumn()` (`GENERATED BY DEFAULT AS IDENTITY`).
- Внешние ключи именуются по формату `"{ИмяТаблицы}Id"` (`RoleId`, `OwnerId`, `ProjectId`, `CommitId`, `AnalysisId`).
- Управление схемой выполняется строго через механизм миграций EF Core в проекте `Infrastructure`.

## 10. Авторизация и аутентификация
В системе реализована ролевая модель доступа (RBAC):
- Роли: `Admin` и `User`.
- Пароли хэшируются с солью с помощью алгоритма BCrypt (`IPasswordHasher`).
- При успешном входе генерируется JWT-токен (`JwtTokenService`) с claims `NameIdentifier`, `Name`, `Role`.
- Администратор имеет право просматривать и изменять данные любых пользователей; обычный пользователь — только собственные проекты и запуски анализов.

## 11. Фоновые задачи и жизненный цикл анализа
- **Фактическое состояние в кодовой базе (Асинхронная очередь в PostgreSQL):**
  1. PostgreSQL является долговременным надёжным хранилищем состояния задач.
  2. Клиент отправляет запрос `POST /api/projects/{projectId}/commits/{commitId}/analyses`.

  3. API проверяет отсутствие активного анализа на этот коммит (дедупликация через транзакционную блокировку `analysis_enqueue_{commitId}`), создаёт запись в таблице `"Analyses"` со статусом `Pending` и немедленно возвращает `202 Accepted` со ссылкой на ресурс задачи.
  4. Фоновый обработчик `AnalysisBackgroundService` ASP.NET Core извлекает ожидающие задачи из PostgreSQL методом `AcquireNextPendingAnalysisAsync` по алгоритму `SELECT ... FOR UPDATE SKIP LOCKED`, исключая гонки между воркерами, переводит их в статус `Running`, устанавливает токен выполнения `ExecutionToken` и срок аренды `LeaseExpiration`.
  5. В процессе анализа воркер периодически продлевает аренду (`HeartbeatAsync`). При завершении результаты сохраняются в `"AnalysisResults"`, а статус анализа обновляется на `Completed` (или `Failed` с фиксацией ошибки в `ErrorMessage`).

  6. Клиент отслеживает прогресс и получает результаты отдельными запросами `GET .../analyses/{analysisId}`.
  7. Применение внешних брокеров (RabbitMQ, Redis) исключено: при перезапуске сервера незавершённые задачи восстанавливаются непосредственно из PostgreSQL.
- **Исторический контекст:**
  На начальном этапе прототипирования запуск анализа в методе `AnalysesController.Create` выполнялся синхронно в рамках одного HTTP-запроса (`await analysisService.AnalyzeAsync(...)`), возвращая `200 OK` с готовым объектом `AnalysisDto` для простоты первых тестов. Это решение было полностью заменено на асинхронную архитектуру очереди.









## 12. Логирование и диагностика
- Логирование в системе организовано с использованием стандартных интерфейсов `Microsoft.Extensions.Logging` (`ILogger<T>`).
- Журналируются ключевые события: регистрация и аутентификация, загрузка исходных кодов с GitHub, время работы анализаторов и ошибки выполнения операций.
- Вывод логов осуществляется в стандартный поток консоли и в файлы логов с ротацией.

## 13. Обработка ошибок
- Обработка исключений построена на многоуровневой валидации и защитных блоках:
  - Проверка входных аргументов в сервисах и анализаторах (`ArgumentNullException`, `DirectoryNotFoundException`).
  - Возврат стандартных кодов ошибок HTTP: `400 Bad Request`, `401 Unauthorized`, `403 Forbidden`, `404 Not Found`.
  - Централизованная обработка ошибок выполнена по стандарту RFC 9457 (формат ProblemDetails): клиенту возвращается JSON с полями status, title, detail, instance, машиночитаемым code в SCREAMING_SNAKE_CASE и traceId. Словарь errors передаётся исключительно при коде 400 (валидация DTO). Внутренние исключения, стектрейсы и параметры SQL изолированы в серверном ILogger с привязкой к traceId.

- Модульное и интеграционное тестирование реализовано с использованием фреймворка **xUnit**:
  - `SqlAnalyzer.Tests` (44 теста) — проверка правил `SQL001` и `SQL002` на синтаксических деревьях Roslyn.
  - `CSharpAnalyzer.Tests` (17 тестов) — тесты синтаксических правил Roslyn (`LargeClassRuleTests`, `LongMethodRuleTests`).
  - `SecurityAnalyzer.Tests` (56 тестов) — проверка правил `SEC001`–`SEC005` (поиск секретов, опасный CORS, слабая криптография, отключение SSL).
  - `DatabaseAnalyzer.Tests` (64 теста) — тесты разрешения проектов (`EfCoreDatabaseProjectResolverTests`), инспекции моделей (`EfCoreModelInspectorTests`), маппинга (`EfCoreMetadataMapperTests`) и правил проверки схемы (`DatabaseAnalyzerTests`, правила `DB01`–`DB05`).
  - `Backend.Tests` (528 тестов) — компонентные и сервисные тесты контроллеров, DTO, очередей, авторизации и бизнес-логики.
- Автоматический запуск тестов обеспечивается стандартной командой `dotnet test` (всего 709 тестов успешно пройдено). Детальный отчёт: `docs/audits/test-suite-evaluation.md`.

## 15. Клиентские приложения: CLI, Desktop и Telegram-бот
- Клиентские приложения проектируются как потребители публичного REST API системы.
- **Расположение и дистрибуция:** Исходный код клиентов проектируется для размещения в монорепозитории (`src/Cli`, `src/Desktop`, `src/Bot`), а отдельные публичные GitHub-репозитории предназначены для дистрибуции и скачивания готовых сборок.
- **Фактическое состояние в репозитории:** Единственным фактически работающим интерактивным интерфейсом системы в настоящий момент является веб-интерфейс Swagger UI (`/swagger`) в `src/Backend/Api`. Каталоги `src/Cli`, `src/Desktop` и `src/Bot` в монорепозитории являются зарезервированными под будущие проекты клиентов (не входят в решение `CourseProject.slnx` и не содержат файлов исходного кода в текущем репозитории).
- **Ограничения клиентов:**
  - Клиенты не содержат бизнес-логики анализа и не дублируют правила.
  - Клиенты категорически не подключаются к базе данных PostgreSQL напрямую.
  - Все операции (запуск, статус, просмотр нарушений) выполняются через HTTP API с передачей JWT-токена.
- **Статус компонентов:**
  - `src/Cli` (.NET / Spectre.Console) — консольный клиент целевого MVP для автоматизации и сценариев локальной разработки (каталог зарезервирован, проект планируется к интеграции).
  - `src/Desktop` (Tauri + React + TypeScript) — визуальный десктопный интерфейс (каталог зарезервирован, планируемый компонент).
  - `src/Bot` (.NET / Telegram.Bot) — бот для уведомлений и оперативных команд (каталог зарезервирован, планируемый компонент).

## 16. Добавление новых правил и анализаторов
Система открыта для расширения:
- Для создания нового правила анализатора реализуется отдельный класс логики проверки с однозначным идентификатором (`CSHARPxxx`, `DBxxx`, `SQLxxx`), уровнем `Severity`, сообщением и рекомендацией по устранению.
- Новый модуль анализатора регистрируется в DI-контейнере (`builder.Services.AddScoped<IAnalyzer, T>()`) и автоматически подключается к конвейеру `AnalysisService` без изменения кода оркестратора.

## 17. Масштабирование и дальнейшее развитие
Векторы развития системы после стабилизации MVP:
- Оптимизация опроса очереди задач в PostgreSQL (например, использование механизма PostgreSQL LISTEN/NOTIFY или внутрипроцессных сигналов пробуждения фонового обработчика при безусловном сохранении PostgreSQL единственным источником истины и долговечного состояния задач).
- Реализация вебхуков (GitHub Webhooks) для автоматического запуска проверок при каждом push/pull-request.
- Архитектурная изоляция инспектора моделей EF Core и отказоустойчивость конвейера анализа (см. принятый [ADR-001](architecture/database-analyzer-isolation.md) и связанные задачи [`TD-001`](plans/Technical-Debt-Plan.md#td-001) и [`TD-002`](plans/Technical-Debt-Plan.md#td-002)).
- Выделение воркеров анализа в отдельные изолированные контейнеры при росте объема анализируемых репозиториев.
