# Реестр технических аудитов и аналитических материалов CourseProject

В данном реестре зафиксированы все ключевые аналитические материалы, технические регламенты и отчёты аудита архитектуры, базы данных, анализаторов и REST API проекта CourseProject.

---

## 1. Действующие архитектурные спецификации и регламенты

### 1.1. Технический регламент системы
- **Расположение:** `docs/Технический регламент.md`
- **Дата / Версия:** Октябрь 2026 г. (.NET 10 / EF Core 10 / PostgreSQL 17)
- **Охват:** Архитектурный стиль (модульный монолит), границы слоев (`Domain`, `Application`, `Infrastructure`, `Api`), контракт анализаторов `IAnalyzer`, спецификация очереди задач в PostgreSQL, правила именования и организация клиентских приложений (`Cli`, `Desktop`, `Bot`).
- **Ключевой вывод:** Прямой доступ клиентов к БД запрещен; клиенты взаимодействуют исключительно через REST API; внешние брокеры (RabbitMQ, Kafka, Redis) исключены из рамок MVP; очередь задач реализуется на уровне PostgreSQL и `BackgroundService`.

### 1.2. Исполнительное резюме проекта
- **Расположение:** `docs/Исполнительное резюме.md`
- **Дата / Версия:** 28 октября 2026 г.
- **Охват:** Схема базы данных в 3НФ, DDL схемы миграций EF Core, описание сущностей (`Role`, `User`, `Project`, `Commit`, `Analysis`, `AnalysisResult`), доменные перечисления, каталог HTTP-эндпоинтов, модули анализаторов Roslyn и правила развертывания в Docker.

### 1.3. Правила проектирования базы данных
- **Расположение:** `docs/Правила-базы-данных.txt`
- **Охват:** Нормализация (3НФ), ссылочная целостность, первичные ключи (`"Id"` integer GENERATED BY DEFAULT AS IDENTITY), вторичные ключи (`"{Таблица}Id"` integer), строгое именование в `PascalCase` в кавычках.

### 1.4. Архитектурная схема системы
- **Расположение:** `docs/Архитектура проекта.drawio`
- **Охват:** Диаграмма компонентов модульного монолита, взаимодействие API, фонового сервиса, PostgreSQL, GitHub REST API и анализаторов.

## 2. Спецификации и аудиты модулей анализаторов

### 2.1. Спецификация и аудит DatabaseAnalyzer
- **Расположение:** `docs/Исполнительное резюме анализатор БД.md`
- **Охват:** Архитектура статического анализа моделей EF Core, конвейер `IDatabaseProjectResolver` → `IEfCoreModelInspector` → `EfCoreMetadataMapper` → `DatabaseAnalyzer`, правила `DB01`–`DB05`.
- **Статус реализации:** Реализован в `src/Analyzers/Database/`, покрыт 64 unit-тестами в `tests/DatabaseAnalyzer.Tests/`.

### 2.2. Спецификация компонента SqlAnalyzer
- **Расположение:** `docs/Исполнительное резюме анализатор SQL.md`
- **Охват:** Спецификация статического анализа Roslyn для сырых методов EF Core (`FromSqlRaw`, `ExecuteSqlRaw`, `ExecuteSqlRawAsync`), правила `SQL001` (динамическая интерполяция/конкатенация SQL) и `SQL002` (`SELECT *`).
- **Статус реализации:** Реализован в `src/Analyzers/Sql/`, покрыт 44 unit-тестами в `tests/SqlAnalyzer.Tests/`.

### 3.1. Аудит и реализация обработки дубликатов имен проектов
- **Материалы:** `dump_project_conflict_review.md`, коммит `9f7992e` (*fix: handle duplicate project names and secure integration tests*)
- **Охват:** Обработка уникального составного индекса `IX_Projects_OwnerId_Name` в PostgreSQL при конкурентных запросах создания и переименования проектов.

## 4. Комплексные аудиты REST API перед разработкой клиентов

### 4.1. Критический технический аудит REST API
- **Дата проведения:** 30 октября 2026 г.
- **Базовый коммит:** `9f7992e`
- **Охват:** Полный аудит 21 эндпоинта REST API, контрактов DTO, ролевой модели RBAC, IDOR-изоляции, очереди фоновых задач, интеграции с GitHub, сериализации JSON, валидации, логирования и анализа тестового покрытия (214 unit-тестов и 69 проверок в `test_all.ps1`).
- **Сформированный реестр:** Замечания `API-001` – `API-025`.
- **Ключевой вывод:** Текущее API требует предварительной стабилизации перед началом клиентской разработки: необходимо устранить разрывы в навигации (`GET /api/projects`, `GET /api/auth/me`), стандартизировать ошибки через `ProblemDetails`, включить строковую сериализацию перечислений, внедрить валидацию DTO, добавить поле `ErrorMessage` в сущность анализа и защитить учетную запись последнего администратора.

### 4.2. Анализ и предварительный план стабилизации API
- **Дата проведения:** 30 октября 2026 г.
- **Базовый коммит:** `9f7992e`
- **Охват:** Перепроверка замечаний API-001–API-025, пересмотр критичности CORS (снятие статуса блокера для CLI и Telegram-бота; минимальный проверяемый CORS для локальной веб-разработки; перенос точной конфигурации Tauri на этап разработки Desktop-клиента), расследование причин сбоя первой сборки тестов (файловый лок библиотек запущенным локальным процессом `Api.exe`), выбор актуального стандарта ошибок `ProblemDetails` (RFC 9457) с изоляцией технической диагностики, фиксация строковой сериализации перечислений и защиты от Zip-бомб зафиксированными квотами с поточной проверкой.

### 4.3. Единый план технической стабилизации REST API
- **Расположение:** `docs/plans/API-Stabilization-Plan.md`
- **Версия документа:** 1.4.0
- **Статус документа:** Основной руководящий документ по подготовке серверного API к разработке клиентов (готов к исполнению).
- **Охват:**
  - Сводный реестр проблем `API-001`–`API-025` с однозначной классификацией (11 подтверждённых дефектов, 13 рекомендаций по улучшению, 1 отложено, 0 требуют дополнительной проверки);
  - Зафиксированные проектные решения:
    * Строковая сериализация перечислений (`JsonStringEnumConverter`);
    * Единый расширенный контракт ошибок `ProblemDetails` по стандарту RFC 9457 со словарем `errors` исключительно при валидации (400) и изоляцией стектрейсов/SQL в `ILogger`;
    * Четкое разграничение границ этапов строго в пределах Этапов 0–7: Этап 1 (навигация и профиль), Этап 2 (инфраструктура ошибок и enums), Этап 3 (валидация DTO, `ErrorMessage` в `Analysis` и целевая миграция БД), Этап 4 (изолированная защита последнего администратора с защитой от состояния гонки), Этап 5 (GitHub, зафиксированные квоты архивов и конкурентность БД), Этап 6 (CORS, OpenAPI и тестирование), Этап 7 (отложенные плановые улучшения);
    * Логика эндпоинта `GET /api/projects`: для `User` строго свои проекты, для `Admin` — свои по умолчанию или все при `all=true`;
    * Разграничение кодов ошибок GitHub API (400, 404, 502) с проверкой заголовков rate limit (`X-RateLimit-*`);
    * Проверяемый CORS для локальной веб-разработки (доверенные origin: `http://localhost:5173`, `http://localhost:3000`), обязательность явного списка origin при передаче credentials, подтверждение 5 критериев приёмки (preflight OPTIONS, origin, заголовки, отклонение неразрешенных origin, отсутствие регрессий авторизации), указание, что CORS не заменяет авторизацию на сервере, и откладывание настройки Tauri до разработки десктоп-клиента;
    * Окончательно зафиксированные проектные квоты распаковки архивов (архив до 50 МиБ, отдельный файл до 50 МиБ, суммарно до 250 МиБ, не более 10 000 файлов) с поточной проверкой и очисткой в `finally`;
    * Политика схемы БД и миграций EF Core: стабилизация API не является рефакторингом БД, запрет косметических миграций, единственная разрешенная миграция — `AddAnalysisErrorMessage` на Этапе 3, обратная совместимость данных, отсутствие автомиграций при запуске;
    * Базовые параметры пагинации списков данных (page = 1, pageSize = 20, max 100, валидация параметров, детерминированная сортировка на уровне БД);
  - Пошаговые этапы реализации строго в границах Этапов 0–7 с детальными критериями приёмки, обязательными тестами и командами верификации;
  - Сквозная архитектурная диаграмма Mermaid, объединяющая все Этапы 0–7;
  - Закрытие открытых вопросов: все проектные параметры утверждены, сформулированы эксплуатационные предпосылки для начала реализации.
