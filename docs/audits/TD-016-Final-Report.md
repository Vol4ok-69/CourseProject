## 2. Executive Summary

По результатам статического и тестового аудита серверная часть NetScope имеет чётко разделённую архитектуру (слои `Domain`/`Application`/`Infrastructure`/`Api`), а в проверенном объёме сохранены ранее внедрённые механизмы: изоляция Docker Runner (TD-001/ADR-001), изоляция сбоев анализаторов (TD-002), изоляция рабочих каталогов с advisory locks (TD-003), потоковая синхронизация GitHub DAG (TD-006) и очередь PostgreSQL (TD-007). Вместе с тем часть эксплуатационных и нагрузочных сценариев не могла быть проверена динамически в текущем окружении.
- **Сводный реестр (`findings-registry.json`):** `18` консолидированных записей (`0` P0/P1, `9` P2, `4` P3, `5` без приоритета — информационные ограничения, продуктовые вопросы, hardening-рекомендации и `needs_validation`-кандидаты).
- **Главный блокер перед автоматической генерацией клиентских SDK:** несоответствие `swagger.json` актуальному коду и настройкам сериализации/авторизации (`3` консолидированных подтверждённых дефекта P2 в `TD016-F-001..003` и `2` неоднозначности контракта P2 в `TD016-F-004`, `TD016-F-004B`).
- **Ограничение безопасности:** на хосте Windows отсутствует OS-enforced sandbox для динамической эксплуатации, поэтому `12` security-кандидатов Stage 4 и `1` операционный риск (`ZW-005`) сохранены в статусе `needs_validation` в `TD016-F-010` без назначения severity; отсутствие динамического подтверждения не означает отсутствия потенциальных рисков.
- **Тесты:** `1533` тест-кейса (`1530` пройдено, `0` ошибок, `3` `[DockerFact]` пропущены в локальной среде без целевого Docker-образа; см. `TD016-F-011`, `TD016-F-011B`, `TD016-F-011C`, `TD016-F-012`).

## 3. Краткий ответ на 10 вопросов из раздела 7 плана TD-016

1. **В каком фактическом состоянии находится Backend?** Архитектурно целостный в проверенных границах: зависимости слоёв `Domain`/`Application`/`Infrastructure`/`Api` не нарушены, сборка и `1530/1533` тестов проходят успешно, однако динамическая безопасность, нагрузочный профиль БД и контейнерный прогон требуют допроверки.
2. **Есть ли подтверждённые критические или высокоприоритетные дефекты?** **Нет (`0` подтверждённых P0/P1).**
3. **Достаточно ли текущего REST API для CLI?** **Да (готово для начала разработки с ограничениями):** все сценарии покрыты 26 MVC-операциями; перед автоматической генерацией SDK нужно исправить OpenAPI (`TD016-F-001`..`004B`).
4. **Достаточно ли текущего REST API для Desktop?** **Да (готово для начала разработки с ограничениями):** все UI-сценарии покрыты; перед автоматической генерацией TS-клиента нужно исправить OpenAPI и оценить пагинацию проектов (`TD016-F-007`).
5. **Достаточно ли текущего REST API для Telegram-бота в пределах его назначения?** **Частично / требует продуктового решения:** базовые команды чтения/запуска покрыты, но не определены привязка `TelegramUserId`/`ChatId` и доставка уведомлений (`TD016-F-013`).
6. **Какие эндпоинты отсутствуют и почему без них нельзя реализовать конкретные сценарии?** Доказанных недостающих эндпоинтов для CLI/Desktop нет (**0**). Отмена анализа (`AnalysisStatus.Cancelled`) не подтверждена требованиями и оставлена открытым вопросом.
7. **Какие контракты API необходимо уточнить или исправить?** Обновить `swagger.json` (`GitHubSyncResultDto`, `CreateCommitDto.CommitHash`, `409` в `SyncGitHub`), описать `ProblemDetails` (`code`, `traceId`, `errors`, `application/problem+json`), снять глобальный `Bearer` с `register`/`login`, добавить `operationId` и включить `SupportNonNullableReferenceTypes()` (отдельно от оценки `required` в Swashbuckle `10.2.3`).
8. **Какие риски PostgreSQL и безопасности остаются?** Отставание проверенной БД `courseproject-db` на 2 миграции (`TD016-F-008`, назначение БД не подтверждено, без безусловного приоритета), 0 строк в основных таблицах не позволили провести нагрузочный `EXPLAIN ANALYZE` (`TD016-F-009`), а также 12 security-кандидатов и 1 операционный риск `ZW-005` в статусе `needs_validation` в `TD016-F-010` и 8 hardening-рекомендаций в `TD016-F-014`.
9. **Какие критичные сценарии недостаточно покрыты тестами?** HTTP-интеграция мутаций `AdminUsersController` (unit-тесты есть, `TD016-F-011` / `S6-001`), слабые негативные assertions при `403`/`409` (`TD016-F-011B` / `S6-006`) и пропуск 3 `[DockerFact]` тестов в локальной среде (`TD016-F-011C` / `S6-012`).
10. **Можно ли начинать разработку клиентов без существенного риска переделки API?** **Да для CLI и Desktop** при разграничении этапов: ручную или прототипную разработку и согласование сценариев можно начинать уже сейчас, автоматическую генерацию клиентских SDK рекомендуется запускать после актуализации OpenAPI (`TD017-001`), а внедрение `/api/v1/` остаётся рекомендацией по эволюции API, а не жёстким блокером старта. Для **Telegram-бота** предварительно требуется продуктовое решение по привязке аккаунта и уведомлениям (`TD017-010`).

## 9. PostgreSQL и производительность

По результатам инспекции кода и схемы PostgreSQL 17 в Stage 3 применены `AsNoTracking`, детерминированная сортировка `.ThenByDescending(x => x.Id)` (`CommitRepository.cs:48-49`, `AnalysisRepository.cs:109-110`; гипотеза `TD016-S3-002` была опровергнута кодом), `FOR UPDATE SKIP LOCKED` и advisory locks. При этом зафиксированы: отставание проверенной БД `courseproject-db` на 2 миграции (`TD016-F-008`, назначение БД не подтверждено, поэтому запись отнесена к инфраструктурным ограничениям без безусловного приоритета), гипотезы производительности `Include(Results)` и индекса `CommitDate DESC` (`TD016-F-009`), которые не удалось проверить замерами из-за 0 строк в основных таблицах, а также обоснованный статус `DEFERRED` для префиксных индексов `API-023` до нагрузочных замеров.
