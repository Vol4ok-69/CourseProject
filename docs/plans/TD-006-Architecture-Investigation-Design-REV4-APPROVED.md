## 1. Назначение и границы

Документ фиксирует утверждённое архитектурное решение TD-006 (ревизия 4). Настоящее решение полностью реализовано (`IMPLEMENTED`) и верифицировано в кодовой базе проекта для критериев TD-006 (`VERIFIED`).

Цель: сократить повторную загрузку истории коммитов GitHub, не теряя коммиты и родительские ветви, не доверяя произвольным SHA из БД и не объявляя неподтверждённое переписывание истории.

Архитектурное решение сформировано на основе инвентаризации исходного состояния проекта и отчёта Antigravity, согласованных владельцем проекта, с последующей независимой проверкой математической и алгоритмической корректности модели. Исторические сведения раздела 2 отражают состояние кодовой базы до внедрения TD-006. Фактическая реализация задачи TD-006 внесена в кодовую базу строго в соответствии с утверждёнными требованиями данного документа.

## 2. Подтверждённые исходной инвентаризацией факты и ограничения

### 2.1. Пути создания `Commit`

В отчёте инвентаризации указаны следующие пути:

| Путь | Источник SHA | Parent-связи | Доверие |
|---|---|---|---|
| `CommitsController.Create` → `CommitService.CreateAsync` | Пользовательский ввод | Не сохраняются | Запись недоверенная |
| `ProjectsController.SyncGitHub` → `GitHubSyncService.SyncAsync` | GitHub REST API | В текущей реализации отбрасываются | Старые строки недоверенные |
| Тестовые фикстуры | Тестовые данные | Обычно не сохраняются | Не являются доказательством |

Наличие строки `Commit` не доказывает полноту графа. Все существующие записи до внедрения TD-006 должны начинать с `IsVerified = false`, если для них нет отдельного проверяемого доказательства provenance.

### 2.2. Пакетная дедупликация и сохранение

Сохранить пакетное получение существующих SHA (`GetExistingHashesAsync` или эквивалентный пакетный запрос). Не заменять его запросом на каждый коммит.

По инвентаризации `CommitRepository.AddRangeAsync` предназначен для вставки новых строк и при конфликте уникальности может пропускать конфликтующую запись. Поэтому он не подходит для обновления существующего непроверенного коммита.

Архитектура требует отдельного атомарного механизма сохранения, который различает:
- новую строку, реально вставленную текущим запуском;
- существующую непроверенную строку, обновлённую текущим запуском;
- существующую проверенную строку, оставленную без изменений;
- конфликт, при котором строка появилась из параллельного запуска.

Историческое состояние: в исходной реализации `CommitRepository.AddRangeAsync` не поддерживал обновление непроверенных коммитов и требовал создания специализированного атомарного метода сохранения. В текущей кодовой базе реализован метод `CommitRepository.SaveSyncBatchAsync`, который разграничивает вставку новых строк, обновление непроверенных записей и фиксацию checkpoint с обработкой конфликтов уникальности 23505 через savepoint.

## 3. Модель доверия и данных

### 3.1. Поля `Commit`

Предлагаются поля:
- `ParentHashes`: все SHA родителей из GitHub API, включая каждого родителя merge-коммита;
- `IsVerified`: признак доказанной полноты родительской цепочки для данной записи.

Семантика `IsVerified = true`:

1. Список родителей коммита получен из GitHub API и сохранён.
2. Каждый родитель либо сохранён в том же атомарном наборе как проверенный коммит, либо уже существует в БД с `IsVerified = true`.
3. Проверенные узлы образуют замкнутую цепочку до корня или ранее проверенной границы.
4. Запись не была признана проверенной только из-за наличия SHA в БД.

Корневой коммит имеет пустой список родителей. Пустой `ParentHashes` у старой или ручной записи не доказывает, что она является корнем.

### 3.2. Поля checkpoint в `Project`

Предлагаются:
- `LastSyncedCommitHash` – SHA последнего полностью проверенного HEAD;
- `LastSyncedBranch` – имя отслеживаемой ветки;
- `LastSyncedRepositoryId` – устойчивый идентификатор репозитория GitHub;
- `LastSyncedRepositoryHost` – host API/репозитория, чтобы не смешивать GitHub.com и GitHub Enterprise;
- `LastSyncedAt` – время успешной фиксации checkpoint.

Checkpoint действителен только при совпадении идентичности репозитория (host + repository ID) и отслеживаемой ветки. Имя репозитория или URL сами по себе не являются устойчивой идентичностью: репозиторий может быть переименован, перенесён или удалён и создан заново.

Если текущий контракт проекта поддерживает только default branch, `LastSyncedBranch` означает именно default branch. Не смешивать его с произвольной пользовательской веткой. Если выбор ветки будет добавлен позднее, это отдельное расширение контракта.

### 3.3. Начальная миграция

Все существующие записи `Commits` после миграции получают `IsVerified = false`. Нельзя автоматически выставлять `true` старым строкам только потому, что они уже присутствуют в БД.

Все поля checkpoint изначально `NULL`. Старые данные не являются доказанным checkpoint. Первая синхронизация после миграции выполняет проверку графа от текущего HEAD до корней или до уже проверенных границ, созданных новым алгоритмом.

## 4. Формальная модель обхода DAG

### 4.1. Множества

Для одного запуска определяются:

- `V_fetched` – все уникальные SHA, полученные из API в этом запуске;
- `V_expanded` – полученные коммиты, для которых текущий запуск обязан раскрыть родителей. Сюда входят новые и существующие `IsVerified = false` записи;
- `V_verified` – SHA, подтверждённые в БД как `IsVerified = true`;
- `Parents(C)` – полный набор SHA непосредственных родителей коммита `C`;
- `Parents(V_expanded) = ⋃ Parents(C)` для всех `C ∈ V_expanded`.

Множество незамкнутых родителей:

\[
U = Parents(V_{expanded}) \setminus (V_{fetched} \cup V_{verified})
\]

Ключевое отличие от предыдущей редакции: родители уже проверенного узла не раскрываются повторно. Проверенный узел является доверенной границей; его собственная родительская цепочка была доказана в момент его проверки.

### 4.2. Правила обработки страницы

Для каждой страницы:

1. Получить уникальные SHA страницы и пакетно запросить их состояние в БД.
2. Для каждого SHA впервые в текущем запуске:
   - добавить SHA в `V_fetched`;
   - если запись существует и `IsVerified = true`, добавить SHA в `V_verified`; родителей этого узла не добавлять в `Parents(V_expanded)`;
   - если запись отсутствует, добавить коммит в набор новых кандидатов и в `V_expanded`;
   - если запись существует с `IsVerified = false`, добавить её в набор обновления и в `V_expanded`;
   - сохранить все `ParentHashes` для новых/непроверенных записей.
3. Повторное появление SHA, уже содержащегося в `V_fetched`, не должно повторно добавлять кандидата на INSERT/UPDATE.
4. Пакетно проверить родителей из `Parents(V_expanded)`, которые ещё не находятся в `V_fetched` или `V_verified`. Найденные в БД строки с `IsVerified = true` добавить в `V_verified`.
5. Пересчитать `U` по формуле из раздела 4.1.

Порядок коммитов внутри страницы и распределение потомка/родителя по страницам не влияют на корректность: решение принимается по накопленным множествам после обработки всей страницы.

### 4.3. Обязательное условие получения HEAD

Отдельно поддерживается `fixedHeadFetched`. Он становится `true` только после получения из API коммита, SHA которого равен зафиксированному `H_curr`.

Успешное завершение допускается только при одновременном выполнении:

- `fixedHeadFetched == true`;
- `U == ∅`;
- все новые и обновляемые записи имеют полный `ParentHashes`;
- идентичность репозитория и ref не изменилась относительно начала запуска.

Если страницы закончились до получения `H_curr`, результат неполный независимо от значения `U`. Если страницы закончились при `U != ∅`, результат также неполный.

### 4.4. Условия завершения

| Состояние | Условие | Результат |
|---|---|---|
| `CompleteProven` | `fixedHeadFetched` и `U = ∅` | Разрешена атомарная фиксация данных и checkpoint |
| `IncompleteHeadMissing` | Страницы закончились, `H_curr` не получен | Ошибка неполной истории, без записи в БД |
| `IncompleteParents` | Страницы закончились, `U != ∅` | Ошибка неполной истории, без записи в БД |
| `ApiError` | 403/429/5xx/сетевой сбой/ошибка десериализации | Типизированная ошибка, без фиксации результата |
| `Cancelled` | Отмена `CancellationToken` | Отмена, освобождение координатора |

До завершения сетевого обхода изменения в БД не выполняются. Поэтому для `Incomplete*`, `ApiError` и `Cancelled` транзакция сохранения ещё не открыта и откатывать нечего. Транзакция начинается только после доказанного завершения обхода.

## 5. Псевдокод алгоритма

```text
Sync(projectId, token):
    acquire process-local project lock
    projectSnapshot = load project and checkpoint

    repo = GetRepositoryInfo()
    currentIdentity = (repo.ApiHost, repo.RepositoryId)
    currentBranch = repo.DefaultBranch
    H_curr = repo.DefaultBranchHeadSha

    checkpointMatches =
        projectSnapshot.LastSyncedRepositoryHost == currentIdentity.ApiHost
        AND projectSnapshot.LastSyncedRepositoryId == currentIdentity.RepositoryId
        AND projectSnapshot.LastSyncedBranch == currentBranch

    if checkpointMatches
       AND projectSnapshot.LastSyncedCommitHash == H_curr
       AND DB contains H_curr with IsVerified = true:
        return Added=0, Skipped=0; record reason=AlreadyCurrent in diagnostics

    initialize:
        V_fetched = {}
        V_expanded = {}
        V_verified = {}
        ParentsByHash = {}
        NewCandidates = {}
        ExistingUnverifiedUpdates = {}
        fixedHeadFetched = false
        uniqueFetchedCount = 0
        U = {}

    for each page from GetCommitPagesAsync(fixedSha=H_curr):
        token.ThrowIfCancellationRequested()

        query DB statuses for unique page SHA in one batch

        for each commit in page:
            if commit.Sha is already in V_fetched:
                continue

            add commit.Sha to V_fetched
            uniqueFetchedCount += 1

            if commit.Sha == H_curr:
                fixedHeadFetched = true

            if DB row exists and IsVerified == true:
                add commit.Sha to V_verified
                continue

            save all commit.ParentHashes in ParentsByHash
            add commit.Sha to V_expanded

            if DB row does not exist:
                add commit to NewCandidates
            else:
                add update instruction to ExistingUnverifiedUpdates

        query DB in batch for parents( V_expanded )
            where parent not in V_fetched and not already checked
        add only IsVerified=true results to V_verified

        U = Parents(V_expanded) - (V_fetched union V_verified)

        if fixedHeadFetched AND U is empty:
            stop pagination successfully

    if not fixedHeadFetched:
        throw IncompleteHistory(HeadNotFetched)

    if U is not empty:
        throw IncompleteHistory(UnresolvedParents, U)

    classify history using section 6
    persist verified graph and checkpoint atomically using section 7
    return counters based on actual persistence result
```

Важно: проверка `U` выполняется после обработки всей страницы. Нельзя прекращать обработку страницы сразу при встрече первого известного SHA. Пагинация не использует `since` как условие полноты и не имеет произвольного `maxPages`/`maxCommits`.

## 6. Checkpoint и классификация истории

### 6.1. Проверка области сравнения

Сравнивать старый и новый HEAD разрешено только при совпадении:
- `LastSyncedRepositoryHost` и текущего host;
- `LastSyncedRepositoryId` и текущего repository ID;
- `LastSyncedBranch` и текущего отслеживаемого ref.

Если идентичность репозитория изменилась, статус `RepositoryChanged`; старый checkpoint не используется для классификации истории. Если репозиторий тот же, но изменилась отслеживаемая ветка, статус `BranchSwitch`. Ни один из этих статусов сам по себе не означает Force Push.

### 6.2. Доказательство связи со старым HEAD

`H_prev` считается пригодным для сравнения только если он был установлен успешным запуском новой модели и его граф имеет `IsVerified = true`.

После завершения текущего обхода доступны проверенные граничные узлы текущей истории. Для каждого такого узла `A` его проверенная ancestry-цепочка может быть исследована по сохранённым `ParentHashes`.

Классификация:

1. `InitialSync`: checkpoint отсутствует или не имеет доказанной provenance.
2. `RepositoryChanged`: изменился host или repository ID. Старый HEAD не сравнивается с новым.
3. `BranchSwitch`: репозиторий тот же, но имя отслеживаемой ветки изменилось.
4. `FastForward`: `H_prev` получен в текущем обходе либо доказано, что `H_prev` является предком хотя бы одной достигнутой текущей доверенной границы.
5. `NonFastForwardHistory`: `H_prev` не является предком текущего HEAD, но пересечение полных ancestry-графов старого и нового HEAD содержит хотя бы один общий проверенный коммит.
6. `IndependentHistory`: оба графа полностью проверены, их идентичность репозитория и ref совпадает, но общего предка нет.
7. `InsufficientEvidence`: старый checkpoint или его ancestry не имеет доказанной полноты. В этом случае нельзя объявлять ни `FastForward`, ни `NonFastForwardHistory`, ни `IndependentHistory`.

Термин `Force Push` не используется как установленный факт. `NonFastForwardHistory` означает доказанное расхождение графа, но не доказывает, каким именно действием изменён ref.

Старые коммиты, parent-связи и `Analyses` никогда не удаляются.

## 7. Атомарное сохранение и конкурентность

### 7.1. Сохранение

После успешного обхода открывается короткая транзакция БД:

1. Заблокировать строку `Project` на время транзакции сохранения (`SELECT ... FOR UPDATE` либо эквивалентный механизм).
2. Повторно прочитать checkpoint и проверить, что он не изменился с момента начала сетевого обхода. Если изменился, отменить фиксацию как устаревший запуск (`SyncCheckpointChanged`); не перезаписывать более новый checkpoint.
3. Вставить новые проверенные коммиты.
4. Обновить существующие `IsVerified = false` записи: записать `ParentHashes`, установить `IsVerified = true`.
5. Не изменять существующие `IsVerified = true` записи.
6. Обновить `LastSyncedCommitHash`, `LastSyncedBranch`, repository host/ID и `LastSyncedAt`.
7. Зафиксировать транзакцию.

Транзакция и блокировка строки Project не должны удерживаться во время HTTP-запросов к GitHub. Это предотвращает долгую занятость соединений Npgsql.

### 7.2. Межпроцессные гонки при вставке

Уникальный индекс `IX_Commits_ProjectId_CommitHash` остаётся последней защитой от повторных строк, но сам по себе не защищает checkpoint и не предотвращает лишние HTTP-запросы.

Механизм пакетного сохранения обязан вернуть фактические множества SHA:
- `InsertedHashes`;
- `UpdatedHashes`;
- `UnchangedHashes`.

Если строка появилась после первоначальной проверки, сохранение должно перечитать её состояние в транзакции: непроверенная строка обновляется, проверенная остаётся без изменений. Конфликт не должен приводить к потере `ParentHashes` или ложному увеличению `Added`.

Для `Project` применяется короткая блокировка строки и проверка версии checkpoint, поэтому два экземпляра API не смогут молча перезаписать checkpoint результатом устаревшего запуска. При конфликте один запуск получает `SyncCheckpointChanged` и может быть повторён отдельным запросом.

### 7.3. Process-local координатор

В пределах одного процесса используется Singleton-координатор на основе `ConcurrentDictionary<ProjectId, SemaphoreSlim>`. Второй параллельный запрос того же проекта получает `409 Conflict` (`SyncAlreadyInProgress`) без вызова GitHub API.

Этот механизм не является распределённой блокировкой. Межпроцессная целостность обеспечивается уникальным индексом, короткой блокировкой Project при фиксации и проверкой checkpoint. Лишние внешние запросы между репликами при этом возможны и явно допускаются текущим контрактом.

## 8. Контракт `Added` и `Skipped`

Контракт для успешного завершённого запуска:

- `Added` – количество строк, фактически вставленных текущим запуском;
- `Skipped` – количество уникальных SHA, фактически полученных от GitHub, которые не были вставлены текущим запуском. Сюда входят уже существующие записи, обновлённые непроверенные записи и строки, вставленные параллельным запуском;
- повторные появления одного SHA в ответах API не увеличивают `uniqueFetchedCount` и не учитываются повторно;
- быстрый выход `AlreadyCurrent` возвращает `Added = 0`, `Skipped = 0`, поскольку коммиты в этом запуске не загружались и не просматривались;
- ошибки и неполные результаты не возвращают успешные счётчики как завершённую синхронизацию.

Формула после успешной фиксации:

`Added = |InsertedHashes|`

`Skipped = uniqueFetchedCount - Added`

`UpdatedHashes` входят в `Skipped`, так как строка уже существовала до вставки текущим запуском. Если публичный DTO не позволяет передать `AlreadyCurrent` или причину ошибки, статус передаётся существующим механизмом ошибок/диагностики; расширение DTO требует отдельного согласования.

## 9. Пагинация GitHub API и rate limits

1. На один запуск фиксируется `H_curr`; все страницы запрашиваются относительно этого SHA через параметр `sha`.
2. `Link: rel="next"` обрабатывается с проверкой scheme, host и допустимого path. Если ссылка не содержит обязательный `sha`, он сохраняется при построении следующего запроса. Фактическое поведение GitHub и реализация URL validation должны быть проверены интеграционными тестами.
3. Фиксированный SHA не объявляется snapshot isolation. Если API не может продолжить выдачу фиксированной истории, запуск завершается ошибкой без фиксации checkpoint.
4. Не полагаться на строгий топологический порядок коммитов.
5. `since` не используется как доказательство полноты или условие остановки. Документ не делает неподтверждённого утверждения о точном поле даты, по которому GitHub применяет этот фильтр.
6. Не вводить произвольные пределы страниц/коммитов.
7. Сохранять последовательную загрузку страниц одного запуска. Использовать имеющийся `GitHubRateLimitParser`, `Retry-After` и доступные rate-limit заголовки. Не утверждать наличие фиксированного порога secondary rate limit.
8. Ошибки 403/429/5xx, timeout, 404/422 при потере доступности фиксированного SHA и ошибки десериализации не должны приводить к успешному checkpoint.

## 10. Предлагаемые изменения модели и файлов

Список является архитектурным направлением, а не утверждением о точных текущих сигнатурах. Перед реализацией сверить фактическую структуру проекта.

| Область | Изменение |

| GitHub response DTO | Десериализация всех элементов `parents` |

## 11. Обязательная тестовая матрица

| ID | Сценарий | Ожидаемый результат |
|---|---|---|
| TR-01 | HEAD и checkpoint совпадают, репозиторий/ref совпадают | `AlreadyCurrent`, `Added=0`, `Skipped=0`, API-страницы не запрашиваются |
| TR-02 | Ручная запись без подтверждённых родителей | Не является доверенной границей; родители загружаются и запись обновляется |
| TR-03 | Линейная цепочка новых коммитов | Все новые SHA и родители сохранены; остановка на проверенной границе |
| TR-04 | Merge с двумя родителями, один уже проверен, второй неизвестен | Вторая ветвь полностью исследуется |
| TR-05 | Родитель на предыдущей странице | Родитель учитывается в `V_fetched`; нет ложной незамкнутости |
| TR-06 | Родитель раньше потомка на одной странице | Результат не зависит от порядка JSON |
| TR-07 | Родитель позже потомка на одной странице | Результат не зависит от порядка JSON |
| TR-08 | API исчерпал страницы при `U != ∅` | `IncompleteParents`, никаких изменений в БД |
| TR-09 | Страницы закончились, но `H_curr` не получен при `U = ∅` | `IncompleteHeadMissing`, checkpoint не меняется |
| TR-10 | Повтор одного SHA в одной/разных страницах | SHA обрабатывается один раз, счётчики не завышаются |
| TR-11 | Повторная синхронизация с большим количеством старых коммитов | Остановка на проверенной границе без повторного раскрытия родителей проверенного узла |
| TR-12 | Изменение HEAD во время пагинации | Все запросы используют `fixedSha`; новые коммиты вне фиксированного HEAD не попадают в запуск |
| TR-13 | 5+ страниц | Нет искусственного лимита; все страницы до доказанного условия |
| TR-14 | 429/timeout/API error на промежуточной странице | Нет checkpoint и частичной успешной фиксации |
| TR-15 | Отмена во время ожидания/HTTP | Координатор освобождён; checkpoint не изменён |
| TR-16 | Два вызова одного проекта в одном процессе | Второй получает 409 до вызова GitHub API |
| TR-17 | Два экземпляра API вставляют одинаковый SHA | Одна строка; `Added` отражает фактическую вставку; checkpoint не перезаписывается устаревшим запуском |
| TR-18 | Существующая непроверенная запись | UPDATE `ParentHashes` + `IsVerified=true`, без повторного INSERT |
| TR-19 | Смена default branch того же репозитория | `BranchSwitch`, не `NonFastForwardHistory` |
| TR-20 | Изменение repository ID или host | `RepositoryChanged`, старый checkpoint не сравнивается с новым графом |
| TR-21 | Старый HEAD является предком текущей доверенной границы | `FastForward`, даже если старый HEAD не пришёл отдельным элементом API |
| TR-22 | Старый HEAD отсечён, но ancestry имеет общий проверенный узел | `NonFastForwardHistory`; не утверждать, что точно выполнен `git push --force` |
| TR-23 | Полные проверенные графы не имеют общего предка | `IndependentHistory` |
| TR-24 | Старый checkpoint/ancestry не доказан | `InsufficientEvidence`; не выдавать force-push/independent вывод |
| TR-25 | Родитель проверенного узла не загружается повторно | Проверенный узел корректно завершает ветвь обхода |

Тесты должны проверять точный набор SHA, все `ParentHashes`, `IsVerified`, checkpoint, фактические результаты INSERT/UPDATE, число HTTP-запросов и итоговый статус.

## 12. Критерии приёмки реализации

TD-006 может получить `VERIFIED` только если:

1. Все новые и обновлённые коммиты имеют полный список родителей.
2. `IsVerified` означает доказанную замкнутость ancestry, а не наличие SHA.
3. Успешный запуск обязательно получил `H_curr`.
4. Успешный запуск завершил `U = ∅`.
5. Проверенные узлы служат доверенными границами без повторного раскрытия их родителей.
6. Старые непроверенные строки обновляются, а не пропускаются при уникальном конфликте.
7. Счётчики отражают фактические INSERT и уникальные полученные SHA.
8. Checkpoint связан с host, repository ID и branch.
9. Устаревший параллельный запуск не может перезаписать более новый checkpoint.
10. Ошибки/отмена/неполная история не меняют checkpoint.
11. Нет `since` как гарантии, произвольного лимита страниц и предположения о топологическом порядке.
12. Не удаляются коммиты, связи и анализы.
13. Классификация истории использует доказанную ancestry, а не только факт отсутствия `H_prev` в текущей выборке.
14. Применимые TR-01–TR-25 реализованы и проходят.
15. Независимый аудит реализации не содержит блокирующих замечаний.

## 13. Риски и принятые ограничения

| Риск/ограничение | Контроль |
|---|---|
| Неполная старая история | Все старые записи `IsVerified=false`; первый запуск строит provenance |
| Изменение удалённой истории во время обхода | Fixed SHA, ошибки не фиксируют checkpoint |
| Независимая история | Отдельный статус, без утверждения о Force Push |
| Несколько API-реплик | Уникальный индекс + короткая блокировка Project + проверка версии checkpoint |
| Лишние HTTP-запросы между репликами | Допускаются; process-local lock не является distributed lock |
| Изменение контракта `Added`/`Skipped` | Контрактные тесты всех потребителей |
| Rate limits | Существующий parser, sequential pagination, Retry-After |

### Поддерживаемые GitHub API host

Текущая реализация TD-006 использует GitHub.com API с базовым адресом
`https://api.github.com/`.

Поддержка GitHub Enterprise и произвольных GitHub API host в рамках
текущей реализации не заявляется.

Поле `LastSyncedRepositoryHost` входит в идентичность checkpoint и
используется для предотвращения смешивания истории разных источников.
Само наличие этого поля не означает, что приложение умеет подключаться
к произвольному GitHub API host.
