## 1. Назначение документа

Документ фиксирует исходную проблему TD-006, утверждённые архитектурные решения ревизии 4, ограничения реализации, требования к инкрементальной синхронизации GitHub, тестовую матрицу и результаты проверки.

Статусы `APPROVED`, `IMPLEMENTED` и `VERIFIED` имеют разные значения:

- `APPROVED` – архитектурное решение утверждено.
- `IMPLEMENTED` – изменения внесены в кодовую базу.
- `VERIFIED` – обязательные критерии приёмки подтверждены фактическими проверками и независимым аудитом.

Наличие реализации само по себе не является доказательством успешной приёмки.

Главное требование TD-006: сократить повторную загрузку истории коммитов GitHub, не допуская незаметной потери коммитов, повреждения существующих связей и ложных выводов о переписывании истории.

## 2. Исходное состояние

### 2.1. Проблема

Повторная синхронизация может загружать значительную часть или всю историю коммитов репозитория. Простая остановка на первом уже известном SHA не является универсально безопасной.

Git хранит историю как ориентированный граф. У коммита может быть один родитель, несколько родителей или не быть родителей. История может включать merge-коммиты, долгоживущие боковые ветви, cherry-pick, squash merge и переписывание истории. Поэтому алгоритм не может опираться только на наличие SHA в БД или на хронологическое сравнение дат.

### 2.2. Уже существующая пакетная дедупликация

В `Technical-Debt-Plan.md` указано, что `GetExistingHashesAsync` решает проблему N+1: SHA существующих коммитов выбираются пакетно. TD-006 не должна повторно решать эту проблему поштучными запросами. Пакетная проверка должна сохраниться; уникальное ограничение БД остаётся последней защитой от дублей, но не заменяет пакетную дедупликацию.

### 2.3. Ручное создание коммитов

В аудите TD-006 ревизии 2 обнаружен публичный путь ручного создания коммита: `CommitsController.Create` и `CommitService.CreateAsync`. Следовательно, SHA может присутствовать в БД, хотя коммит не был получен полной синхронизацией GitHub, а его родители и предки могут отсутствовать.

Перед реализацией необходимо повторно проверить актуальный код этих методов и все остальные пути записи в `Commits`. Указанные методы являются отправной точкой аудита, а не заменой проверки репозитория.

### 2.4. Требования исходного реестра

Раздел TD-006 в `Technical-Debt-Plan.md` устанавливает следующие ограничения:

- свежие коммиты запрашиваются от HEAD;
- ранняя остановка должна быть безопасной для соответствующего класса истории;
- нелинейная история не должна обрабатываться предположением о строгой хронологии;
- `since` не является самостоятельной гарантией полноты;
- произвольный лимит страниц, например `maxPages = 10`, запрещён;
- существующие SHA не должны повторно вставляться и вызывать `23505`;
- расхождение удалённой истории не должно приводить к удалению исторических данных.

## 3. Термины

**Commit SHA** – идентификатор Git-коммита. Используется для дедупликации, но сам по себе не доказывает полноту истории.

**Parent** – родительский коммит из массива `commit.parents` ответа GitHub. У merge-коммита несколько родителей, и учитывать нужно каждого.

**Граф истории** – ориентированный граф, в котором вершины являются коммитами, а рёбра ведут от коммита к его родителям.

**Известный коммит** – SHA которого уже существует в БД. Это означает только наличие записи, а не полноту родительской цепочки.

**Проверенная история** – история, для которой имеются достаточные сведения, подтверждающие полноту сохранённого графа до установленной границы.

**Доверенная граница** – коммит или множество коммитов, достижение которых при обходе всех родительских ветвей позволяет безопасно прекратить получение предков.

**Checkpoint** – сохранённая точка последней успешной синхронизации. Обычный SHA checkpoint не доказывает, что все его предки сохранены.

**Независимая история** – текущий граф, для которого в доступных подтверждённых данных не установлен общий предок с прежним графом.

**Переписывание истории** – ситуация, когда прежняя подтверждённая вершина отслеживаемой ветки перестаёт быть предком текущей вершины. Для такого вывода нужно сравнивать подтверждённые вершины одной и той же области синхронизации.

## 4. Цели, нецели и инварианты

### 4.1. Цели

1. Сократить количество запросов GitHub API при повторной синхронизации.
2. Сохранять все новые коммиты в выбранной области истории.
3. Корректно обрабатывать merge-коммиты и все родительские связи.
4. Не использовать даты как единственное доказательство полноты.
5. Не считать произвольный SHA из БД безопасной точкой остановки.
6. Не допускать повторной вставки существующих SHA.
7. Не повреждать старые коммиты, связи и анализы.
8. Не вводить искусственный предел страниц.
9. Определить предсказуемое поведение конкурентных запросов.
10. Подтвердить корректность автоматическими тестами.

### 4.2. Нецели

В TD-006 не входят удаление коммитов и анализов, каскадное удаление исторических данных, перестройка всей модели Git без обоснования, изменение публичных DTO без необходимости и согласования, введение `maxPages`, использование `since` как единственного механизма инкрементальности, объявление force push только на основании отсутствия общего предка и миграция БД до доказательства её необходимости.

### 4.3. Обязательные инварианты

- **I-01. Сохранность.** Существующие коммиты и анализы не удаляются.
- **I-02. Дедупликация.** Один SHA не приводит к повторной вставке. Проверка остаётся пакетной.
- **I-03. Полнота.** Ранняя остановка допустима только при достижении доказанной доверенной границы. Простого наличия SHA в БД недостаточно.
- **I-04. Все родители.** У merge-коммита учитываются все `parents`, а не только первый.
- **I-05. Даты не являются гарантией.** `author.date` и `committer.date` не заменяют обход родительского графа.
- **I-06. Нет искусственного лимита.** Обход завершается по доказанному условию или по исчерпанию страниц API.
- **I-07. Фиксированная вершина.** Один запуск использует один зафиксированный HEAD SHA.
- **I-08. Нет ложного force push.** Отсутствие общего предка само по себе не доказывает force push.
- **I-09. Конкурентная корректность.** Параллельные запуски не повреждают данные; уникальный индекс остаётся последней защитой.
- **I-10. Честная диагностика.** `Added`, `Skipped` и причина остановки отражают фактически обработанные данные.

## 5. Зафиксированные решения

В документе разделены обязательные ограничения и решения, которые ещё требуют выбора конкретной реализации.

### D-01. Сохранить пакетную дедупликацию

**Статус:** `ACCEPTED AS CONSTRAINT`.

`GetExistingHashesAsync` должен использоваться для пакетного получения уже сохранённых SHA. Поштучные запросы для каждого коммита не допускаются. Уникальный индекс БД остаётся последней защитой от дублей.

### D-02. Известный SHA не является доверенной границей

**Статус:** ограничение принято; модель хранения `OPEN`.

Наличие записи в `Commits` не доказывает, что коммит получен полной синхронизацией GitHub, что все родители и предки сохранены, что он был частью подтверждённого графа или что запись не была создана вручную.

Рассматриваются три варианта:

**Вариант A – без миграции, с проверкой графа.** Использовать существующие parent-связи и/или повторные запросы GitHub API. Требуется доказать, что текущая модель данных хранит достаточно сведений. Если родители не сохраняются или исторически отсутствуют, одной БД недостаточно.

**Вариант B – явная provenance-модель.** Хранить происхождение и подтверждённость коммитов/графа: каким запуском подтверждён SHA, какая вершина HEAD была зафиксирована, какие связи проверены и где находится граница полноты. Вероятно потребуется миграция, но конкретные таблицы и поля нельзя утверждать до изучения текущей схемы.

**Вариант C – checkpoint с доказательством замыкания.** Хранить не только последний SHA, но и подтверждённую вершину/состояние завершённого обхода. Одно поле `Project.LastSyncedCommitHash` само по себе недостаточно.

**Предварительное направление:** не вводить `LastSyncedCommitHash` как единственное средство доверия. Сначала сравнить A–C на сценариях неполной исторической БД и ручного создания коммитов.

### D-03. Родительский граф – основа доказательства полноты

**Статус:** `ACCEPTED AS REQUIREMENT`.

Алгоритм должен учитывать все `commit.parents`. Требуемая семантика:

1. Зафиксировать SHA HEAD.
2. Получить коммиты от этой вершины.
3. Учесть все родительские SHA каждого коммита.
4. Определить, какие вершины существуют в БД и какие из них являются доверенными границами.
5. Продолжить обход каждой непроверенной ветви до доверенной границы или исчерпания истории.
6. Сохранить новые коммиты пакетно.
7. Завершить запуск только после выполнения формального условия полноты.

Конкретный механизм – REST pagination, отдельное получение коммитов или локальный Git-граф – должен быть выбран после сравнения стоимости API, сложности и доказуемости.

### D-04. `since` не гарантирует полноту

**Статус:** `ACCEPTED AS CONSTRAINT`.

`since` может быть вспомогательным фильтром после проверки фактической семантики. Документация GitHub описывает фильтр по времени обновления результата, но не даёт основания без эксперимента утверждать, что он работает строго по `author.date` или `committer.date`.

Документация должна разделять публично документированное поведение, наблюдение конкретного эксперимента и проектную эвристику.

### D-05. Фиксированный SHA на один запуск

**Статус:** требование принято; стабильность пагинации `OPEN`.

Для одного запуска фиксируется HEAD SHA, и запросы должны относиться к этой вершине, если endpoint поддерживает параметр `sha`.

Нужно отдельно проверить сохранение `sha` в `Link` следующей страницы, сохранение `per_page` и других параметров, реализацию `ValidateNextPageUrl` (scheme, host, path и query), а также поведение при перемещении refs и force push во время обхода.

Фиксированный SHA не следует называть полной snapshot isolation без доказательства.

### D-06. Различать переписывание и независимую историю

**Статус:** `ACCEPTED AS CONSTRAINT`.

Разделять три результата:

1. Новые достижимые коммиты, сохраняющие подтверждённую связь с прежней историей.
2. Переписывание/расхождение ранее отслеживаемой ветки, когда прежняя подтверждённая вершина перестала быть предком текущей вершины той же ветки.
3. Независимая история, для которой общий предок не установлен.

Третий результат не доказывает `git push --force`: возможны orphan branch, смена репозитория/ветки, неполная старая история, ручные записи или недостаток данных. Для независимой истории допустимо предупреждение «общий предок не установлен», но не утверждение «выполнен force push».

### D-07. Произвольный `maxPages` запрещён

**Статус:** `ACCEPTED`.

Пагинация завершается только при доказанном достижении доверенных границ для всех исследуемых ветвей, исчерпании страниц API или корректном завершении с ошибкой/неполным результатом. Нельзя объявлять полную синхронизацию, если полнота не доказана.

### D-08. Не удалять исторические данные

**Статус:** `ACCEPTED`.

Старые коммиты, анализы и связи сохраняются. Изменение удалённой истории отражается диагностикой, а не физическим удалением результатов анализа.

### D-09. Конкурентная синхронизация

**Статус:** требование принято; механизм `OPEN`.

Рассматриваемое направление – `SemaphoreSlim` на проект в общем process-local координаторе. Это работает только внутри одного процесса и при общем жизненном цикле координатора.

Нужно проверить DI lifetime, блокировку по ProjectId, освобождение в `finally`, поведение при исключении и отмене, ожидание второго запроса либо явный ответ «синхронизация уже выполняется», безопасную очистку неиспользуемых семафоров.

Уникальный индекс предотвращает дубли строк, но не дубли HTTP-запросов. Process-local lock не координирует несколько реплик API. Для нескольких процессов нужна отдельная распределённая координация или явное ограничение гарантии.

Длительную транзакцию БД вокруг HTTP-запросов открывать не следует. Session-level advisory lock допустим к рассмотрению только после анализа физического соединения Npgsql и connection pool.

### D-10. Семантика `Added` и `Skipped`

**Статус:** `PROPOSED CONTRACT – проверить клиентов`.

Предлагается:

- `Added` – количество новых коммитов, успешно добавленных в текущем запуске;
- `Skipped` – количество фактически просмотренных коммитов, не добавленных из-за уже существующего SHA или дубликата в API-ответе;
- непросмотренные страницы не включаются в `Skipped`;
- ранняя остановка не должна искусственно приравнивать `Skipped` к числу всех коммитов репозитория.

Например, если просмотрено 100 уже известных коммитов и достигнута доверенная граница, `Skipped` может быть 100. Нельзя считать все коммиты репозитория, которые не были загружены, пропущенными.

Нужно проверить все потребители результата: контроллеры, клиенты, тесты, документацию и UI. Неизменность DTO не означает неизменность семантики.

### D-11. Rate limits

**Статус:** `ACCEPTED AS CONSTRAINT`.

Нельзя утверждать, что GitHub гарантированно возвращает 429 после 100 последовательных запросов. Документация описывает несколько secondary rate limits, включая предел одновременных запросов и лимит REST API points в минуту; часть ограничений может меняться и не раскрывается полностью.

Необходимо избегать ненужной параллельности страниц одного графа, использовать существующую обработку rate limit, учитывать `Retry-After` и доступные заголовки, не вводить выдуманный порог запросов и не логировать секреты.

Реализация решения внесена в кодовую базу проекта (`IMPLEMENTED`). Статус приёмки (`VERIFIED` / `NOT VERIFIED`) определяется результатами автоматизированного тестирования обязательных сценариев TR-01–TR-25 и критериев приёмки.

### Этап 0. Инвентаризация фактического кода

**Цель:** получить достоверную картину до изменения исходников.

Работы:

1. Проверить Git status; не выполнять destructive Git-команды.
2. Изучить `GitHubService.cs` и `GitHubSyncService.cs`.
3. Найти интерфейсы и DTO синхронизации.
4. Изучить сущность `Commit`, конфигурацию EF Core, таблицу и индексы.
5. Установить, хранятся ли parent SHA и в какой форме.
6. Изучить `GetExistingHashesAsync`, пакетную вставку и обработку `23505`.
7. Найти все пути создания `Commit`: GitHub sync, ручной API, импорт, фоновые процессы и тестовые фабрики.
8. Проверить DI lifetime сервиса и его зависимостей.
9. Найти все места вызова синхронизации и все потребители `Added`/`Skipped`.
10. Изучить существующие тесты и HTTP-фикстуры GitHub.
11. Сверить фактическое состояние с `Technical-Debt-Plan.md` и DEF-009/NEW-001.

**Артефакт:** таблица «код – фактическое поведение – требование – разрыв».

**Критерий выхода:** установлены реальные типы, методы, пути записи, DI lifetime и потребители контракта. Не допускаются предположения о несуществующих полях и методах.

### Этап 1. Модель доверия и полноты

**Цель:** решить проблему «известный SHA не означает полную историю».

Работы:

1. Описать доступные сведения о коммите: SHA, все родители, источник получения и реально существующие метаданные.
2. Выделить непроверенные исторические записи.
3. Смоделировать ручной коммит без родителей.
4. Смоделировать merge с двумя родителями.
5. Смоделировать известный merge-коммит с отсутствующим родителем.
6. Сравнить варианты A–C из D-02.
7. Выбрать минимальную модель, которая доказывает достижение доверенной границы.
8. Определить поведение для старых данных без provenance.
9. Решить, может ли старая история быть доверенной или обход должен идти до корня/подтверждённого checkpoint.
10. Зафиксировать необходимость миграции, если она действительно нужна.

**Артефакт:** спецификация доверия к коммитам и checkpoint.

**Критерий выхода:** система отличает просто существующий SHA от проверенного узла и доверенной границы. Ручная неполная запись не может остановить синхронизацию.

### Этап 2. Формальный алгоритм обхода графа

**Цель:** описать проверяемое условие полноты.

Работы:

1. Зафиксировать HEAD SHA.
2. Определить источник коммитов и получения `parents`.
3. Описать структуру обхода: очередь/стек непроверенных SHA, посещённые SHA и доверенные границы.
4. Обработать всех родителей merge-коммита.
5. Определить, когда известный узел является доверенной границей.
6. Продолжать обход всех непроверенных ветвей.
7. Определить обработку повторных SHA.
8. Определить поведение при неизвестном parent, API error, отмене и rate limit.
9. Доказать, что известность одного родителя не приводит к пропуску второго.
10. Оценить число API-вызовов для разных стратегий.
11. Не использовать `since` как единственное условие остановки.

**Артефакт:** псевдокод, инварианты, таблица состояний и оценка API-запросов.

**Критерий выхода:** условие остановки формально проверяемо и покрывает все родительские ветви.

### Этап 3. Пагинация и фиксированный HEAD

**Цель:** не смешивать разные графы и не терять страницы.

Работы:

1. Проверить endpoint `GET /repos/{owner}/{repo}/commits`.
2. Фиксировать `fixedSha` на запуск.
3. Проверить сохранение `sha` в `Link` следующей страницы.
4. Проверить `ValidateNextPageUrl`: scheme, host, path и query.
5. Проверить сохранение `per_page` и остальных параметров.
6. Проверить перемещение ветки между страницами.
7. Проверить force push во время пагинации.
8. Зафиксировать, что доказано: фиксированный корень, стабильность страниц или только best-effort.
9. Не заявлять snapshot isolation без доказательства.

**Артефакт:** спецификация пагинации и интеграционные тесты.

**Критерий выхода:** один запуск использует один HEAD; ошибки и неполнота не маскируются под полную синхронизацию.

### Этап 4. Переписывание истории и независимые графы

**Цель:** не выдавать ложный force push.

Работы:

1. Определить отслеживаемую ветку/ref.
2. Установить способ хранения прежней подтверждённой вершины.
3. Подтвердить происхождение старой вершины.
4. Проверить, является ли она предком новой вершины.
5. При отсутствии такой связи проверить общий предок.
6. Разделить переписывание ветки и независимую историю.
7. Не удалять старые коммиты и анализы.
8. Определить диагностические сообщения.
9. Проверить повторную синхронизацию после каждого вида расхождения.

**Артефакт:** таблица классификации истории.

**Критерий выхода:** независимая история не называется доказанным force push; исторические данные сохраняются.

### Этап 5. Конкурентное выполнение

**Цель:** определить область действия блокировки.

Работы:

1. Установить DI lifetime `GitHubSyncService`.
2. Определить источники вызовов: HTTP, фоновые задачи или оба.
3. Установить deployment-модель: один процесс или несколько реплик.
4. Для одного процесса спроектировать общий координатор и блокировку по ProjectId.
5. Выбрать поведение второго запроса: ожидание или явный ответ.
6. Проверить освобождение при исключении и отмене.
7. Определить безопасную очистку блокировок.
8. Сохранить уникальный индекс БД как защиту от дублей.
9. При необходимости сравнить распределённые блокировки.
10. Не удерживать транзакцию БД во время HTTP.
11. При рассмотрении advisory lock проверить физическое соединение Npgsql и connection pool.

**Артефакт:** спецификация конкурентности.

**Критерий выхода:** тесты подтверждают поведение; документация явно обозначает process-local или distributed гарантию.

### Этап 6. Контракт результата и диагностика

**Цель:** однозначно сообщать результат синхронизации.

Работы:

3. Проверить UI и клиентов.
4. Определить поведение при частичной загрузке.

6. Если DTO не выражает нужное состояние, подготовить отдельное предложение об изменении API.
7. Логировать проект, fixed HEAD, обработанные страницы/коммиты, Added/Skipped, доверенные границы и причину остановки.
8. Не логировать секреты.
9. Не включать непросмотренные коммиты в `Skipped`.

**Артефакт:** контракт результата и диагностических событий.

**Критерий выхода:** клиент отличает полную синхронизацию от частичной/ошибочной.

## 8. Критерии приёмки TD-006

Статус `VERIFIED` допускается только при одновременном выполнении условий:

1. Повторная синхронизация не загружает всю историю без необходимости.
2. Остановка не происходит на произвольном известном SHA.
3. Полнота подтверждается по всем родителям и доверенным границам.
4. Ручные/непроверенные записи не становятся checkpoint автоматически.
5. Merge-графы и боковые ветви не теряют предков.
6. `since` не является единственным доказательством полноты.
7. Для запуска фиксируется HEAD.
8. Нет искусственного лимита страниц.
9. Отсутствие общего предка не объявляется доказанным force push.
10. Старые коммиты и анализы сохраняются.
11. Повторные SHA не создают дубли.
12. Конкурентное поведение соответствует документированной границе гарантии.
13. `Added` и `Skipped` имеют однозначную проверенную семантику.
14. Частичная загрузка не маскируется под полную.
15. Все обязательные сценарии утверждённой матрицы приёмки TR-01–TR-25 проверены и подтверждены тестами.
16. Независимый аудит не содержит блокирующих замечаний.

## 9. Запрещённые упрощения

Без нового архитектурного обоснования запрещены:

- остановка на первом SHA, просто найденном в БД;
- использование одного `LastSyncedCommitHash` как доказательства полноты;
- использование только `since` или дат;
- остановка после N известных SHA без доказательства для всех ветвей;
- проверка только первого родителя merge-коммита;
- смешивание страниц разных HEAD;
- заявление, что fixed SHA автоматически обеспечивает snapshot isolation;
- `maxPages`, `maxCommits` и другие произвольные лимиты, приводящие к тихой неполноте;
- удаление старых коммитов или анализов;
- классификация любой независимой истории как force push;
- заявление, что process-local `SemaphoreSlim` координирует несколько процессов;
- заявление, что уникальный индекс предотвращает лишние HTTP-запросы;
- утверждение о гарантированном 429 после 100 последовательных запросов;
- замена фактических тестов описанием предполагаемого поведения.

## 10. Риски и контроль

| Риск | Последствие | Контроль |
|---|---|---|
| Неполная старая история | Пропуск предков | Provenance/проверка замыкания |
| Ручные записи Commit | Ложное доверие к SHA | Разделить существование и подтверждённость |
| Merge с несколькими родителями | Потеря боковой ветви | Обход всех `parents` |
| Изменение HEAD во время пагинации | Смешанный набор страниц | Fixed SHA и интеграционные тесты |
| Недокументированный порядок API | Неверное предположение о порядке | Не строить гарантию на неподтверждённой сортировке |
| Независимая история | Ложный force push | Отдельная классификация |
| Несколько API-процессов | Параллельные синхронизации | Распределённая координация или ограничение гарантии |
| Частичный сбой API | Ложный статус полной синхронизации | Разделить полный/частичный/ошибочный результат |
| Изменение Skipped | Регрессия клиента | Поиск потребителей и контрактные тесты |
| Rate limit | Задержка/ошибка синхронизации | Существующий retry/backoff и диагностика |

### 12.1. Ограничения текущей реализации

#### Поддерживаемые GitHub API host

Текущая реализация TD-006 использует GitHub.com API с базовым адресом
`https://api.github.com/`.

Поддержка GitHub Enterprise и произвольных GitHub API host в рамках
текущей реализации не заявляется.

Поле `LastSyncedRepositoryHost` входит в идентичность checkpoint и
используется для предотвращения смешивания истории разных источников.
Само наличие этого поля не означает, что приложение умеет подключаться
к произвольному GitHub API host.
