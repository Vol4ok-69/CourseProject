# TD-001 Stage 2. Архитектурная спецификация изолированного анализатора БД
## Редакция 6. Нормативная версия для реализации

Статус: проект архитектурного решения, подготовленный на основе ревизии v5.  
Область: изолированное исполнение правил DB01–DB05 и JSON-обмен между Backend и автономным Runner.  
Связанные задачи: TD-001, TD-002, TD-003.  
Целевой стек: .NET 10, C#, PostgreSQL, Docker.

---

## 1. Назначение и границы

Цель TD-001 Stage 2 – перенести выполнение правил DB01–DB05 в автономный процесс, запускаемый в изолированном контейнере. Backend извлекает сведения о модели EF Core статическим анализом Roslyn, формирует входной JSON, запускает Runner и проверяет его результат.

Runner не должен собирать, загружать или исполнять анализируемый проект. Он получает только сериализованные метаданные и вычисляет результаты правил.

В Stage 2 входят:
- независимый проект `NetScope.DatabaseAnalyzer.Runner`;
- независимые DTO и JSON Schema для входа и выхода;
- сериализация/десериализация через `System.Text.Json` и source generation;
- реализация DB01–DB05 в Runner;
- запуск Runner в Docker с ограничениями;
- проверка входного и выходного документов;
- интеграция с Backend;
- обработка ошибок и отмены на границе DatabaseAnalyzer.

В Stage 2 не входят:
- общий рефакторинг цикла анализаторов в `AnalysisService` (TD-002);
- реализация полного Cleanup Worker (TD-003), кроме обязательных интерфейсных инвариантов, которые Runner не должен нарушать;
- изменение схемы PostgreSQL без отдельного обоснования и согласования;
- переключение production pipeline на новый Runner до прохождения критериев приёмки;
- расширение правил DB01–DB05 за пределы согласованной семантики.

## 2. Архитектурные инварианты

### 2.1. Zero Shared Code

Runner не ссылается на сборки Backend, Domain, Application, Infrastructure или существующих анализаторов. Между процессами нет общей DLL с DTO.

Стороны независимо реализуют собственные DTO. Совместимость обеспечивается версионированными JSON Schema и тестами контрактной совместимости.

### 2.2. Недоверенный вход

Все метаданные, пути, имена типов, SQL-фильтры и прочие строки из анализируемого проекта считаются недоверенными данными. Runner не интерпретирует их как команды и не выполняет SQL.

Runner не получает:
- строк подключения к БД;
- секреты Backend;
- токены доступа;
- исходники проекта, если они не нужны для отдельного диагностического сценария;
- доступ к сети по умолчанию.

### 2.3. Отсутствие ложной уверенности

Если данных недостаточно для безопасного выполнения правила, Runner пропускает соответствующую проверку и возвращает диагностику. Он не должен подменять неизвестное значение значением по умолчанию, которое меняет смысл проверки.

### 2.4. Production isolation

В production используется только контейнерный адаптер. Локальный запуск процесса допустим для тестов CLI и правил, но не считается изолированным исполнением и не может быть выбран production DI-конфигурацией.

## 3. Проекты и ответственность компонентов

### 3.1. Backend

Backend отвечает за:
1. получение задания и проверку владения им;
2. запуск Roslyn extraction;
3. преобразование результата extraction в DTO входного контракта;
4. запись входного JSON в выделенный каталог;
5. запуск контейнера через ограниченный адаптер;
6. проверку кода завершения и состояния контейнера;
7. чтение и валидацию выходного JSON;
8. повторную проверку владения заданием перед сохранением findings;
9. отображение результатов Runner в существующие Backend-модели.

Backend не должен передавать Runner объекты `AnalyzerFinding`, EF Core metadata или типы из Domain напрямую.

### 3.2. Runner

Runner отвечает за:
1. проверку входного JSON;
2. проверку поддерживаемой версии контракта;
3. проверку обязательных возможностей и полноты метаданных;
4. выполнение только тех правил, для которых входные данные достаточны;
5. формирование findings и diagnostics;
6. атомарную запись результата;
7. возврат документированного exit code.

Runner не обращается к PostgreSQL, Docker API, файловой системе проекта или сетевым ресурсам, кроме заранее смонтированных файлов обмена.

### 3.3. Container Process Adapter

Адаптер запускает контейнер и возвращает технический результат процесса: идентификатор контейнера, exit code, признак OOM, stdout/stderr с ограничением размера, факт отмены и факт таймаута.

Адаптер не интерпретирует findings и не принимает решения о сохранении результатов.

## 4. Модель идентификаторов

Типы идентификаторов сверены с фактическими сущностями Domain, конфигурацией EF Core и миграциями текущей ветки:

| Идентификатор | Backend | PostgreSQL | JSON |
|---|---|---|---|
| AnalysisId | `int` | `INTEGER` | integer |
| ExecutionToken | `Guid` / nullable в сущности | `UUID` | string, format uuid |
| FindingId | `int` (`AnalysisResult.Id`) | `INTEGER GENERATED BY DEFAULT AS IDENTITY` | integer |

Тип `FindingId` подтверждён и зафиксирован в нормативной схеме v1.0: в модели Backend (`AnalysisResult.Id`) – `int`, в PostgreSQL – целочисленный автоинкремент `INTEGER GENERATED BY DEFAULT AS IDENTITY` (таблица `"AnalysisResults"`), в выходном контракте JSON Schema (`database-analyzer-output-v1.schema.json`) и DTO `FindingContract` – `integer`.

`ContextId` и `EntityId` – строковые идентификаторы внутри одного документа анализа. Они не являются первичными ключами PostgreSQL.

Рекомендуемая детерминированная идентичность:
- `ProjectId`: нормализованный относительный путь к проекту относительно корня репозитория;
- `ContextId`: `ProjectId` + полное имя DbContext;
- `EntityId`: `ContextId` + стабильный идентификатор сущности.

Для Shared Type Entity идентификатор строится по имени сущности EF Core, а не по CLR-типу контейнера `Dictionary<string, object>`. Поле CLR-типа может быть null.

Нельзя использовать абсолютные пути машины разработчика в идентификаторах.

## 5. Модель метаданных EF Core

### 5.1. Сопоставление с хранилищем

`mappingType` описывает способ отображения сущности:
- `Table`;
- `View`;
- `SqlQuery`;
- `Function`;
- `Unmapped`;
- `Unknown`.

`Unknown` необходим для случаев, когда Roslyn extractor не смог определить тип сопоставления. Неизвестное значение не должно автоматически трактоваться как `Table`.

### 5.2. Ключи и статус идентификации

В нормативной схеме `database-analyzer-input-v1.schema.json` способ идентификации сущности задаётся перечислением `keyType` на уровне сущности:
- `PrimaryKey` – подтверждённый первичный ключ;
- `Keyless` – явно сконфигурированная сущность без ключа;
- `ImplicitKey` – ключ по соглашению;
- `Unknown` – статус ключа не определён или метаданные неполны.

Список ключей сущности передаётся в коллекции `keys`. Каждый элемент `KeyContract` содержит:
- `properties`: упорядоченный список свойств ключа (массив строк);
- `isPrimaryKey`: признак первичного ключа (boolean);
- `isExplicitName`: флаг явного именования ключа (boolean);
- `location`: исходное расположение в коде (`LocationContract`, nullable).

Keyless-сущность представляется значением `keyType="Keyless"` и соответствующей capability/диагностикой. Отсутствие ключа в неполных метаданных приводит к `keyType="Unknown"`, а не к предположению о Keyless.

### 5.3. Свойства

Каждое свойство (`PropertyContract`) содержит:
- `name`: имя свойства (строка);
- `columnName`: имя столбца в БД (nullable);
- `clrTypeName`: имя типа CLR (nullable);
- `isRequired`: признак обязательности свойства (boolean);
- `isPrimaryKey`: признак вхождения в первичный ключ (boolean);
- `isForeignKey`: признак вхождения во внешний ключ (boolean);
- `isShadowProperty`: признак теневого свойства EF Core (boolean);
- `isConcurrencyToken`: признак токена конкурентного доступа (boolean);
- `location`: исходное расположение в коде (`LocationContract`, nullable).

Для shadow property отсутствие явной CLR-декларации в исходном классе является ожидаемым и не должно считаться ошибкой извлечения.

### 5.4. Shared Type Entity

Сущность содержит:
- `isSharedType`: признак разделяемого типа (boolean);
- `name`: имя сущности в модели EF Core;
- `clrTypeName`: nullable (для shared type может быть `Dictionary<string, object>`);
- `entityId`: стабильный детерминированный строковый идентификатор, основанный на `contextId` и имени сущности EF Core.

Для сущности также передаются флаги неполноты метаданных: `hasIncompleteMetadata`, `hasIncompleteKeys`, `hasIncompleteForeignKeys`, `hasIncompleteIndexes`, `hasIncompleteNavigations`, `hasIncompleteSkipNavigations`, признак наследования `isDerivedEntity`, `baseEntityName` и список `unsupportedFeatures`.

### 5.5. Связи, внешние ключи и индексы

Внешний ключ (`ForeignKeyContract`) передаёт:
- `principalEntityName`: имя главной сущности (строка);
- `properties`: зависимые свойства внешнего ключа (массив строк);
- `principalProperties`: главные свойства (массив строк);
- `navigationPropertyName`: навигационное свойство (nullable);
- `navigationToPrincipal` и `navigationToDependent`: навигации к главной и зависимой сущности (nullable);
- `deleteBehavior`: поведение каскадного удаления (`Cascade`, `ClientCascade`, `ClientNoAction`, `ClientSetNull`, `NoAction`, `Restrict`, `SetNull`, `Unknown`);
- `isExplicitName`: флаг явного именования FK (boolean);
- `isNavigationResolved`: флаг разрешения навигаций (boolean);
- `location`: исходное расположение (`LocationContract`, nullable).

Индекс (`IndexContract`) передаёт:
- `name`: имя индекса (nullable);
- `properties`: упорядоченный список свойств (массив строк);
- `isUnique`: признак уникальности (boolean);
- `filter`: SQL-фильтр частичного индекса (nullable);
- `isExplicitName`: флаг явного именования (boolean);
- `location`: исходное расположение (`LocationContract`, nullable).

Пропуск навигации (`SkipNavigationContract`) для many-to-many связей передаёт:
- `navigationPropertyName`: имя навигационного свойства;
- `targetEntityName`: имя целевой сущности;
- `targetEntityId`: идентификатор целевой сущности (nullable);
- `joinEntityName`: имя промежуточной сущности join table;
- `joinEntityId`: идентификатор промежуточной сущности (nullable);
- `inverseNavigationPropertyName`: имя обратной навигации (nullable);
- `location`: исходное расположение (`LocationContract`, nullable).

Имена FK/индексов не являются обязательными: EF Core может генерировать их по соглашению.

## 6. Capabilities и полнота данных

### 6.1. Разделение понятий

В контракте используются два разных набора:

- `metadataCapabilities`: возможности, которые extractor действительно распознал и корректно отразил в переданном документе;
- `runnerCapabilities`: возможности, которые данная версия Runner умеет корректно интерпретировать.

Runner не должен считать, что наличие capability в одном наборе означает наличие её в другом.

### 6.2. Уровни полноты

Одного глобального набора capabilities недостаточно. Документ должен фиксировать полноту на уровнях:
- всего extraction result;
- DbContext;
- Entity;
- при необходимости конкретной связи/индекса.

Для каждого уровня используется список `unsupportedFeatures` или эквивалентная структура с кодом, областью действия и кратким описанием. `hasIncompleteMetadata` может быть агрегированным признаком, но не заменяет детализацию.

### 6.3. Правило принятия решения

Для каждой проверки Runner определяет:
1. какие сведения нужны правилу;
2. на каком уровне эти сведения должны быть полными;
3. какие capabilities требуются;
4. есть ли диагностические признаки, что сведения не извлечены или неоднозначны.

Правило выполняется только при подтверждённой достаточности входа. Иначе Runner пропускает проверку соответствующей области и создаёт diagnostic с `ruleId`, `contextId`, `entityId` и кодом причины.

Нельзя использовать только условие `requiredCapabilities ⊆ metadataCapabilities ∩ runnerCapabilities`, если полнота конкретной сущности не подтверждена.

### 6.4. Базовые capabilities

Предлагаемый базовый реестр для первой версии:
- `CoreRelational`;
- `KeylessEntities`;
- `ViewMapping`;
- `SqlQueryMapping`;
- `FunctionMapping`;
- `FilteredIndexes`;
- `ImplicitJoinEntities`;
- `ShadowProperties`;
- `InheritanceHierarchy`;
- `SharedTypeEntities`;
- `CompositeKeys`;
- `CompositeForeignKeys`.

Реестр является версионируемым нормативным списком. Неизвестная строковая capability не должна приводить к падению Runner. Если неизвестная capability влияет на семантику конкретной сущности, зависимые проверки пропускаются.

## 7. Правила DB01–DB05

Перед реализацией каждое правило должно иметь тестируемую спецификацию: входные поля, исключения, условия пропуска и примеры.

Минимальные требования:

| Правило | Условия корректного выполнения |
|---|---|
| DB01 | Достоверно известны mapping type, наличие PK и полнота данных о ключах; Keyless/View/SqlQuery/Function обрабатываются отдельно согласно семантике правила |
| DB02 | Связь и навигационные свойства достаточно полно извлечены; неизвестная навигация не приравнивается к отсутствующей |
| DB03 | Достоверно определены skip navigation и join entity; отсутствие сведений о M:N не трактуется как отсутствие M:N в модели |
| DB04 | Доступны упорядоченные свойства FK и индексов, включая composite keys, shadow properties и покрытие первичным/alternate key |
| DB05 | Доступны упорядоченные свойства, уникальность и фильтр индекса; сравнение фильтров выполняется консервативно |

Для DB04 индекс покрывает FK, только если последовательность его начальных столбцов совпадает с последовательностью dependent properties FK. Сравнение как неупорядоченных множеств недопустимо.

Для DB05 два индекса не считаются дубликатами только на основании одинакового списка столбцов. Учитываются как минимум порядок столбцов, уникальность и фильтр. Если нормализация SQL-фильтра не реализована надёжно, правило пропускается для соответствующей пары индексов с диагностикой.

DB02 не должен выдавать finding при `isNavigationResolved=false` или неизвестном значении, если вывод зависит от наличия навигации.

## 8. JSON-контракты

### 8.1. Версионирование

Используется `schemaVersion` в формате `major.minor`. Runner:
- принимает только поддерживаемый major;
- допускает неизвестные необязательные поля в пределах согласованной minor-совместимости;
- отклоняет неизвестную major-версию;
- проверяет наличие всех семантически обязательных данных;
- не считает `JsonUnmappedMemberHandling.Skip` достаточной проверкой совместимости.

Изменение смысла существующего поля требует новой major-версии.

### 8.2. Входной документ

Входной документ включает:
- `schemaVersion`;
- `analysisId`;
- `executionToken`;
- `createdAtUtc`;
- `metadataCapabilities`;
- `metadata`;
- `configuration`;
- `diagnostics`/`unsupportedFeatures` extraction, если они нужны для оценки полноты.

`analysisId` – integer, соответствующий целочисленному идентификатору `Analysis.Id` в Backend и PostgreSQL. `executionToken` – UUID.

Все nullable поля явно описаны в JSON Schema. Значение null и отсутствие поля имеют однозначную семантику. Для обязательных коллекций передаётся пустой массив, а не null.

### 8.3. Выходной документ

Выходной документ включает:
- `schemaVersion`;
- `analyzerVersion`;
- `analysisId`;
- `executionToken`;
- `status`;
- `completedAtUtc`;
- `metrics`;
- `findings`;
- `diagnostics`;
- `errors`.

Каждый finding содержит:
- `id` (integer, согласованный с `AnalysisResult.Id` в Backend и `INTEGER GENERATED BY DEFAULT AS IDENTITY` в таблице PostgreSQL `"AnalysisResults"`);
- `ruleId`;
- `ruleName`;
- `severity`;
- `message`;
- `recommendation`;
- `contextId`;
- `entityId` (nullable, если finding относится к контексту/модели в целом);
- `targetEntityName` (nullable);
- `targetTable` (nullable);
- `location` (nullable).

Контракт не должен требовать строку там, где достоверное значение может отсутствовать.

`diagnostics` описывают неполноту, пропуск правила, неизвестные capabilities и неразрешённые ссылки. `errors` описывают фатальные ошибки обработки документа или Runner.

### 8.4. Валидация

Валидация выполняется на обеих сторонах:
- Runner валидирует вход до оценки правил;
- Backend валидирует выход до маппинга и сохранения;
- размер входа/выхода и количество объектов ограничены конфигурацией;
- неизвестные enum значения обрабатываются безопасно;
- сообщения ошибок и stderr ограничиваются по длине;
- stack trace и локальные абсолютные пути не возвращаются клиенту API.

JSON Schema – часть исходников и тестируется на соответствие DTO. Схема не заменяет бизнес-валидацию.

## 9. Статусы и жизненный цикл исполнения

Нужно разделять три независимых результата:

1. `RunnerStatus`: `Success`, `PartialSuccess`, `Failed`.
2. `ExecutionControlStatus` на стороне Backend: `Completed`, `LeaseLost`, `Cancelled`, `TimedOut`, `InfrastructureFailure`.
3. Статус Analysis в БД: определяется существующей моделью и логикой `AnalysisService`, а не новым enum Runner.

Runner не принимает решений о статусе всей Analysis и не записывает данные в БД.

Findings могут быть переданы слою сохранения только при `RunnerStatus` `Success` или `PartialSuccess` и после успешной повторной проверки владения Analysis.

`LeaseLost` означает, что Backend прекращает обработку результата и не сохраняет findings. Он не должен самовольно менять статус записи, если уже не владеет задачей.

`Cancelled`, `TimedOut` и `InfrastructureFailure` обрабатываются согласно существующей политике очереди. Нельзя объявлять их автоматически retryable или terminal без согласования с TD-002/TD-007.

## 10. TD-003: блокировки, токен и файловое владение

Этот раздел задаёт обязательные ограничения для интеграции, но не утверждает, что TD-003 уже реализована.

### 10.1. Владение задачей

`AnalysisId` идентифицирует запись анализа. `ExecutionToken` идентифицирует конкретное исполнение/lease. Каждый файловый каталог и контейнер должны быть привязаны к обоим значениям.

До файловых операций Backend обязан проверить актуальный токен. После длительных операций и непосредственно перед сохранением findings владение проверяется повторно.

Проверка токена должна выполняться атомарно с операцией сохранения результата или в транзакции/условном UPDATE, который гарантирует, что устаревший worker не сможет записать результат после потери lease.

### 10.2. Advisory locks

Если используется session-level `pg_advisory_lock_shared`, соединение должно оставаться тем же физическим PostgreSQL-сеансом до освобождения блокировки. Соединение с активной блокировкой нельзя возвращать в общий пул.

Выделенное соединение с `Pooling=false` является допустимым вариантом, но требует отдельного лимита одновременных соединений и корректного освобождения ресурсов.

Потеря соединения означает, что PostgreSQL освободит session-level lock после обнаружения разрыва. Это не гарантирует мгновенного обнаружения разрыва приложением. Поэтому обязательны:
- ограниченный таймаут операций;
- контроль состояния соединения;
- отмена/остановка контейнера при подтверждённой потере владения;
- повторная проверка ExecutionToken перед любым сохранением;
- запрет продолжения файловых операций после того, как потеря владения установлена.

### 10.3. Cleanup

Cleanup Worker получает эксклюзивную блокировку для конкретного AnalysisId, перечитывает состояние БД и удаляет только каталоги, для которых доказано отсутствие активного владельца и истечение срока хранения.

Если БД недоступна, блокировку получить нельзя, токен нельзя проверить или файловое состояние неоднозначно, удаление запрещено.

Правило «удалить все каталоги, чей токен не равен текущему» недостаточно. Оно не учитывает orphan-каталоги, удалённые записи, retry, retention и промежуточные состояния. Политика удаления должна быть отдельной частью TD-003.

Worker, который установил, что потерял lease или соединение, не удаляет собственный рабочий каталог. Его судьбу определяет Cleanup Worker по отдельной политике.

## 11. Безопасность контейнера и Sidecar

### 11.1. Контейнер

Минимальные ограничения:
- `--network none`;
- `--read-only`;
- запуск не от root;
- CPU, memory, PID и wall-clock limits;
- ограниченный размер входа/выхода;
- отсутствие секретов и Docker socket внутри контейнера;
- только необходимые bind mounts;
- input mount read-only;
- output mount только для записи результата;
- фиксированный образ по digest;
- запрет произвольных аргументов и команд от Backend.

Нельзя считать эти флаги абсолютной гарантией безопасности. Остаточные риски ядра, runtime и конфигурации хоста должны быть задокументированы.

### 11.2. Docker Sidecar

Процесс с доступом к Docker Daemon socket является высокопривилегированным. Компрометация Sidecar, имеющего unrestricted socket, может означать компрометацию хоста.

RPC-интерфейс Sidecar должен принимать только типизированные параметры: AnalysisId, ExecutionToken и ограниченные настройки. Backend не передаёт произвольные пути, Docker args, image names, entrypoints или команды.

Ограничение набора API-вызовов внутри Sidecar само по себе не является сильной границей, если Sidecar может напрямую обращаться к неограниченному Docker socket. Для снижения риска нужны отдельный Docker Engine/VM либо строго ограниченный посредник Docker API с проверяемой политикой.

Вариант инфраструктуры должен быть утверждён до production-реализации. Нельзя называть Sidecar с root-equivalent Docker socket безопасной изоляцией Backend от хоста без описания остаточного риска.

### 11.3. Работа с файлами результата

Проверка `FileInfo` перед открытием файла не устраняет все TOCTOU-сценарии. Реализация должна использовать безопасное открытие файла без следования символическим ссылкам там, где это поддерживает целевая ОС, проверять, что файл расположен внутри ожидаемого каталога, и ограничивать размер.

Чтение выполняется только после завершения контейнера. Runner пишет во временный файл и переименовывает его в итоговый в пределах одной файловой системы. Это снижает риск частичного результата, но не заменяет проверку пути и прав.

## 12. Права доступа и переносимость

Модель UID/GID `10000`, `10001`, GID `10002` может применяться на Linux при явном создании пользователей/группы и проверке bind mount permissions.

Необходимо отдельно протестировать:
- Linux filesystem;
- Docker Desktop на Windows;
- WSL2, если он входит в поддерживаемую среду.

Нельзя утверждать, что Windows/Docker Desktop полностью эмулирует POSIX-права. Фактическое поведение зависит от механизма shared filesystem и конфигурации Docker Desktop.

`chmod 777` запрещён. SGID/shared group допустимы только после проверки на целевой файловой системе. Если bind mount не обеспечивает ожидаемую семантику, следует выбрать другой способ обмена, например выделенный volume или подготовку каталогов на стороне хоста.

## 13. Тестирование и адаптеры

### 13.1. Тесты Runner

Без Docker тестируются:
- парсинг CLI;
- валидация входной схемы;
- совместимость версий;
- capabilities negotiation;
- правила DB01–DB05;
- сериализация выходного документа;
- лимиты размера и количества элементов;
- атомарная запись файла на поддерживаемой файловой системе.

### 13.2. Docker integration tests

Только реальные контейнерные тесты подтверждают:
- отсутствие сетевого доступа;
- read-only root filesystem;
- UID/GID и права на bind mounts;
- CPU/memory/PID limits;
- таймаут и принудительную остановку;
- OOM handling;
- невозможность чтения/записи за пределами mounts;
- обработку symlink/path traversal.

### 13.3. LocalProcessAdapter

`LocalProcessAdapter` разрешён только в тестовых конфигурациях и CI для проверки запуска CLI без Docker. Он не проверяет и не обеспечивает изоляцию.

Production DI должен регистрировать только Docker adapter. Защита от ошибочной регистрации должна быть явной: конфигурация окружения, fail-fast при production startup и тест DI, подтверждающий отсутствие LocalProcessAdapter в production.

## 14. Обработка ошибок и границы TD-002

DatabaseAnalyzer должен преобразовывать ожидаемые ошибки контейнерного запуска и протокола в типизированный результат/диагностику, чтобы не выбрасывать наружу обычные ошибки Runner как необработанные исключения.

При этом нельзя поглощать:
- потерю lease;
- отмену вызывающей задачи;
- ошибки БД при сохранении;
- ошибки инфраструктуры, которые требуют остановки текущего исполнения.

TD-002 остаётся отдельной задачей: общий цикл `AnalysisService` должен изолировать сбои отдельных анализаторов и корректно сохранять частичные результаты. TD-001 не должен незаметно менять общую семантику AnalysisService.

10. Docker integration tests подтверждают реальные ограничения изоляции на Linux — *статус: NEEDS_VERIFICATION (требуется прогон в Linux-окружении)*.
