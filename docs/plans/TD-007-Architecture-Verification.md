## 1. Назначение и границы TD-007

### 1.1. Исходная проблема и цели задачи

В текущей кодовой базе CourseProject / NetScope фоновая обработка задач анализа коммитов опирается на модель долговечной очереди в PostgreSQL с механизмом аренды (`LeaseExpiration`) и токенами владения (`ExecutionToken`), реализованными в рамках TD-002.

Однако текущая архитектура очереди обладает существенными уязвимостями надёжности:
1. **Угроза бесконечного аварийного цикла (Poison Pill / CrashLoop):** Если задача анализа содержит специфические входные данные, вызывающие фатальный сбой процесса (например, `OutOfMemoryException`, переполнение стека в Roslyn, сбой нативного процесса Docker CLI или ОС SIGKILL), воркер аварийно завершается, не успев записать терминальный статус в базу данных. После перезапуска сервиса и истечения времени аренды (`LeaseExpiration`) эта же задача повторно захватывается воркером, вызывая циклический перезапуск процесса (`CrashLoop`) и блокируя всю очередь.
2. **Отсутствие классификации отказов и Retry-механизма:** Любая кратковременная ошибка (сетевой сбой GitHub API при скачивании архива, кратковременный таймаут Docker daemon, временная блокировка дискового I/O) немедленно переводит сущность `Analysis` в терминальный статус `Failed` ([AnalysisService.cs#L578](../../src/Backend/Application/Services/AnalysisService.cs#L578)), требуя от пользователя ручной повторной отправки коммита.
3. **Неконтролируемый повторный захват:** Сущность `Analysis` не содержит информации о числе предпринятых попыток выполнения и времени следующего допустимого запуска.

### 1.2. Границы задачи и сохранение гарантий TD-002

Задача TD-007 призвана внедрить:
- Учёт числа попыток исполнения задачи с ограничением максимального числа захватов (`MaxAttempts`);
- Отложенный повторный запуск (Delayed Retry / Backoff) с экспоненциальной задержкой и случайным разбросом (Jitter);
- Корректную реакцию на серверные заголовки ограничения интенсивности внешних API (`Retry-After`, `X-RateLimit-Reset`);
- Перевод задачи в статус `Failed` при исчерпании лимита попыток или при обнаружении детерминированного постоянного сбоя.

**Обязательные инварианты TD-002, которые должны быть полностью сохранены:**
- Протокол владения рабочей директорией `IAnalysisLeaseGuard` и периодическое продление аренды (`LeaseRenewal`);
- Защита от потери владения: если аренда истекла или перехвачена, зомби-воркер не имеет права обновлять состояние задачи или удалять рабочие директории;
- Атомарность переходов между состояниями с использованием оптимистических предикатов `WHERE "Id" = @id AND "ExecutionToken" = @token AND "Status" = 1`.

### 1.3. Что явно НЕ входит в границы TD-007

1. **Фоновая очистка брошенных каталогов аварийно упавших процессов (`AnalysisCleanupService`):** Данная функциональность относится к задаче **`TD-003`**, которая сохраняет статус **`DEFERRED`**. В рамках TD-007 решается только штатная очистка директории текущей попытки при контролируемом сбое.
2. **Расширение публичного API и пользовательского интерфейса:** Включение полей `AttemptCount` и `NextAttemptAt` в `AnalysisDto` не предусмотрено проектными требованиями и не входит в объём TD-007.
3. **Изменение публичного контракта анализаторов (`IAnalyzer`):** Сигнатура `Task<IReadOnlyList<AnalyzerFinding>> AnalyzeAsync(...)` остаётся неизменной для всех анализаторов (C#, SQL, Security, Database).
4. **Ревизия устаревшего синхронного пути `AnalyzeAsync`:** Синхронный метод [AnalysisService.cs#L798](../../src/Backend/Application/Services/AnalysisService.cs#L798), выполняющийся напрямую в обход долговечной очереди, исключён из скоупа TD-007.

## 2. История архитектурной верификации

Архитектурное исследование TD-007 проводилось в пять последовательных этапов. Ниже зафиксирована хронология исследований, выявленные противоречия и текущий статус по каждому проходу.

### 2.1. Проход 1: Первичный аудит очереди и концепция Poison Pill
- **Исследованные направления:** Базовая модель повторных попыток, структура сущности `Analysis`, различие временных (transient) и постоянных (permanent) сбоев.
- **Найденные проблемы:** В базе данных отсутствуют поля `AttemptCount`, `MaxAttempts`, `NextAttemptAt`. Любой сетевой сбой переводит анализ в `Failed`. При падении процесса воркера задача зависает до истечения аренды, после чего бесконечно перехватывается.
- **Устранённые противоречия:** Сформулирована потребность в расширении таблицы `"Analyses"` и экспоненциальном backoff.
- **Оставшиеся вопросы:** Был предложен неверный порядок вызовов: `ScheduleRetryAsync` (сброс статуса в `Pending` и очистка `ExecutionToken`) до вызова `repositorySourceService.CleanupAsync`. Это нарушало контракт `IAnalysisLeaseGuard` (невозможно подтвердить владение рабочей директорией после сброса токена).
- **Итоговый статус прохода:** `NEEDS INVESTIGATION`.

### 2.2. Проход 2: Взаимодействие LeaseGuard и очистки директорий
- **Исследованные направления:** Порядок операций `ScheduleRetryAsync` и `CleanupAsync`, изоляция файлов при повторных попытках.
- **Найденные проблемы:** Выявлено, что очистка директории должна выполняться строго до сброса `ExecutionToken` в базе данных. Было выдвинуто ошибочное предположение, что сервис `AnalysisCleanupService` автоматически удаляет брошенные каталоги в фоне.
- **Устранённые противоречия:** Закреплено правило: очистка текущей попытки выполняется строго при подтверждённом владении до сброса аренды в БД.
- **Оставшиеся вопросы:** Проверка фактической регистрации `AnalysisCleanupService` в DI показала, что сервис не зарегистрирован и относится к отложенной задаче TD-003. Предложенный цикл захвата очереди содержал потенциальную бесконечную петлю при отказе `pg_try_advisory_xact_lock`.
- **Итоговый статус прохода:** `NEEDS INVESTIGATION`.

### 2.3. Проход 3: Границы TD-003 и конкурентный захват
- **Исследованные направления:** Проверка регистрации сервисов в `Program.cs`, поведение advisory lock при конкурентном захвате, жизненный цикл `DatabaseAnalyzer` в DI.
- **Найденные проблемы:** Подтверждено, что `AnalysisCleanupService` не зарегистрирован в DI, а задача TD-003 отложена (`DEFERRED`). Обнаружено, что цикл `while (true)` с `tx.RollbackAsync(); continue;` при отказе advisory lock приводит к 100% CPU spinning, так как rollback снимает блокировку строки, и `FOR UPDATE SKIP LOCKED` снова выбирает ту же самую строку.
- **Устранённые противоречия:** Зафиксировано, что TD-007 не должен зависеть от реализации фоновой очистки TD-003.
- **Оставшиеся вопросы:** Устранение бесконечного цикла выборки кандидатов; рассинхронизация времени приложения и СУБД; механизм тестирования потери Commit ACK; устранение мутабельного состояния из `Scoped` анализатора `DatabaseAnalyzer`.
- **Итоговый статус прохода:** `NEEDS INVESTIGATION`.

### 2.4. Проход 4: Анализ временной модели, токенов и классификации
- **Исследованные направления:** Пропуск заблокированных кандидатов (`skippedCandidateIds`), генерация путей по `ExecutionToken:D`, расширение `AnalyzerFinding` вместо мутабельных свойств сервиса, аудит `DateTime.UtcNow`.
- **Найденные проблемы:** Концептуальная ошибка: предложенный `DbTransactionInterceptor.TransactionCommittedAsync` не моделирует потерю сетевого пакета ACK коммита (он вызывается после успешного получения ACK клиентом). Выявлено, что `GitHubService` и `RepositorySourceService` полностью уничтожают HTTP-заголовки ответа (`Retry-After`, `Date`, `X-RateLimit-Reset`), делая невозможным расчёт задержки в `AnalysisService`. Предложено необоснованное расширение DTO публичного API.
- **Устранённые противоречия:** Доказана уникальность путей директорий при каждом захвате задачи благодаря GUID; обоснована семантика `AttemptCount` как счётчика захватов задачи.
- **Оставшиеся вопросы:** Реалистичный сетевой fault injection для Commit ACK loss; алгоритм объединения нескольких сроков Retry-After; устранение противоречий по вызовам времени; отказ от несанкционированного изменения `AnalysisDto`.
- **Итоговый статус прохода:** `NEEDS INVESTIGATION`.

### 2.5. Проход 5: Спецификация серверных ограничений и сетевого отказа
- **Исследованные направления:** Алгоритм объединения серверных ограничений $\max(T_{\text{RetryAfter}}, T_{\text{RateLimitReset}})$, компенсация Clock Skew по заголовку `Date`, архитектура сетевого fault injection через TCP-прокси / Toxiproxy, сверка всех вхождений `DateTime.UtcNow`.
- **Найденные проблемы:** Выявлены фундаментальные ограничения наивного текстового TCP-прокси (отсутствие сохранения границ сообщений TCP, невозможность инспекции при TLS, риск гонки сокета, эвристичность фиксированных задержек). Зафиксирована необходимость согласования продуктовых политик по максимальному времени ожидания Rate Limit.
- **Устранённые противоречия:** Сформулированы строгие требования к математической модели задержек и разграничению зон ответственности между TD-007 и TD-003.
- **Итоговый статус прохода:** `NEEDS INVESTIGATION` (переход к `READY FOR DESIGN` отложен до разрешения оставшихся технических вопросов).

## 3. Poison Pill и конкурентный захват

### 3.1. Семантика полей очереди и исчерпание лимита захватов

В таблице `"Analyses"` проектируются следующие поля управления жизненным циклом:

1. **`AttemptCount` (integer, NOT NULL, DEFAULT 0):**
   - **Семантика:** Счётчик **количества фактических захватов задачи для исполнения (Acquisition Attempts)** воркерами.
   - **Атомарность инкремента:** `AttemptCount` должен увеличиваться атомарно строго в СУБД при успешном захвате задачи воркером.
2. **`MaxAttempts` (integer, NOT NULL, DEFAULT 3):**
   - Внутренний лимит допустимых захватов для конкретной задачи. Значение по умолчанию задаётся в конфигурации приложения и требует отдельного продуктового согласования.
3. **`NextAttemptAt` (timestamp with time zone, NULL):**
   - Отметка времени СУБД, ранее которой задача не должна выбираться воркерами из очереди. При установке задержки задача переводится в статус `Pending (0)`.

#### Точная целевая семантика исчерпания `MaxAttempts`:
- **Запрет перевода в `Running`:** Захват задачи воркером **не должен переводить задачу в статус `Running (1)`**, если лимит попыток уже исчерпан (`AttemptCount >= MaxAttempts`).
- **Обработка Stale-задач с исчерпанным лимитом:** Если задача находилась в статусе `Running (1)`, время её аренды истекло (`LeaseExpiration < clock_timestamp()`), но её счётчик `AttemptCount` уже достиг или превысил `MaxAttempts`, такая задача **должна перейти в терминальный статус `Failed (3)` без нового выполнения**, с фиксацией диагностического сообщения в `ErrorMessage` (например: *"Превышен лимит попыток выполнения анализа (3/3). Задача остановлена для предотвращения циклического сбоя"*).
- **Исключение превышения лимита конкурентными воркерами:** Конкурентные параллельные воркеры в условиях состязания за выборку строк из очереди не должны иметь возможности запустить задачу сверх установленного лимита `MaxAttempts`.
- **Защита перехода в `Failed` условиями конкурентного обновления:** Перевод зависшей задачи с исчерпанным лимитом в статус `Failed` должен быть защищён строгим предикатом конкурентного обновления (проверка текущего `Status = 1`, `ExecutionToken` или условия подтверждённого истечения аренды), чтобы исключить сценарий, при котором запоздавший перевод в `Failed` перезапишет задачу, уже успешно завершённую или перехваченную другим воркером.
- **Статус реализации:** Конкретный SQL-запрос для атомарного захвата и условного перевода в `Failed` при исчерпании лимита на текущий момент ещё не зафиксирован и является предметом проектирования. Данное требование нуждается в **обязательной проверке сквозными PostgreSQL integration tests** с имитацией конкурентных воркеров.

### 3.2. Алгоритм пропуска кандидатов (Candidate Skipping)

Для предотвращения 100% CPU spinning при отказе `pg_try_advisory_xact_lock` предлагается сохранять идентификаторы временно заблокированных кандидатов в локальной коллекции вызова и исключать их из последующих итераций:

```sql
SELECT "Id"
FROM "Analyses"
WHERE ("Status" = 0
   OR ("Status" = 1 AND ("LeaseExpiration" IS NULL OR "LeaseExpiration" < clock_timestamp())))
  AND ("NextAttemptAt" IS NULL OR "NextAttemptAt" <= clock_timestamp())
  AND "Id" != ALL(@skippedCandidateIds)
  AND NOT EXISTS (
      SELECT 1 FROM pg_locks
      WHERE locktype = 'advisory'
        AND classid = hashtext('netscope_analysis_workspace')
        AND objid = "Analyses"."Id"
        AND objsubid = 2
        AND granted = true
  )
ORDER BY "CreatedAt" ASC
LIMIT 1
FOR UPDATE SKIP LOCKED;
```

#### Нерешённые технические вопросы реализации алгоритма:
- **Npgsql Parameter Mapping:** Требуется проверить поведение драйвера Npgsql 10.0 при передаче пустого массива `int[]` в конструкцию `"Id" != ALL(@array)` (в PostgreSQL выражение `!= ALL('{}')` возвращает `true`, но требует валидации со стороны типизации Npgsql);
- **Производительность при больших очередях:** При многократных коллизиях advisory lock объём массива `@skippedCandidateIds` может расти, что требует ограничения максимального числа итераций в рамках одного вызова;
- **Необходимость тестов:** Корректность работы алгоритма должна быть подтверждена сквозными тестами на реальном PostgreSQL с параллельными соединениями. SQLite и InMemory не поддерживают семантику `FOR UPDATE SKIP LOCKED` и advisory locks.

#### Целевое требование будущей реализации TD-007:
Обязательным целевым инвариантом будущей реализации TD-007 является обеспечение того, чтобы **все без исключения** операции перевода задачи из статуса `Running` (`CompleteAsync`, `FailAsync`, `RenewLeaseAsync`, а также проектируемый метод `ScheduleRetryAsync`) выполнялись строго через атомарный предикат:
```sql
WHERE "Id" = @analysisId
  AND "ExecutionToken" = @executionToken
  AND "Status" = 1;
```

## 4. GitHub Rate Limit и Retry-After

### 4.1. Установленные факты текущей кодовой базы

1. **Уничтожение заголовков:** В методах [GitHubService.cs#L235-L245](../../src/Backend/Infrastructure/GitHub/GitHubService.cs#L235-L245) и [RepositorySourceService.cs#L645-L685](../../src/Backend/Infrastructure/GitHub/RepositorySourceService.cs#L645-L685) при получении ответов 429 или 403 (Rate Limited) создаётся исключение `GitHubIntegrationException`, а объект `HttpResponseMessage` утилизируется в блоке `using`.
2. **Потеря метаданных:** Заголовки `Retry-After`, `X-RateLimit-Reset` и `Date` в текущей реализации **не считываются и не передаются**.
3. **Отсутствие информации в очереди:** В [AnalysisService.cs#L190-L240](../../src/Backend/Application/Services/AnalysisService.cs#L190-L240) ошибка классифицируется без информации о времени сброса лимита.

### 4.2. Предварительный алгоритм объединения серверных ограничений

При возникновении ограничения интенсивности запросов алгоритм обязан удовлетворить **все** предъявленные сервером требования. Если сервер вернул одновременно локальный `Retry-After` и глобальный `X-RateLimit-Reset`, повтор разрешается только после наступления **самого позднего обязательного срока**:

$$T_{\text{mandatory}} = \max(T_{\text{RetryAfter}}, T_{\text{RateLimitReset}})$$

#### Обработка дрейфа часов (Clock Skew):
- Если сервер предоставил заголовок `Date`, дельта вычисляется относительно этого заголовка: $\Delta = T_{\text{target}} - T_{\text{Date}}$;
- Если заголовок `Date` отсутствует, дельта вычисляется относительно времени клиента с добавлением защитного буфера безопасности (Safety Margin, 5 секунд);
- Если полученная задержка отрицательна или равна нулю (прошедшая дата), устанавливается минимальная ненулевая задержка в 1 секунду.

### 4.3. Открытые вопросы и несогласованные политики

1. **Недопустимость сокращения обязательного срока:** Технический предел планировщика очереди (`MaxTechnicalQueueDelay`) **нельзя использовать для усечения обязательного серверного срока**. Если GitHub требует ожидания 40 минут, а технический предел установлен в 15 минут, повтор запроса через 15 минут гарантированно нарушит правила API и может повлечь блокировку IP-адреса сервиса.
2. **Поведение при превышении технического предела:** Если серверный срок превышает интервал, который очередь может безопасно удерживать, задача **не должна ставиться в повтор**. Она должна быть немедленно переведена в статус `Failed` с детальным сообщением.
3. **Статус порога ожидания:** Значение `MaxRateLimitWaitMinutes = 15` является предварительным предложением, а не установленным правилом. Необходима фиксация продуктового решения: сколько времени допустимо задерживать анализ коммита пользователя при исчерпании квоты GitHub API (5 минут, 15 минут, 1 час или завершать сразу).
4. **Некорректные данные:** Требуется верификация поведения парсера при повреждённых строках даты и переполнении 64-битных целых чисел.
5. **Трассировка контракта:** Требуется спроектировать и протестировать сквозной путь передачи задержки: от `HttpResponseHeaders` через свойства `GitHubIntegrationException` до вызова `ScheduleRetryAsync`.

## 5. Моделирование Commit ACK Loss

### 5.1. Анализ точки отказа

В предыдущих отчётах ошибочно утверждалось, что использование перехватчика `DbTransactionInterceptor.TransactionCommittedAsync` моделирует потерю сетевого подтверждения коммита.

**Причина ошибочности:**
- Метод `TransactionCommittedAsync` в EF Core вызывается **после того**, как Npgsql на стороне клиента успешно вычитал из сетевого сокета пакеты PostgreSQL `CommandComplete('COMMIT')` и `ReadyForQuery('Z')`, сбросил статус транзакции и уведомил контекст данных.
- Выброс исключения в этот момент моделирует сбой в коде приложения **после успешного коммита**, а не потерю сетевого пакета.
- Настоящая потеря ACK означает, что сам вызов `await transaction.CommitAsync()` на клиенте завершается исключением `NpgsqlException` / `IOException` из-за внезапного обрыва сокета во время ожидания ответа от сервера, хотя СУБД транзакцию уже зафиксировала в WAL.

### 5.2. Подтверждённые версии библиотек

По фактическим файлам проектов:
- `Microsoft.EntityFrameworkCore`: **`10.0.12`**
- `Npgsql.EntityFrameworkCore.PostgreSQL`: **`10.0.3`**
- `Npgsql`: **`10.0.3`**
- `Testcontainers.PostgreSql`: **`4.16.0`** ([Backend.Tests.csproj#L20](../../tests/Backend.Tests/Backend.Tests.csproj#L20))

Драйвер Npgsql 10.0 выполняет отправку команды коммита и вычитывание ответа монолитно во внутренних методах коннектора. Стандартный публичный API Npgsql и EF Core не предоставляет точек внедрения в промежутке между отправкой запроса `COMMIT` и чтением ответа СУБД.

### 5.3. Недостатки наивного TCP-прокси и открытые вопросы

Рассматривалось создание тестового `TcpListener` для перехвата трафика между Npgsql и PostgreSQL. Однако анализ выявил серьёзные технические уязвимости этого подхода:
1. **Отсутствие границ сообщений в TCP:** TCP является байтовым потоком (stream-oriented). Сообщение клиента может прийти разбитым на произвольные фрагменты (TCP segments), поэтому наивный поиск подстроки `COMMIT` в очередном буфере ненадежен.
2. **Extended Query Protocol:** Npgsql при коммите транзакций может использовать протокол расширенных запросов (`Sync` / `Execute`), где команда не передаётся в виде открытого ASCII-текста `"COMMIT"`.
3. **Недоступность при TLS:** Если между клиентом и СУБД включено TLS-шифрование (`SslMode=Require/Prefer`), прикладной протокол PostgreSQL недоступен для анализа промежуточным TCP-прокси.
4. **Гонка доставки пакетов (Race Condition):** Асинхронная пересылка между сокетами может успеть доставить клиенту пакет ответа PostgreSQL до того, как сработает принудительный сброс сокета (`RST`).
5. **Эвристичность задержки:** Фиксированная пауза (`Task.Delay(50)`) не гарантирует, что PostgreSQL действительно успел выполнить fsync WAL-лога на диск до разрыва соединения.

#### Вывод по Commit ACK Loss:
Локальный TCP-прокси и контейнер Toxiproxy зафиксированы как **направления исследования**. На текущий момент готовый, верифицированный и детерминированный механизм воспроизведения потери ACK коммита в проекте **отсутствует**.

## 6. Изоляция рабочих каталогов и границы TD-003

### 6.1. Гарантии изоляции по `ExecutionToken`

В проекте действуют следующие механизмы изоляции путей:
- Каталог репозитория: `Path.Combine(_baseStoragePath, analysisId.ToString(), executionToken.ToString("D"))` ([RepositorySourceService.cs#L60-L63](../../src/Backend/Infrastructure/GitHub/RepositorySourceService.cs#L60-L63));
- Временный каталог обмена с Docker: `Path.Combine(Path.GetTempPath(), "netscope-database-analyzer", $"{analysisId}_{executionToken:N}")` ([DatabaseContainerRunner.cs#L103-L106](../../src/Analyzers/Database/Runner/DatabaseContainerRunner.cs#L103-L106)).

#### 1. Подтверждённые факты (подтверждено исходным кодом):
- **Уникальность путей:** Разные `ExecutionToken` гарантированно формируют разные пути каталогов на файловой системе за счёт использования UUID v4 (`ToString("D")` и `ToString("N")`).
- **Штатная очистка при сохранении владения:** В методе [AnalysisService.cs#L595-L600](../../src/Backend/Application/Services/AnalysisService.cs#L595-L600) при контролируемом сбое конвейера и подтверждённом владении (`ownershipConfirmed == true`) вызывается `repositorySourceService.CleanupAsync(...)`.
- **Защита удаления текущей попытки:** Метод [RepositorySourceService.cs#L90-L115](../../src/Backend/Infrastructure/GitHub/RepositorySourceService.cs#L90-L115) (`EnsureWorkspaceCleanupOwnershipAsync`) проверяет совпадение `guard.ExecutionToken == executionToken` и подтверждает владение в БД перед вызовом `Directory.Delete`.

#### 2. Архитектурные ожидания:
- Новая попытка выполнения задачи должна работать исключительно со своим собственным рабочим каталогом, соответствующим её новому `ExecutionToken`, без доступа к остаточным файлам предыдущих попыток.

#### 3. Неподтверждённые гарантии (требуют дополнительной проверки):
- **Уникальность путей не доказывает полную изоляцию:** Тот факт, что пути каталогов различны, сам по себе не гарантирует отсутствия взаимного влияния процессов.
- **Отсутствие чтения старых каталогов во всех путях выполнения:** Требуется дополнительная проверка и тесты, доказывающие, что компоненты анализа (включая синтаксический анализ Roslyn, сборочные адаптеры и проверки зависимостей) строго ограничены границами переданного `context.RepositoryPath` и ни при каких условиях не осуществляют чтение соседних каталогов (например, через подъём вверх по дереву каталогов `..`).
- **Защита всех операций записи и удаления:** Не подтверждено, что зомби-воркер со старым токеном лишён возможности удалить родительскую директорию верхнего уровня `{analysisId}`, в которой расположен каталог новой попытки.
- **Отказоустойчивость при крашах:** При аварийном завершении процесса очистка каталогов не выполняется.

Задача **`TD-003`** сохраняет статус **`DEFERRED`**.

### 6.2. Ограничения и остаточные риски (Зона TD-003)

- **Аварийный сбой процесса:** При аварийной остановке хоста, нехватке памяти (Linux OOM killer) или `kill -9` блоки `finally` не выполняются. Каталоги упавших попыток **остаются на диске**.
- **Временные каталоги Docker:** Каталоги в `/tmp` также остаются на диске при аварийных падениях.
- **Статус TD-003:** Фоновый сервис периодического сканирования и удаления осиротевших каталогов (`AnalysisCleanupService`) относится к задаче **`TD-003`**, которая сохраняет статус **`DEFERRED`**.

> [!WARNING]
> Формулировка «100% изоляция» к файловой системе не применяется. В рамках TD-007 обеспечивается разделение путей рабочих каталогов разных попыток при использовании различных ExecutionToken. Полная изоляция файловых операций и отсутствие взаимного влияния процессов требуют дополнительной проверки. Очистка каталогов после аварийного завершения остаётся в границах TD-003 (задача сохраняет статус **`DEFERRED`**).

## 8. `AttemptCount`, `MaxAttempts` и публичный API

### 8.1. Семантика и назначение полей
- `AttemptCount`: счётчик количества захватов задачи воркерами;
- `MaxAttempts`: максимальное число попыток (значение `3` является рабочим предложением и требует утверждения);
- `NextAttemptAt`: отметка времени СУБД для сокрытия задачи из выборки на период backoff.

### 8.2. Публичный API и DTO
- Проведён анализ планов развития API ([API-Stabilization-Plan.md](API-Stabilization-Plan.md)) и требований к UI.
- **Установлено:** Реальные требования к отображению `AttemptCount` и `NextAttemptAt` в пользовательском интерфейсе **отсутствуют**.
- **Решение:** Публичный контракт DTO `AnalysisDto` ([AnalysisDto.cs](../../src/Backend/Application/DTOs/AnalysisDto.cs)) в рамках TD-007 **НЕ расширяется**. Поля остаются сугубо внутренней деталью инфраструктуры очереди.

### 8.3. Требуемые изменения схемы БД (для будущего этапа реализации)

```sql
-- Предварительная спецификация миграции таблицы Analyses
ALTER TABLE "Analyses"
    ADD COLUMN "AttemptCount" integer NOT NULL DEFAULT 0,
    ADD COLUMN "MaxAttempts" integer NOT NULL DEFAULT 3,
```

### 9.2. Условия перехода TD-007 в статус `READY FOR DESIGN`

Перевод задачи TD-007 в статус **`READY FOR DESIGN`** разрешается строго после выполнения следующих условий:
1. **Решён вопрос с Commit ACK Loss (Q-04):** Разработан и верифицирован надёжный механизм сетевого fault-injection тестирования (например, на базе Toxiproxy или протокольного прокси), подтверждающий идемпотентность `CompleteAsync` без использования эвристических пауз;
2. **Проверена работа `!= ALL(...)` в Npgsql (Q-01):** Подтверждена корректность генерации SQL драйвером Npgsql при передаче коллекций идентификаторов в запросах к PostgreSQL;
3. **Верифицирована семантика восстановления после hard crash и лимита попыток (Q-02):** Интеграционным тестом на PostgreSQL доказано, что задача со stale lease после аварийного сбоя воркера захватывается с увеличением `AttemptCount`, а при достижении лимита `AttemptCount >= MaxAttempts` атомарно переводится в статус `Failed` без запуска нового цикла выполнения анализа;
4. **Верифицирована защита конкурентных обновлений (Q-03):** Многопоточным интеграционным тестом подтверждено, что предикат условного обновления надёжно отсекает попытки записи от устаревших воркеров (`affected == 0`), а конкурентные параллельные воркеры физически не способны превысить лимит `MaxAttempts`;
5. **Протестированы коллизии серверных сроков Rate Limit (Q-05):** Разработана спецификация и создан набор unit-тестов, верифицирующий расчёт наибольшей задержки $\max(T_{\text{RetryAfter}}, T_{\text{RateLimitReset}})$ с чётким разделением источников требований:
   - стандарты RFC 7231 / RFC 9110 — для форматов и семантики HTTP-заголовков `Retry-After` (delta-seconds, HTTP-date) и `Date`;
   - официальная документация GitHub REST API — для формата и семантики заголовка `X-RateLimit-Reset` (Unix epoch seconds);
   - отдельные тестовые сценарии — проверка взаимодействия этих заголовков, выбор максимального обязательного срока ожидания и верификация основных классов некорректных данных и граничных случаев:
     * отрицательные значения;
     * пустые значения;
     * некорректные даты;
     * переполнение числовых типов;
     * прошедшие даты;
     * отсутствие заголовка `Date`;
     * конфликтующие значения `Retry-After` и `X-RateLimit-Reset`.
   *(На текущем этапе зафиксировано, что такие тесты в репозитории отсутствуют и должны быть созданы на этапе реализации)*;
6. **Определено безопасное поведение при превышении технического предела очереди (Q-06):** Спроектирована и верифицирована спецификация поведения очереди, гарантирующая, что если серверный срок ожидания превышает поддерживаемый технический предел очереди, задача не ставится в повтор с усечённым сроком, а завершается со статусом `Failed` с фиксацией диагностического сообщения;

### 9.3. Фактическое выполнение требований верификации и статус реализации (TD-007 Fix 1 / Fix 2 / Fix 3)

Все вышеперечисленные условия перехода и требования верификации были последовательно реализованы и технически подтверждены:
1. **Q-01..Q-03 (Управление очередью, пропуск кандидатов, Poison Pill и строгий контроль владения):**
   - Реализована выборка с `!= ALL(@skippedCandidateIds)` с типизацией `NpgsqlDbType.Array | NpgsqlDbType.Integer`.
   - Атомарная нейтрализация Poison Pill при `AttemptCount >= MaxAttempts` с переводом в `Failed`.
   - Строгий контроль владения: устранены все guard-less перегрузки. Защищённые операции записи в PostgreSQL выполняются через физическое соединение guard, удерживающее session advisory lock (`pg_locks.pid = pg_backend_pid()`), что исключает TOCTOU race conditions.
   - Запрет `NULL` lease: `"LeaseExpiration" >= clock_timestamp()`.
2. **Q-04 / Q-04-A / Q-04-B / Q-04-C (Ambiguous COMMIT ACK Loss Recovery):**
   - Разработан потоковый парсер PostgreSQL wire protocol 3.0 (`PostgreSqlProtocolParser`) с юнит-тестами (26/26).
   - Внедрён in-process proxy `PostgreSqlLoopbackFaultProxy` с перехватом пакета `CommandComplete('COMMIT')` и аварийным обрывом сокета через TCP RST (`LingerState = 0`).
   - Реализована ветка восстановления в `AnalysisService`: независимое чтение состояния задачи через `GetByIdAsync`, проверка токена, безопасная очистка рабочего каталога (`CleanupAsync`) и предотвращение дублирования `AnalysisResult`.
   - Полное покрытие интеграционными тестами `PostgreSqlCommitAckLossIntegrationTests` (5/5).
3. **Q-05..Q-07 (Парсинг Rate Limit и безопасность метаданных):**
   - `GitHubRateLimitParser` реализован по RFC 9110 (IMF-fixdate, RFC 850, asctime, delta-seconds, дельта серверных часов `Date`).
   - Исключена утечка токенов и чувствительных данных (диагностический allow-list заголовков).
   - `AnalysisRetryPolicy` с экспоненциальной задержкой, джиттером и ограничением 15 мин (cap).
4. **Q-09 (Временная модель):**
   - Серверное время `clock_timestamp()` используется во всех SQL-запросах очереди.
