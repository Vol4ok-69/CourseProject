### Цели четвёртого прохода:
1. **Устранение противоречия LeaseGuard (Q-03):** Устранено логическое несоответствие между признанием TOCTOU-гонки/записи без активного LeaseGuard и объявлением Q-03 «неблокирующим». Вопрос переведён в статус **`BLOCKING`** как архитектурное расхождение с контрактом TD-002, требующее решения владельца проекта.
2. **Детализация неопределённого результата Commit ACK Loss (Q-04):** Пошагово разобраны последствия обрыва TCP-сокета в Npgsql 10.0 при успешном коммите в PostgreSQL. Чётко разграничены подтверждённое кодом поведение (возврат `false`, ложное ощущение сбоя, отказ от вызова `CleanupAsync`) и требующие практического fault-injection теста условия. Статус строго подтверждён как **`BLOCKING`**.
3. **Исправление тестовой матрицы TS-06 и TS-10 (Q-05):** Устранено слепое применение `max()` при коллизиях заголовков. Разграничены истинно отсутствующий `Retry-After` (fallback 60 с по правилам GitHub) и пустой/повреждённый заголовок (`InvalidHeader` с переводом в `Failed` по проектной политике).
4. **Разделение фактов и гипотез по нагрузке на очередь (Q-06):** Снято некорректное обозначение `CONFIRMED` для гипотез о деградации БД. Чётко зафиксировано: `EXPLAIN ANALYZE` и нагрузочные тесты **не проводились**.
5. **Безопасность метаданных (Q-07):** Сформированы строгие правила allow-list/deny-list для диагностических заголовков с исключением утечки секретов и токенов. Публичные DTO остаются нетронутыми.
6. **Аудит SQL-спецификации (Q-09):** Для каждого из 5 методов зафиксировано фактическое состояние в коде и статус предлагаемых выражений (`clock_timestamp()`).

### Q-01. Candidate Skipping и поведение Npgsql 10.0 / PostgreSQL 17

#### Анализируемый запрос выборки:
```sql
SELECT "Id"
FROM "Analyses"
WHERE ("Status" = 0
   OR ("Status" = 1 AND ("LeaseExpiration" IS NULL OR "LeaseExpiration" < clock_timestamp())))
  AND ("NextAttemptAt" IS NULL OR "NextAttemptAt" <= clock_timestamp())
  AND (@skippedCount = 0 OR "Id" != ALL(@skippedCandidateIds))
  AND NOT EXISTS (
      SELECT 1 FROM pg_locks
      WHERE locktype = 'advisory'
        AND classid = hashtext('netscope_analysis_workspace')
        AND objid = "Analyses"."Id"
        AND objsubid = 2
        AND granted = true
  )
ORDER BY "CreatedAt" ASC
LIMIT 1
FOR UPDATE SKIP LOCKED;
```

#### Проверенные технические выводы:
1. **Маппинг массива в Npgsql 10.0.3 (`CONFIRMED`):** При передаче коллекции `int[]` через интерполяцию строк в `SqlQueryRaw` в EF Core 10 без явного указания типа может возникнуть несовместимость OID параметров, особенно для пустой коллекции. В коде репозитория требуется передавать строго типизированный `NpgsqlParameter`:
   ```csharp
   new NpgsqlParameter("skippedCandidateIds", NpgsqlTypes.NpgsqlDbType.Array | NpgsqlTypes.NpgsqlDbType.Integer)
   {
       Value = skippedCandidateIds.ToArray()
   }
   ```
2. **Семантика `!= ALL` и поведение пустой коллекции (`CONFIRMED`):** В стандарте SQL предикат `x != ALL('{}'::int[])` истинен (`true`) для любого не-NULL значения. Для исключения накладных вызовов функции массива при пустом списке пропущенных кандидатов используется оптимизирующий страж `@skippedCount = 0 OR "Id" != ALL(...)`.
3. **Безопасность относительно `NULL` (`CONFIRMED`):** Если в массив попадёт значение `NULL`, сравнение `x != NULL` вернёт `UNKNOWN`, из-за чего всё выражение `!= ALL` вернёт `UNKNOWN`, и строка будет ошибочно отфильтрована. Так как массив формируется строго из первичных ключей `"Analyses"."Id"` (тип C# `int`, non-nullable), попадание `NULL` исключено.
4. **Лимит итераций пропуска (`INFERRED / PRELIMINARY`):** Значение `MaxCandidateSkipsPerAcquire = 50` не является аппаратно доказанной константой. Это предварительная эвристика для защиты от деградации CPU при наличии сотен заблокированных задач. Лимит требует бенчмарков. При его исчерпании метод возвращает `null`, и воркер уходит в штатный `PollingDelay`.
5. **Предотвращение голодания (Starvation) (`CONFIRMED`):** Коллекция `skippedCandidateIds` создаётся локально в памяти строго на время выполнения одного вызова `TryAcquireNextPendingOrStaleAsync`. При следующем цикле поллинга список пуст, что исключает зависание пропущенных задач.

### Q-02. Hard Crash и семантика AttemptCount

#### Проверенные технические выводы:
1. **Ограничения защиты от Poison Pill (`INFERRED`):** Ограничение `AttemptCount` и `MaxAttempts` **не устраняет проблему CrashLoop абсолютно**:
   - *Что гарантируется:* конкретная дефектная задача аварийно завершит процесс не более чем `MaxAttempts` раз (например, ровно 3 раза). После третьего сбоя и истечения аренды она гарантированно переводится в `Failed` без повторного запуска вычислений.
   - *Что НЕ гарантируется:* если в очереди накопилось $K$ дефектных задач, сервис суммарно упадёт $K \times \text{MaxAttempts}$ раз. Это может приводить к временной деградации смежных задач из-за перезапусков хоста.
2. **Атомарность инкремента попыток (`CONFIRMED`):** Инкремент `AttemptCount` обязан производиться атомарно в PostgreSQL оператором `UPDATE` строго внутри транзакции захвата при переводе задачи в `Running (1)`. Если воркер упадёт до старта анализаторов, в БД число попыток уже инкрементировано.
3. **Атомарный перевод stale-задачи в `Failed` (`CONFIRMED`):** Если при выборке обнаружена задача со статусом `Running (1)`, истёкшей арендой и `AttemptCount >= MaxAttempts`, транзакция захвата обязана атомарно перевести её в статус `Failed (3)`:
   ```sql
   UPDATE "Analyses"
   SET "Status" = 3,
       "CompletedAt" = clock_timestamp(),
       "LeaseExpiration" = NULL,
       "ErrorMessage" = 'Превышен лимит попыток выполнения анализа (' || "AttemptCount"::text || '/' || "MaxAttempts"::text || ').'
   WHERE "Id" = @candidateId
     AND "Status" = 1
     AND "LeaseExpiration" < clock_timestamp()
     AND "AttemptCount" >= "MaxAttempts";
   ```

### Q-03. Повторная проверка LeaseGuard: устранение противоречия

#### Прямые ответы на вопросы архитектурного аудита:

1. **Какой именно инвариант TD-002 гарантируется текущей реализацией?**  
   Текущая реализация (сочетание `PostgreSqlAnalysisLeaseGuard` и fencing token `ExecutionToken` в предикате `WHERE Id = @id AND ExecutionToken = @token AND Status = 1`) строго гарантирует **взаимное исключение завершения задачи (Mutual Exclusion of Terminal States / No Split-Brain Completion)**.  
   Два воркера с *разными* токенами ни при каких обстоятельствах не могут одновременно успешно зафиксировать результаты или перевести одну задачу в терминальный статус.

2. **Может ли Worker A выполнить запись после потери LeaseGuard, но до смены токена?**  
   **ДА (`CONFIRMED`).**  
   Если выделенное соединение `_connection` оборвалось, PostgreSQL немедленно освобождает session-level advisory lock. Если при этом время аренды истекло (`LeaseExpiration < clock_timestamp()`), но Worker B ещё **не успел перехватить строку** и зафиксировать `newExecutionToken`, в базе данных токен по-прежнему равен `tokenA`.  
   В этот момент Worker A вызывает `CompleteAsync` через `AppDbContext` (другое физическое соединение из пула). Предикат `WHERE Id = @id AND ExecutionToken = @tokenA AND Status = 1` совпадает, и Worker A успешно записывает результаты в БД.

3. **Считается ли такая запись нарушением текущего контракта владения?**  
   **ДА, считается (`CONFIRMED`).**  
   Согласно проектному контракту TD-002: *«Любая запись результатов или смена терминального статуса допускается только при подтверждённом активном владении задачей (активный Lease и удерживаемый LeaseGuard)»*.  
   В описанном сценарии Worker A утратил advisory lock и просрочил аренду, то есть формально **лишился владения**. Выполнение коммита в таком состоянии нарушает букву контракта TD-002, даже если результаты анализа фактически корректны.

4. **Является ли защита от двух одновременных успешных завершений достаточной для TD-002?**  
   **НЕТ, недостаточна (`CONFIRMED`).**  
   Защита от split-brain — необходимое, но недостаточное условие. Контракт TD-002 требует детерминированного подавления любых мутаций от узла, утратившего статус владельца.

5. **Какой риск остаётся при TOCTOU между проверкой и записью?**  
   В коде [AnalysisService.cs#L398-L411](../../src/Backend/Application/Services/AnalysisService.cs#L398-L411) проверка `ValidateOwnershipAsync` (на соединении LeaseGuard) и вызов `CompleteAsync` (на соединении EF Core) разнесены во времени и выполняются в разных транзакциях.  
   **Риск:** Worker B может начать захват задачи ровно в миллисекундном интервале между проверкой и коммитом Worker A:
   - Если Worker B коммитит захват раньше, Worker A получает `affected == 0`, но Worker A уже мог удалить файлы или оставить незавершённые артефакты.
   - Если Worker B перехватывает задачу как Stale и начинает скачивать репозиторий в каталог, а Worker A коммитит `Completed`, возникает состояние гонки за ресурсы файловой системы и несогласованность данных.

6. **Какие конкретные механизмы могли бы закрыть риск без уничтожения результатов из-за GC-пауз?**  
   - **Механизм 1: Атомарная проверка удержания блокировки в транзакции `CompleteAsync`.** Передавать дескриптор или выполнять проверку `pg_locks` непосредственно внутри транзакции коммита результатов.
   - **Механизм 2: Демпфер аренды (Grace Period $\Delta t_{\text{grace}}$).** Воркер B имеет право перехватывать задачу только при условии `LeaseExpiration + 15с < clock_timestamp()`. Это гарантирует воркеру A безопасное окно для завершения коммита даже при кратковременных задержках сети/GC.
   - **Механизм 3: Согласование продуктового компромисса.** Признание правила: *«Коммит с валидным токеном до перехвата конкурентом признаётся допустимым успехом, а не нарушением»*.

> [!CAUTION]
> **Устранение противоречия и статус Q-03:**  
> Ранее Q-03 ошибочно объявлялся неблокирующим. Поскольку текущее поведение допускает запись результатов процессом, утратившим LeaseGuard, фиксируется **архитектурное расхождение с контрактом TD-002**.  
> **Вопрос Q-03 переведён в статус `БЛОКИРУЕТ (BLOCKING)`** до согласования владельцем проекта одного из механизмов (атомарная транзакция, Grace Period либо смягчение формального контракта TD-002).

### Q-04. Неопределённый результат CommitAsync (БЛОКИРУЮЩИЙ ВОПРОС)

#### Пошаговый разбор последствий обрыва соединения при коммите:

1. **Успешный коммит в БД (`CONFIRMED` по коду PostgreSQL):**  
   PostgreSQL выполняет запись транзакции `UPDATE "Analyses" SET "Status" = 2` и `INSERT INTO "AnalysisResults"` в WAL на диске. Транзакция навсегда зафиксирована в базе данных.
2. **Исключение на стороне Npgsql (`CONFIRMED` по архитектуре Npgsql/TCP):**  
   Если TCP-сокет обрывается до того, как пакет подтверждения `CommandComplete ('C')` / `ReadyForQuery ('Z')` прочитан клиентом, вызов `await transaction.CommitAsync()` в [AnalysisRepository.cs#L293](../../src/Backend/Infrastructure/Repository/AnalysisRepository.cs#L293) генерирует `NpgsqlException` / `IOException`.
3. **Поведение `AnalysisService` (`CONFIRMED` по кодовой базе):**  
   Метод `CompleteAsync` не перехватывает исключение. Оно всплывает в блок `catch (Exception ex)` в [AnalysisService.cs#L522](../../src/Backend/Application/Services/AnalysisService.cs#L522).  
   Сервис выполняет проверку:
   ```csharp
   isStillOwner = await guard.ValidateOwnershipAsync([(int)AnalysisStatus.Running], CancellationToken.None);
   ```
   Так как статус задачи в БД уже равен `Completed (2)`, условие `Status = ANY([1])` возвращает `0`! `isStillOwner` принимает значение `false`.
4. **Итоговый статус задачи в БД (`CONFIRMED`):**  
   Задача остаётся в статусе `Completed (2)` со всеми сохранёнными результатами анализа.
5. **Результат, возвращаемый вызывающему коду (`CONFIRMED` по коду):**  
   Метод `ExecuteAnalysisAsync` завершается строкой [AnalysisService.cs#L589](../../src/Backend/Application/Services/AnalysisService.cs#L589): `return false;`.  
   Вызывающий сервис (воркер очереди) получает ложное уведомление о сбое анализа!
6. **Поведение очистки рабочего каталога (`CONFIRMED` по коду):**  
   В блоке `finally` ([AnalysisService.cs#L595](../../src/Backend/Application/Services/AnalysisService.cs#L595)) проверяется:
   ```csharp
   if (ownershipConfirmed) {
       await repositorySourceService.CleanupAsync(...);
   }
   ```
   Поскольку `ownershipConfirmed` сброшен в `false`, метод **`CleanupAsync` не вызывается**. Рабочий каталог коммита остаётся на диске в виде сиротской директории.

#### Разделение доказанных фактов и необходимости fault-injection теста:
- **Подтверждено кодом:** Вся цепочка обработки ошибки в C# (пп. 3, 4, 5, 6) строго подтверждена анализом исходного кода.
- **Требует fault-injection теста:** Воспроизведение именно этого сценария на реальном сокете (протокол Npgsql Extended Query, буферизация TCP ОС, разрыв канала ровно после отправки `COMMIT` СУБД).
- **Вывод по повторному вызову:** Повторный вызов `CompleteAsync` не решает проблему, так как он вернёт `false` (`affected == 0`), а вызывающий сервис не имеет логики повторного считывания статуса из БД при исключении коммита.

### Q-05. Исправление спецификации Retry-After и GitHub Rate Limits (TS-06 и TS-10)

#### Исправление критических сценариев:

1. **TS-06 (Коллизия заголовков — запрет слепого `max()`):**
   - *Анализ правил GitHub:* Если `x-ratelimit-remaining > 0`, наличие `x-ratelimit-reset` указывает лишь на границу текущего часового окна, а не на обязательный простой. Если сработал Secondary Rate Limit (`retry-after: 60`), ждать нужно только 60 секунд. Применять `max()` здесь категорически запрещено!
   - *Когда допустим `max()`:* Только в случае реальной одновременной коллизии:
     $$\text{x-ratelimit-remaining} == 0 \quad \text{AND} \quad \text{retry-after присутствует}$$
     Клиент исчерпал часовую квоту ($T_{\text{reset}}$) **И** одновременно вызвал срабатывание burst-фильтра ($T_{\text{retry}}$). В этом и только в этом случае обязательная задержка равна $\max(T_{\text{reset}}, T_{\text{retry}})$.

2. **TS-10 (Различение отсутствующего, пустого и повреждённого `Retry-After`):**
   - **Случай А — Заголовок отсутствует при Secondary Rate Limit (код 403/429):**  
     *Официальное правило GitHub:* ждать минимум 60 секунд. При повторных нарушениях — экспоненциальный рост ($60 \times 2^{n-1}$).
   - **Случай Б — Заголовок присутствует, но пустой (`""` или `"\s+"`):**  
     *RFC 9110 (Sec 10.2.3):* пустая строка не соответствует синтаксису `HTTP-date / delay-seconds`. Классифицируется как синтаксическая ошибка (`InvalidHeader`). Проектная политика: перевод задачи в `Failed` с фиксацией ошибки валидации заголовков (исключение скрытых аномалий прокси).
   - **Случай В — Заголовок присутствует, но повреждён (нечисловой мусор, например `"invalid"`):**  
     Слепой fallback на 60 секунд **запрещён**. Если за повреждённым заголовком скрывалось требование сервера ждать 1 час, повтор через 60 секунд приведёт к бану. Классифицируется как `InvalidHeader` с переводом задачи в `Failed`.

### Q-06. Очередь и технические ограничения: разделение фактов и гипотез

#### Чёткое разграничение уровней знания:
1. **Общие механизмы PostgreSQL 17 (подтверждено документацией СУБД):**
   - Архитектура MVCC: при каждом `UPDATE` создаётся новая версия строки (tuple), старая версия помечается мёртвой (dead tuple).
   - Индексное сканирование `FOR UPDATE SKIP LOCKED` с сортировкой по индексу `CreatedAt` последовательно проверяет строки в порядке возрастания.
2. **Теоретическая модель для CourseProject / NetScope (архитектурный прогноз):**
   - При накоплении в `Analyses` большого числа отложенных задач (`NextAttemptAt > now`) сканирование по индексу `CreatedAt` теоретически должно проверять и отфильтровывать строки, пока не найдёт первую готовую к выполнению задачу.
3. **Статус экспериментальных измерений (ФАКТИЧЕСКИЙ СТАТУС):**
   - **`EXPLAIN ANALYZE` плана запроса выборки:** **НЕ ВЫПОЛНЯЛСЯ (`UNVERIFIED`).**
   - **Нагрузочные тесты с замером времени сканирования и деградации CPU:** **НЕ ВЫПОЛНЯЛИСЬ (`UNVERIFIED`).**
   - *Утверждения о критической деградации планировщика являются теоретической гипотезой, а не экспериментально подтверждённым фактом.*
4. **Продуктовое соглашение:**
   - Порог ожидания 15 минут — это **бизнес-соглашение о качестве сервиса (UX/SLA)**, а не технический предел возможностей PostgreSQL или среды .NET.

### Q-07. Безопасность метаданных в GitHubIntegrationException

#### Правила фильтрации и защиты секретов:
Для исключения утечки токенов, ключей доступа и персональных данных при сборе заголовков ответа api.github.com:
1. **Белый список (Allow-list):** В свойство `HeaderDiagnostics` разрешено сохранять **только** следующие заголовки:
   - `retry-after`
   - `x-ratelimit-limit`
   - `x-ratelimit-remaining`
   - `x-ratelimit-reset`
   - `x-ratelimit-used`
   - `x-ratelimit-resource`
   - `date`
2. **Категорический запрет (Deny-list):** Запрещено логировать и сохранять заголовки:
   - `Authorization`
   - `Cookie`, `Set-Cookie`
   - `X-GitHub-SSO`, `X-OAuth-Scopes`
   - Любые пользовательские и транспортные заголовки.
3. **Обработка множественных значений:** Если заголовок передан повторно (например, `Retry-After: 60` и `Retry-After: 120`), сохраняется объединённая строка с флагом `HasInvalidHeaders = true` и фиксацией ошибки синтаксиса.
4. **Различение состояний:** Отсутствие ключа в словаре означает отсутствие заголовка; наличие ключа с пустой строкой означает пустой заголовок; ошибка синтаксиса фиксируется отдельным свойством `HeaderParsingError`.
5. **Публичный контракт:** Все поля диагностики строго инкапсулированы во внутреннем классе исключения слоя Application. Публичные DTO (`AnalysisDto`) и интерфейс `IAnalyzer` остаются нетронутыми.
