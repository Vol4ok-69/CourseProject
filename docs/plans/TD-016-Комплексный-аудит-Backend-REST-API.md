## 1. Назначение документа

Настоящий документ фиксирует план комплексного независимого аудита Backend и REST API проекта CourseProject / NetScope перед началом полноценной разработки клиентских приложений.

Аудит должен установить фактическое техническое состояние серверной части, выявить оставшиеся дефекты и риски, проверить согласованность API-контрактов, а также определить, достаточно ли существующего набора HTTP-эндпоинтов для реализации запланированных клиентов:

- CLI на .NET 10 / Spectre.Console;
- Desktop на Tauri / React / TypeScript;
- Telegram-бот на .NET 10 / Telegram.Bot.

Проверка полноты эндпоинтов является обязательной самостоятельной частью аудита. Наличие работающих контроллеров, успешных тестов или корректной OpenAPI-спецификации само по себе не доказывает, что API предоставляет все операции, необходимые клиентам.

Результатом TD-016 должен стать доказательный отчёт и приоритизированный план последующих работ. Исправление найденных проблем в рамках TD-016 не выполняется.

Аудит проводится на фактическом состоянии репозитория на момент начала работ. Документация и предыдущие отчёты используются как источники контекста, но не заменяют проверку реализации.

Если перечисленный файл отсутствует, перемещён или переименован, агент должен найти его актуальный эквивалент и зафиксировать это в отчёте. Не следует считать старые сведения актуальными без проверки.

Перед началом аудита агент обязан:

1. Зафиксировать текущую Git-ревизию.

5. Зафиксировать исходные результаты тестирования и команды, которыми они были получены.
6. Отметить ограничения среды, которые мешают провести отдельные проверки.

Ранее закрытые задачи, включая TD-001, TD-002, TD-003, TD-006, TD-007 и связанные замечания API, необходимо проверять выборочно в соответствии с их влиянием на рассматриваемые области. Статус `VERIFIED` в документации не является самостоятельным доказательством текущей корректности кода.

## 3. Обязательные правила проведения аудита

В рамках TD-016 действуют следующие ограничения:

- Не изменять исходный код и конфигурацию приложения.
- Не выполнять рефакторинг и не исправлять найденные дефекты.
- Не создавать, не изменять и не удалять миграции PostgreSQL.
- Не менять существующие HTTP-маршруты, DTO и публичные API-контракты.
- Не удалять и не переименовывать существующие эндпоинты.
- Не добавлять новые эндпоинты в рамках аудита.
- Не изменять тесты; допускается запуск существующих тестов и анализ их покрытия.
- Не выполнять Git commit, push, reset, checkout, clean, stash и другие операции, изменяющие Git-состояние или пользовательские изменения.
- Не объявлять дефект подтверждённым без ссылки на фактическую реализацию, воспроизводимый сценарий или иное достаточное доказательство.
- Не считать наличие теста доказательством корректности поведения без анализа того, что именно тест проверяет.
- Не предлагать новые эндпоинты только ради симметрии REST или единообразия маршрутов.
- Не считать операцию необходимой только потому, что она присутствует в другом продукте или типовом CRUD-наборе.
- Не раскрывать секреты, токены, пароли, персональные данные и содержимое конфигурации, не предназначенное для публикации.

Агент может запускать сборку, тесты, статические анализаторы, запросы чтения к тестовой БД и диагностические команды. Любые проверки, способные изменить данные, должны выполняться только на специально предназначенной тестовой среде и после проверки их безопасного характера.

Если для достоверной проверки требуется недоступная инфраструктура (например, Docker или PostgreSQL), агент должен указать ограничение и не подменять интеграционную проверку предположением.

## 4. Этапы аудита

### Stage 0. Подготовка и фиксация исходного состояния

**Цель:** обеспечить воспроизводимость аудита и определить точную версию системы, которая проверяется.

Работы:

1. Изучить перечисленные в разделе 2 документы.
2. Проверить соответствие документации текущей структуре репозитория.
3. Зафиксировать Git commit hash, состояние рабочей директории и наличие незакоммиченных изменений.
4. Составить перечень проектов решения, основных модулей Backend и тестовых сборок.
5. Зафиксировать доступные среды и зависимости, необходимые для тестирования.
6. Определить, какие проверки можно выполнить полностью, а какие ограничены окружением.
7. Зафиксировать исходный результат сборки и тестов, не выдавая ранее полученные результаты за новый запуск.

**Результаты Stage 0:**

- паспорт аудита с ревизией и состоянием рабочей директории;
- перечень изученных документов и исходных проектов;
- перечень доступных и недоступных проверок;
- исходные результаты сборки и тестирования с командами и датой запуска.

**Критерий завершения:** исходная точка аудита однозначно определена, пользовательские изменения сохранены, ограничения среды документированы.

### Stage 1. Независимый аудит Backend и REST API

**Цель:** проверить корректность серверной реализации и взаимодействия её слоёв.

Проверить:

1. Архитектуру и границы ответственности `Domain`, `Application`, `Infrastructure`, `Api`.
2. Контроллеры: маршруты, HTTP-методы, статусы ответов, отсутствие необоснованной бизнес-логики.
3. Сервисы: бизнес-правила, обработку ошибок, транзакции и согласованность операций.
4. Репозитории: корректность запросов, ограничения выборок, обработку отсутствующих сущностей и конфликтов.
5. Авторизацию: JWT, роли, владение ресурсами, проверки доступа и риски IDOR.
6. Валидацию DTO: обязательность полей, ограничения длины и диапазонов, nullable-семантику, граничные значения.
7. Конкурентность: гонки, повторные запросы, дедупликацию операций, блокировки и целостность состояния.
8. Обработку ошибок: RFC 9457 ProblemDetails, корректность HTTP-кодов, отсутствие утечек внутренних данных.
9. Внешние интеграции, прежде всего GitHub API: классификацию ошибок, лимиты, таймауты и поведение при недоступности сервиса.
10. Фоновую обработку: очередь, lease, ExecutionToken, повторные попытки, восстановление после сбоев и безопасную очистку.
11. Логирование и диагностику: traceId, полезность диагностических событий, отсутствие секретов и чувствительных данных.
12. Соответствие реализации принятым архитектурным решениям и ограничениям MVP.

Отдельно оценить риски регрессий в компонентах, изменённых при реализации TD-001, TD-002, TD-003, TD-006 и TD-007.

**Результаты Stage 1:**

- перечень подтверждённых дефектов Backend/API;
- перечень архитектурных и эксплуатационных рисков;
- ссылки на файлы, типы, методы и строки кода;
- воспроизводимые сценарии или объяснение способа подтверждения;
- предварительная оценка приоритетов.

**Критерий завершения:** ключевые компоненты Backend проверены, а каждое зарегистрированное замечание имеет доказательную базу.

### Stage 2. Обязательный аудит полноты REST-эндпоинтов

**Цель:** определить, достаточно ли существующего REST API для реализации всех предусмотренных пользовательских сценариев CLI, Desktop и Telegram-бота.

Этот этап обязателен независимо от результатов остальных проверок. Его нельзя считать выполненным только на основании проверки Swagger или инвентаризации контроллеров.

#### 2.1. Инвентаризация фактических эндпоинтов

Собрать полный каталог HTTP-операций непосредственно из реализации. Для каждого эндпоинта указать:

- HTTP-метод и фактический маршрут;
- контроллер и действие;
- назначение операции;
- требования к аутентификации и авторизации;
- входные параметры и DTO;
- формат и DTO ответа;
- возможные HTTP-статусы и ошибки;
- пагинацию, фильтрацию и сортировку, если применимо;
- связанные ресурсы и ограничения доступа.

Сопоставить фактический каталог с OpenAPI/Swagger и документацией. Отдельно отметить маршруты, которые реализованы в коде, но отсутствуют в OpenAPI, и маршруты, описанные в OpenAPI, но не подтверждённые реализацией.

#### 2.2. Функциональная декомпозиция

Проверить покрытие следующих функциональных областей:

- регистрация и аутентификация;
- получение и изменение профиля пользователя;
- управление проектами;
- подключение и настройка GitHub-репозиториев;
- синхронизация коммитов;
- просмотр коммитов;
- запуск анализа;
- получение состояния и истории анализов;
- получение результатов анализа;
- просмотр замечаний и их деталей;
- административное управление пользователями и ролями;
- системная информация и диагностика, если она требуется клиентским сценариям.

Этот перечень является областью исследования, а не требованием реализовать отдельный эндпоинт для каждой строки. Агент должен установить фактические требования по сценариям и архитектуре проекта.

#### 2.3. Проверка сценариев клиентов

Для каждого клиента составить список пользовательских сценариев и последовательность API-вызовов, необходимых для их выполнения.

**CLI:** регистрация/вход, получение текущего пользователя, просмотр и управление доступными проектами, работа с GitHub, синхронизация коммитов, запуск анализа, получение статуса и результатов, обработка ошибок.

**Desktop:** авторизация, навигация и профиль, списки и карточки проектов, подключение GitHub, история коммитов и анализов, запуск анализа, просмотр результатов и деталей замечаний, доступные пользователю операции управления.

**Telegram-бот:** предусмотренный проектом способ идентификации или привязки аккаунта, получение доступной пользователю информации, проверка статуса анализа и получение уведомлений/результатов в пределах утверждённого назначения бота.

Не предполагать, что Telegram-бот должен иметь весь набор возможностей CLI или Desktop. Не придумывать функции, которых нет в утверждённом назначении клиента. Неясные продуктовые решения помечать как вопросы, требующие решения владельца проекта.

#### 2.4. Поиск функциональных пробелов

Определить:

- сценарии, которые невозможно выполнить через существующий API;
- операции, для которых клиенту пришлось бы обращаться напрямую к БД или обходить API;
- недостающие операции чтения, создания, изменения или удаления ресурсов, если они требуются подтверждённым сценарием;
- недостаточность фильтрации, сортировки или пагинации;
- отсутствие необходимых сведений о состоянии фоновой задачи;
- контракты, вынуждающие клиента выполнять неоправданно много запросов;
- невозможность корректно обработать ошибки или определить доступность операции;
- дублирующие, избыточные или неоднозначные эндпоинты.

Для каждого предлагаемого нового эндпоинта указать конкретный пользовательский сценарий, который сейчас невозможно или неоправданно сложно реализовать, и объяснить, почему существующие операции не решают задачу.

### Stage 3. Аудит PostgreSQL и производительности

**Цель:** выявить проблемы целостности данных, конкурентного доступа и производительности.

Проверить:

1. Соответствие EF Core-моделей, конфигураций и миграций фактической схеме PostgreSQL.
2. Первичные и внешние ключи, уникальные ограничения, проверки и поведение каскадных операций.
3. Индексы, составные индексы и соответствие индексов реальным запросам.
4. Потенциальные N+1 и избыточные обращения к БД.
5. Запросы с неограниченными выборками и неэффективной пагинацией.
6. Транзакционные границы и обработку конфликтов.
7. Блокировки и конкурентные сценарии.
8. Критичные запросы через `EXPLAIN` / `EXPLAIN ANALYZE` на безопасной тестовой БД с репрезентативными данными.

Отдельно проверить отложенное замечание API-023. Не удалять и не изменять индексы только на основании предположений: выводы должны опираться на планы запросов, фактические сценарии и измерения.

**Результаты Stage 3:**

- перечень проблем схемы и целостности;
- перечень потенциально тяжёлых запросов;
- результаты измерений и планы выполнения, если проверка доступна;
- рекомендации по индексам и запросам;
- ограничения достоверности измерений.

**Критерий завершения:** рекомендации по производительности имеют измеримое обоснование либо явно обозначены как гипотезы, требующие отдельного нагрузочного тестирования.

### Stage 4. Независимый аудит безопасности

**Цель:** проверить защиту API, данных, интеграций и инфраструктуры исполнения анализаторов.

Проверить:

1. JWT, аутентификацию, авторизацию и разграничение доступа.
2. IDOR и доступ к проектам, коммитам, анализам и результатам других пользователей.
3. Защиту административных операций и последнего администратора.
4. Хранение, передачу и использование секретов, включая GitHub PAT.
5. CORS и Rate Limiting.
6. Валидацию входных данных и защиту от злоупотребления API.
7. Безопасность архивов: Zip Slip, ZIP-бомбы, квоты и очистку.
8. Изоляцию рабочих каталогов, ExecutionToken, advisory locks и безопасную очистку.
9. Docker Runner: пользователя, capabilities, сеть, файловую систему, ресурсы, таймауты и передачу данных.
10. Утечки внутренних исключений, стектрейсов, SQL, путей и секретов в HTTP-ответах и логах.
11. Поведение при сбоях внешних интеграций и инфраструктуры.

Проверки должны по возможности подтверждаться реальными HTTP-интеграционными или инфраструктурными сценариями. Анализ отдельных методов не заменяет проверку сквозного поведения.

**Результаты Stage 4:**

- реестр подтверждённых уязвимостей и рисков;
- оценка критичности и возможных последствий;
- доказательства и безопасные сценарии воспроизведения;
- рекомендации по устранению;
- ограничения проверки.

**Критерий завершения:** каждое замечание безопасности имеет доказательство, оценку риска и конкретное направление устранения.

### Stage 5. Аудит API-контрактов и OpenAPI

**Цель:** установить, насколько публичный контракт API согласован, полон и пригоден для создания независимых клиентов.

Проверить:

1. Соответствие OpenAPI фактическим маршрутам и HTTP-методам.
2. Схемы запросов и ответов, обязательные поля и nullable-семантику.
3. Корректность DTO и сериализации перечислений.
4. HTTP-статусы и единообразие RFC 9457 ProblemDetails.
5. Схемы авторизации и описание требований к доступу.
6. Параметры пагинации, фильтрации и сортировки.
7. Имена, типы и семантику полей публичных DTO.
8. Описание ошибок и возможных ответов для каждого важного маршрута.
9. Возможность генерации клиентского кода из OpenAPI.
10. Необходимость версионирования и правила будущей эволюции контрактов.

Сопоставить результаты с выводами Stage 2. Наличие схемы в OpenAPI не считать подтверждением функциональной достаточности API.

**Результаты Stage 5:**

- перечень расхождений OpenAPI и реализации;
- перечень неполных или неоднозначных контрактов;
- оценка готовности к генерации клиентов;
- рекомендации по стабилизации и версионированию API.

**Критерий завершения:** публичный контракт сопоставлен с реализацией, а существенные расхождения и ограничения документированы.

### Stage 6. Аудит тестового покрытия

**Цель:** оценить, насколько тесты подтверждают критичное поведение Backend и REST API.

Проверить:

1. Интеграционные тесты с настоящим PostgreSQL.
2. HTTP-тесты через `WebApplicationFactory`.
3. Аутентификацию, авторизацию и разграничение доступа.
4. Конкурентные операции и гонки.
5. Жизненный цикл очереди, lease, повторные попытки и восстановление.
6. Обработку ошибок GitHub API и других внешних зависимостей.
7. Валидацию DTO и граничные значения.
8. Контракты ProblemDetails и отсутствие утечек.
9. Сценарии безопасности, включая изоляцию рабочих каталогов.
10. Регрессионные сценарии ранее исправленных дефектов.
11. Негативные сценарии, в которых система не должна выполнять действие или возвращать успешный результат.

Для каждого критичного сценария установить, какой тест его подтверждает, какой уровень тестирования используется и что именно проверяется. Не оценивать качество тестового набора только по общему количеству тестов.

**Результаты Stage 6:**

- карта покрытия критичных сценариев;
- список отсутствующих или недостаточных тестов;
- перечень тестов, которые дают слабую гарантию;
- рекомендуемые новые тестовые сценарии;
- фактические результаты запусков с командами и окружением.

**Критерий завершения:** для критичных сценариев указаны существующие доказательства тестами или явно зафиксированы пробелы.

### Stage 7. Итоговый отчёт и план последующих работ

**Цель:** объединить результаты этапов и сформировать проверяемый план исправлений.

Итоговый отчёт должен содержать:

1. Краткое заключение о состоянии Backend и REST API.
2. Ревизию и состояние рабочей директории, на которых проводился аудит.
3. Области, проверенные полностью, частично или не проверенные из-за ограничений.
4. Подтверждённые дефекты Backend/API.
5. Риски безопасности.
6. Проблемы PostgreSQL и производительности.
7. Расхождения OpenAPI и реализации.
8. Полный каталог существующих эндпоинтов.
9. Матрицу покрытия CLI, Desktop и Telegram-бота.
10. Список недостающих эндпоинтов с обоснованием необходимости.
11. Неоднозначные требования, по которым требуется решение владельца проекта.
12. Пробелы тестового покрытия.
13. Приоритизированный план устранения замечаний.
14. Рекомендации по готовности API к началу разработки клиентов и оставшиеся ограничения.

Каждое подтверждённое замечание должно содержать:

- уникальный идентификатор;
- краткое название;
- описание фактической проблемы;
- доказательства в исходном коде или результатах проверки;
- способ воспроизведения либо проверяемый сценарий;
- последствия и затрагиваемые компоненты;
- приоритет P0–P3;
- рекомендуемое направление исправления;
- критерии приёмки;
- необходимые тесты;
- зависимости от других задач.

Предлагаемая шкала приоритетов:

- **P0 – Критический:** риск компрометации данных/системы, потери данных или полной недоступности ключевой функции.
- **P1 – Высокий:** существенный дефект безопасности, целостности, надёжности или блокировка основного клиентского сценария.
- **P2 – Средний:** значимый функциональный или эксплуатационный недостаток, для которого существует приемлемый обходной путь.
- **P3 – Низкий:** ограниченное улучшение, техническая чистка или некритичное несоответствие.

Если дефект не подтверждён, его нельзя включать в список подтверждённых проблем. Его можно вынести в отдельный список гипотез или вопросов.

**Результаты Stage 7:**

- единый отчёт TD-016;
- реестр замечаний;
- каталог эндпоинтов;
- матрица клиентских сценариев;
- перечень предлагаемых новых эндпоинтов;
- приоритизированный план последующих задач.

**Критерий завершения:** все этапы имеют зафиксированные результаты, ограничения и выводы; рекомендации можно преобразовать в отдельные задачи с критериями приёмки.

## 5. Условия завершения TD-016

TD-016 можно считать завершённой после выполнения всех следующих условий:

1. Зафиксированы проверяемая ревизия и ограничения среды.
2. Backend и REST API проверены по областям Stage 1.
3. Обязательный аудит полноты эндпоинтов Stage 2 завершён.
4. Для CLI, Desktop и Telegram-бота подготовлена матрица сценариев и покрытия.
5. Каждый рекомендуемый новый эндпоинт обоснован конкретным сценарием и отсутствием подходящей существующей операции.
6. PostgreSQL и производительность проверены в доступном объёме, ограничения измерений задокументированы.
7. Безопасность проверена в доступном объёме, ограничения задокументированы.
8. OpenAPI сопоставлен с фактической реализацией.
9. Тестовое покрытие оценено по критичным сценариям.
10. Подготовлен единый отчёт с доказательствами и приоритизированными рекомендациями.
11. В ходе аудита не изменены исходный код, конфигурация, миграции, тесты и пользовательские Git-изменения.

Отсутствие найденных дефектов не освобождает от подготовки каталога эндпоинтов, матрицы клиентских сценариев и заключения о функциональной достаточности API.

## 6. Работы после TD-016

TD-016 является аудиторской задачей и не включает реализацию исправлений.

По итогам Stage 7 владелец проекта рассматривает отчёт и утверждает отдельный план реализации. Для этого могут быть созданы:

- задачи на исправление подтверждённых дефектов Backend;
- задачи на устранение рисков безопасности;
- задачи на оптимизацию PostgreSQL;
- задачи на корректировку API-контрактов;
- задачи на добавление действительно необходимых эндпоинтов;
- задачи на расширение тестового покрытия.

Предварительное обозначение следующего пакета работ: **TD-017 – Устранение подтверждённых замечаний по результатам TD-016**. Его окончательный состав и нумерация определяются только после аудита, чтобы не создавать заранее не подтверждённый технический долг.

Реализация новых эндпоинтов должна начинаться только после утверждения их назначения, сценариев использования, авторизационных требований, DTO, HTTP-статусов и критериев приёмки.

## 7. Формат итогового заключения

В начале итогового отчёта агент должен дать краткий ответ на следующие вопросы:

1. В каком фактическом состоянии находится Backend?
2. Есть ли подтверждённые критические или высокоприоритетные дефекты?
3. Достаточно ли текущего REST API для CLI?
4. Достаточно ли текущего REST API для Desktop?
5. Достаточно ли текущего REST API для Telegram-бота в пределах его назначения?
6. Какие эндпоинты отсутствуют и почему без них нельзя реализовать конкретные сценарии?
7. Какие контракты API необходимо уточнить или исправить?
8. Какие риски PostgreSQL и безопасности остаются?
9. Какие критичные сценарии недостаточно покрыты тестами?
10. Можно ли начинать разработку клиентов без существенного риска переделки API? Если нет, какие конкретные блокеры необходимо устранить?

Заключение должно различать:
- подтверждённые факты;
- выводы, основанные на результатах тестов и измерений;
- гипотезы, требующие дополнительной проверки;
- продуктовые решения, которые должен принять владелец проекта.

---

**Итоговая цель TD-016:** получить доказательное представление о технической надёжности и функциональной полноте REST API, чтобы начать разработку независимых клиентов на стабильном и достаточном серверном контракте, не возвращаясь к постоянному добавлению базовых API-возможностей в процессе клиентской разработки.
